# 业务架构知识生成器

## 标准母版结构（复用）

- 本文件遵循：文档职责边界 -> 角色定位 -> 何时使用 -> 前置输入 -> 执行流程 -> 输出与交付物 -> 规范引用 -> 执行红线。
- 本文件聚焦"流程与边界"，业务全景格式、流程表格结构、领域建模规则等实现细节统一收敛到 \`references/\`。
- 当规则变更时，优先修改 \`references/\`，避免在 \`SKILL.md\` 重复维护细节。

## 文档职责边界

- 本文件负责：执行路径选择、输入输出边界、交付物范围、更新策略与红线约束。
- 本系列文档专注于业务语义、流程编排和领域建模，不涉及具体技术实现细节。
- 细节规范（业务全景格式、流程表格结构、领域建模规则）统一放 \`references/\`，本文件不重复展开。
- 如与项目既有规范冲突，以项目规范为准并显式说明差异。

### 流水线顺序与编号定义权

- 标准流水线顺序：\`code-knowledge-init\` → \`application-knowledge-init\` → \`business-knowledge-init\`。本技能是流水线的最后一环。
- **业务语义权威**：本技能产出的业务场景（S-*）、领域对象（DO-*）、领域事件（DE-*）等是整个知识库的业务语义最终定稿。
- **S-* 编号仲裁**：由于 application 先于 business 执行，application 已基于代码基线定义了 S-* 编号。本技能**默认复用** application 已有的 S-* 编号（保持编号和语义不变）。但当 business 侧发现 application 的 S-* 粒度过粗（如一个 S-* 包含了多个独立的业务动作），**允许在复用基础上进一步细化拆分**，并在全景册中标注拆分说明。
- **DO-* 编号仲裁**：本技能定义的 DO-* 是业务概念的权威定义。\`knowledge/application/\` 下组件册中的 DO-* 必须与本技能保持一致。
- **APP-*、AG-*、AC-* 不越位**：这些编号的定义权归 \`application-knowledge-init\`，本技能在附录映射表中只引用不定义。

## 角色定位

- 本技能是业务架构知识的沉淀与初始化入口，负责在 \`knowledge/business\` 下生成标准化的业务架构文档。
- 核心价值在于从业务视角统一团队对系统边界、流程和领域概念的认知。
- 本技能不负责写 HTTP 接口路径、数据库物理表名、网关路由配置等技术细节（属于应用架构范畴）；不替代 \`application-knowledge-init\` 定义应用部署单元（APP-*）；不直接扫描源代码（依赖代码扫描基线逆向推导）。

## 何时使用

- "帮我梳理一下系统的业务架构和业务全景"
- "生成业务流程和用例说明"
- "从代码里反推一下领域对象(DO)和领域事件(DE)"
- "更新业务规划和领域模型文档"

## 前置输入

- 必选代码基线：读取 \`ocspec-<xxx>/knowledge/code/<项目名>/\` 下的代码扫描基线作为逆向推导的依据（如通过状态机、枚举、包结构推导领域模型）。若基线不存在，必须向用户说明，不得凭印象推断业务规则。
- 强烈推荐应用基线（优先读取）：若 \`ocspec-<xxx>/knowledge/application/\` 已存在，必须读取以获取 application 已定义的 S-* 编号和 DO-* 定义，默认复用。
- 逆向推导优先级：当只有代码时，推导顺序为：枚举值与常量 > 状态机与状态流转 > 包/模块结构 > 注释与方法命名 > 代码逻辑推断。
- 规范文档：\`references/*.md\`

## 执行流程

### 步骤 1：分析输入真相源与梳理索引
- 目标：确定业务分析的输入材料边界，确保逆向推导有据可依。
- 动作：
  - 定位并读取代码基线和应用架构基线。
  - 若应用架构基线已存在，提取其中的 S-* 编号体系和 DO-* 定义，默认全部复用。
  - 若无任何基线，列出缺失项并向用户说明，确认是否继续。
- 检查点：
  - 若无任何基线，必须向用户索要或标记 \`[需人工确认]\`，不得凭印象生成业务规则。
  - 若 application 已有 S-* 编号，必须记录哪些被复用、哪些被调整。

### 步骤 2：全景、协作与流程分析
- 目标：推导业务架构全景、核心业务流程和用例。
- 动作：
  - 业务架构拆解：梳理出业务群（BG-*）、业务（B-*）和业务场景（S-*）。
  - 业务流程推导：梳理"阶段 → 活动 → 任务 → 步骤"的流程线，识别可变点（VP-*）。
  - 业务用例识别：推导系统的核心参与者及业务用例（UC-*）。
- 检查点：
  - 确保业务流程的拆解逻辑符合业务常识，不得将技术实现步骤混入业务流程。
  - S-* 编号若与应用架构基线已有定义冲突，必须对齐后再继续。

### 步骤 3：领域建模与流程-事件串联
- 目标：建立领域模型，并将流程与事件结合。
- 动作：
  - 领域模型提取：识别子域（SD-*）、领域对象（DO-*）和领域事件（DE-*）。
  - **DO 粒度要求**：从代码基线的包结构、Entity/Domain 类逐个推导，每个独立的业务概念都应有自己的 DO 编号，**不要合并**。
  - **DE 粒度要求**：每个流程活动的关键状态变更点都应产生一个 DE，**不要合并**。
  - 领域事件识别来源：优先从 MQ 生产者、Spring Event、Publisher 逻辑中反推；若系统只有同步调用，则从业务流程的状态变更点推导隐式事件，并标注"隐式事件（代码中无显式 MQ）"。
  - 领域模型关系图：使用 Mermaid erDiagram 绘制核心 DO 之间的关系（聚合、关联、包含）。
  - 流程-事件串联（关键）：将步骤 2 的业务流程与提取出的领域事件结合，明确哪个流程活动触发了哪个领域事件（DE）。
  - 与应用架构互证：对照 \`knowledge/application/\` 下组件册中的 DO-* 定义，确保业务侧 DO-* 与应用侧保持一致，不得出现同名不同义的情况。
- 检查点：
  - 领域事件（DE-*）必须能在业务流程中找到触发源，形成闭环，不得存在无触发源的"幽灵事件"。
  - DO-* 代表业务概念，不得写入数据库物理表名或字段名。

### 步骤 4：按规范生成文档并落盘
- 目标：将推导出的业务架构知识严格按照标准模板输出到指定目录。
- 动作：
  - 若已存在产出，根据用户需求判断更新策略（见"输出与交付物"中的更新策略说明）。
  - 当涉及的业务场景（S-*）或流程极多时，必须首先按照 \`references/business-domain-task-template.md\` 生成 \`task.md\` 任务清单进行分批处理，生成后直接按任务顺序执行。
  - 严格按照各专项规范规定的格式，生成四份核心文件。
  - 在整个业务架构知识完全生成并经用户最终确认后，必须删除临时的 \`task.md\` 文件。
- 检查点：
  - 检查产出路径是否正确。
  - 检查格式是否严格遵循 \`references/\` 下对应的专项规范（\`business-overview-and-planning-spec.md\`、\`business-process-and-use-cases-spec.md\`、\`business-domain-and-orchestration-spec.md\`、\`business-capability-and-appendices-spec.md\`）。

### 步骤 5：生成后自检
- 目标：生成后对照标准自查，确保产出质量，发现问题就地修正。
- 动作：
  - 检查产出路径与文件名是否符合约定（\`ocspec-<xxx>/knowledge/business/\`）。
  - 检查产出语言是否为简体中文。
  - 检查 ID 一致性：S-*、DO-*、DE-* 在四份文档的表格、文字和 Mermaid 图中是否完全一致。
  - 检查逻辑闭环：DE-* 是否都关联到了具体的流程阶段，是否存在无触发源的幽灵事件。
  - 检查边界防越位：文档中是否混入了 HTTP 接口名、数据库物理表名、网关路由配置等技术细节。
  - 检查表格完整性：所有表格是否严格遵循规范中定义的表头，无漏列。
  - 检查不确定项是否明确标注 \`[需人工确认]\`。
  - 若 \`knowledge/application/\` 已存在，检查附录 A 中引用的 APP-*/AG-* 是否在 application 文档中存在。
- 检查点：
  - 文档结构与 \`references/\` 下对应的专项规范一致。
  - 没有遗漏必须产出的文档类型。
  - 自检发现问题必须就地修正，不得遗留已知错误后交付。

## 输出与交付物

- 产出目录：\`ocspec-<xxx>/knowledge/business/\`
- 产出文件：
  - \`business-overview-and-planning.md\`：业务全景与规划（BG/B/S），是全局 S-* 编号的权威定义处。
  - \`business-process-and-use-cases.md\`：业务流程与用例（流程阶段/活动/任务、VP-*、UC-*）。
  - \`business-domain-and-orchestration.md\`：领域建模与流程-事件串联（SD-*、DO-*、DE-*）。
  - \`business-capability-and-appendices.md\`：能力建模与技术映射附录（BC-*、可选 CC-*、与应用架构对照表）。
  - \`task.md\`：（可选，仅在大篇幅或多场景分批生成时必需）
- 产出格式要求：
  - 使用 Markdown
  - 仅使用简体中文
  - 结构与字段严格遵循 \`references/\` 下对应的专项规范（\`business-overview-and-planning-spec.md\`、\`business-process-and-use-cases-spec.md\`、\`business-domain-and-orchestration-spec.md\`、\`business-capability-and-appendices-spec.md\`）
- 更新策略：
  - 首次生成：补齐四份核心文档。
  - 新增业务场景：更新 \`business-overview-and-planning.md\`（新增 S-* 行）和 \`business-process-and-use-cases.md\`（补充对应流程与用例）。
  - 领域模型变化：仅更新 \`business-domain-and-orchestration.md\` 对应 DO-*/DE-* 行及串联表。
  - 能力映射变化：仅更新 \`business-capability-and-appendices.md\`。
  - 全量重建：用户明确要求，或业务边界发生重大变化时执行。

## 执行红线

1. 不臆造输入中不存在的业务规则和流程；无法确定的关系必须标记为 \`[需人工确认]\`；但可从代码推断的内容（如状态机、枚举含义）不得以 \`[需人工确认]\` 占位，必须基于代码实际内容生成。
2. 不绕过项目既有约束；严格遵循 \`references/\` 下对应专项规范的 Markdown 结构，不随意合并或拆分既定章节。
3. 不越位写技术细节——业务文档中禁止出现 HTTP 接口路径、数据库物理表名、网关路由配置等技术实现内容。
4. 术语与 ID 绝对一致：\`S-*\`、\`DO-*\`、\`DE-*\` 在四份文件中的编号和命名必须全局唯一且完全一致。
5. 流程与事件必须闭环：\`business-domain-and-orchestration.md\` 中出现的领域事件（DE-*），必须能在 \`business-process-and-use-cases.md\` 的业务流程中找到触发源。
6. Task.md 生命周期管理：所有任务执行完毕且经用户最终确认后，必须删除 \`task.md\`。
7. APP-*/AG-*/AC-* 不越位定义：附录映射表中引用的应用侧编号必须来自 \`application-knowledge-init\` 的产出，不得自行定义。
8. DO 推导完整性：代码基线中每个独立的 Entity/Domain 类、聚合根、值对象都应有对应的 DO 编号。异常处理记录、审批记录、结案记录、财务交易记录等状态变更产物也应独立建模，不得遗漏。
9. DE 推导完整性：流程册中每个标注了状态变更的步骤都应有对应的 DE。异常处理完成、审批通过/拒绝、零值结案等分支路径的状态变更也应产生独立的 DE，不得仅覆盖主路径。
10. 参与者完整性：核心参与者必须覆盖所有与系统交互的角色，包括内部用户、外部用户和外部系统。外部合作方（如服务商、合作机构）、外部平台（如影像平台、用户管理平台、监管平台）也应作为独立参与者列出。
