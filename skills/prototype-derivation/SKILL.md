# 原型 → 需求推导

本技能聚焦**分析与推导过程**（索引表、推导明细、冲突日志等）。一旦进入**从推导结果撰写并落盘正式需求文档**的阶段，**必须**完整使用 **\`/requirement-analysis\`** 技能包（见下节），**不能**仅用本技能的产出代替该流程。  
**说明**：\`/requirement-analysis\` 表示名为 **\`requirement-analysis\`** 的需求分析技能整体，**不**映射为某个固定仓库路径；具体实现可在 Cursor 技能目录、团队技能库或 monorepo 中挂载，以实际环境为准。

## 何时应用

- 存在**静态原型包**（如 Axure：\`start.html\`、各页 HTML、\`document.js\` / 站点图）。
- 需要从原型区块**追溯**到后续需求项/用例 ID。
- **多页或多段文案**描述同一行为，存在静默冲突风险。
- 规则落在**文本组件、表格**等**默认可见**区域（见下文「HTML 可见性」）。

| 产出 | 作用 |
|------|------|
| **推导索引表** | 一行一事：业务主题 → 原型模块/页面标签 → 主入口文件名（仅文件名即可）。 |
| **推导明细** | 按模块：摘录规则、摘要、待澄清问题。 |
| **冲突 / 决策日志** | 两源不一致处：主题、来源 A、来源 B、建议向产品确认的问题。 |

\`ocspec-<xxx>\\requirements\\<需求英文名>_<yyyymmdd>\\requirement\\\`
其中 \`<需求英文名>\` 与 \`<yyyymmdd>\` 使用本次需求目录命名口径。

## 执行原则

- 以用户提供的原型材料为据，**不臆造**材料中未出现的功能；缺失信息用 **\`[需与产品确认]\`** 并列出待澄清问题。
- 术语、模块命名在全文保持一致。
- **HTML 可见性**规则贯穿全流程：\`display:none\` / \`visibility:hidden\` 节点一律跳过。

## 工作流

### 1. 盘点来源

- 定位**站点图**（如 \`document.js\`、清单或设计工具目录树），显式标注**废弃 / 本期不做**节点。
- 区分**权威主干页**（范围、版本说明、单页总述）与**细节页**（规则、表、流程贴示）。
- 扫描 HTML 或导出文本：\`#u*_text\` 类节点、\`<table>\`、便签；**跳过**带 **\`display:none\`** 或 **\`visibility:hidden\`** 的节点及其子树（不摘录、不生成需求条目）。

### 2. 映射模块（先不必对应 REQ 编号）

- 模块划分对齐**产品主题**（如搜索、下单），而非机械照搬 Axure 页面标题——除非产品即以页面名为准。
- **尽早**产出推导索引表，便于暴露缺口。

### 3. 摘录规则（推导明细）

对每个模块：

- 对将驱动行为的规则**引用原文或紧贴原文转述**；评审需要时可记 **控件 id** 或页面 id。
- **表格**：若表达状态机、权重、映射，转为 Markdown 表收录。
- **HTML 可见性**：凡节点（含祖先）呈现 **\`display:none\`** 或 **\`visibility:hidden\`** 的，**一律忽略**，不写入推导明细、不生成需求。**不**从隐藏块「补规则」。动态面板未在默认视图中展示的 state 导出后常为隐藏，同样忽略；多状态以产品另行指定或可见稿为准。
- **纯图流程**：记「无结构化文字，需视觉评审」，并泛化说明位置（如「某页流程图」），不写死具体仓库路径。

### 3.1 原型规则的重点记录项（必须优先）

当页面存在较多说明文字、表格、列表、弹窗或操作按钮时，不得平均摘录；应优先记录真正驱动业务实现与验收的规则，至少覆盖：

- **入口规则**：从哪里进入、谁可见、什么状态下显示、按钮是否置灰/禁用。
- **触发规则**：点击、提交、切换、审核、超时、自动处理等触发条件。
- **类型与枚举**：申请类型、状态枚举、原因枚举、字段选项、筛选项、页签。
- **表单规则**：必填项、默认值、只读项、互斥关系、条件必填、上传数量/格式限制。
- **结果规则**：提交后是否生成单据、是否翻转状态、是否进入列表、是否需要审核、是否跳转/提示。
- **时效规则**：\`X 天\`、\`15 天\`、超时自动通过、超时禁用、时限内仅支持一次等。
- **展示规则**：列表字段、详情展示块、按仓库/门店/角色维度分组展示、时间轴/协商历史模板。
- **角色与端差异**：调货商、供应商、后管，以及 PC/H5/后台在同一规则下的差异口径。

若页面里同时有“背景说明”和“操作规则”，应优先把**操作规则**写全，再补背景。

### 3.2 原型规则的描述粒度（必须达到）

推导稿中的规则描述不能只写“支持售后”“可平台介入”这类结论句；至少要写到可以被正式需求或测试继续使用的粒度。推荐最少包含：

- **场景/前提**：在哪个页面、哪个状态、哪个角色下成立。
- **动作/条件**：用户做了什么，或系统在什么条件下触发。
- **约束**：字段、枚举、次数、时效、可见性、数量限制。
- **结果**：状态如何变化、是否生成记录、是否跳转、是否提示。

可用一句完整句自检：**“谁在什么页面/状态下，执行什么动作，满足什么约束后，会得到什么结果。”**

### 4. 处理冲突

若两段规则不一致（如长度阈值、步骤顺序）：

- 写入**冲突 / 决策日志**一行；在产品拍板前**不要**合并成单一规则。
- 若一侧明显标为旧版，可写假设，但冲突行仍保留直至产品确认。

### 5. 交接给正式规格（推导侧）

- 明确哪些规则**已稳定**、哪些**待决策**、哪些依赖**其他模块**。
- 建议正式规格对关键规则做**条文内化**（正文或附录收录原文层级），而非仅外链原型文件——以**抽象实践**表述，不绑定具体仓库路径。

### 5.1 复杂模块深扫增强（总表页 + 状态页 + 操作页）

若某模块同时具备**总表/总述页**、**多个状态页**、**列表/详情/动作页**、**后管页**，不得只凭总表页或少数页面完成推导；必须按以下方式增强扫描：

- 先建立**页面角色矩阵**，至少区分：**主规则页**、**状态页**、**入口页**、**动作页**、**后管页**、**纯图页**、**无可见文本页**。
- 若主规则页给出的是**汇总口径**，状态页和动作页必须继续逐页检索，用于补足**入口、表单、字段、按钮、提交结果、是否生成单据、是否翻转状态**等操作细则。
- 对**列表/详情/操作页**，除摘录字段外，还要记录：**入口来源、筛选项、按钮显示条件、按钮结果、跳转目标、状态变化**。
- 对**后管页**，不得因为站点图存在就默认有正文规则；必须分别判断是**导航占位**还是**真正承载规则的页面**。
- 对**纯图页**与**无可见文本页**，必须显式写出“仅视觉参考”或“无可见规则文本”，防止后续误认为遗漏。

### 5.2 跨页一致性核对（必须执行）

当同一业务规则在多个页面重复出现时，推导阶段必须做一次**横向核对**，尤其检查：

- **时效**：\`X 天\`、\`15 天\`、超时自动通过等是否一致。
- **入口**：哪些状态可发起、哪些角色可见、按钮是否置灰。
- **类型**：取消订单、取消商品、退货退款、换货、仅退款等枚举是否一致。
- **结果**：提交后是否生成售后单、是否进入列表、是否翻转订单状态、是否需要审核。
- **状态映射**：调货商、供应商、后管三端状态名是否一一对应。

若发现不一致，先写入**冲突 / 决策日志**，不得在推导稿中自行揉平。

### 6. 正式需求文档阶段（必须配合 \`/requirement-analysis\`）

当需要把推导结果落实为**结构化需求文档 / PRD**（标准章节、5W1H、用例图、节点描述、评审准备等）时，执行者**必须**整体遵循 **\`/requirement-analysis\`** 技能包，包括：

| 内容 | 说明 |
|------|------|
| **主流程与能力** | 该技能对需求接收、5W1H、需求清单、业务流程建模、隐藏场景、非功能、成文与评审的完整定义。 |
| **参考规范** | 技能包内 **\`references/\`** 中的文档结构标准、分析指南、评审清单等（**文件名与条目以该技能包实际内容为准**，如 \`requirement-analysis-standard.md\`、\`5w1h-analysis-guide.md\` 等）。 |
| **衔接关系** | 以本技能产出的**推导索引表、推导明细、冲突 / 决策日志**作为 **\`/requirement-analysis\`** 的**输入材料**；**文档结构、体例与质量标准**一律以 **\`/requirement-analysis\`** 为准，不得只凭本技能自行定义「正式需求文档格式」。 |

**定位方式**：在当前环境（如 Cursor 已启用的技能、或团队文档中的技能说明）中查找名为 **\`requirement-analysis\`** 的技能包并**通读**后再撰写正式文档；**不要**假设其在仓库中的物理路径。

## 推导 Pass 质量清单

- [ ] 每个 P0 主题至少对应一个已点名的主原型来源。
- [ ] 已完成**页面角色矩阵**，区分主规则页、状态页、入口页、动作页、后管页、纯图页、无可见文本页。
- [ ] 表格与枚举规则已收录，或已写明暂缓原因。
- [ ] 已按「忽略 CSS 隐藏节点」规则处理，未将 \`display:none\` / \`visibility:hidden\` 内容误写入需求。
- [ ] 对总表页已做**支撑页补检**，未用汇总页替代状态页/操作页细则。
- [ ] 冲突已列出，未凭主观合并。
- [ ] 非文字类视觉已标出待干系人确认。
- [ ] 已完成至少一次**跨页一致性核对**（时效、入口、类型、结果、状态映射）。

## 反模式

- 未经用户说明就写入**特定仓库路径**或内部工单链接。
- 因「某页看起来更新」就跳过冲突行——除非产品已确认。
- 把**推导稿**（追溯、摘录）与**权威规格**（签字范围、完整非功能）混为一谈。
- 从 **\`display:none\` / \`visibility:hidden\`** 节点抽取条文并写入需求（违反本文「HTML 可见性」规则）。
