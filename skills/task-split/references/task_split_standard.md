# 前后端任务拆分标准（参考）

本文件作为 \`task-split\`（任务拆分）技能的输出质量基线。

## 0. 输入依据（强制）

- **主依据**：\`backend-design.md\`、\`frontend-design.md\`。任务条目、流程分支、页面/组件边界均以两份设计为准。
- **追溯与核对**：需求文档（如 \`requirement.md\`）用于 REQ 编号对齐、验收范围核对；若设计与需求表述不一致，在「开放问题」中列出。
- **输入齐备**：产出正式 \`task-split.md\` 前须已具备上述两份设计文档；若缺失，先补设计或仅列阻塞项与待办。

## 1. 必备输出章节（文档内顺序）

1. \`本次任务拆分概览\`（应注明所依据的设计文档路径或文件名）
2. \`后端任务清单\`（按模块/技术层次分区；见本文第 4 节）
3. \`前端任务拆分原则与粒度约定\`（见本文第 2 节）
4. \`前端任务清单\`（按功能点分组；见本文第 3 节）
5. \`依赖关系与时序建议\`（任务级；见本文第 5 节）
6. \`开放问题与需人工确认\`

**任务拆分执行顺序（强制）**：先输出/拆分**后端任务清单**，再输出/拆分**前端任务清单**。

**职责边界（强制）**：
- **后端**：数据模型/迁移、对外能力实现与测试、业务规则与事务边界、外部集成、缓存与性能、后端测试与文档。
- **前端**：页面/路由与组件结构、状态管理与交互流程、表单校验与错误/空态呈现、按设计消费后端能力、前端测试与文档（如适用）。

## 2. 前端任务拆分原则

### 2.1 任务粒度

- **适中粒度**：每个任务应聚焦于一个独立的功能模块或组件，完成后可独立验证
- **单一职责**：每个任务只完成一个明确的功能点
- **可测试**：每个任务完成后应有明确的验证标准

### 2.2 任务依赖

- **明确依赖**：在任务描述中说明依赖的前置任务
- **并行任务**：识别可以并行开发的任务
- **关键路径**：标注影响整体进度的关键任务

### 2.3 任务组织

- **按功能点分组**：每个功能点独立组织任务，根据功能点复杂度灵活拆分
- **任务数量自适应**：根据功能点复杂度自动识别所需任务数量，不必强制按固定阶段拆分
- **实现顺序**：按照前端开发的实现流程顺序排列任务（数据准备 → 结构搭建 → 逻辑实现 → 交互完善）
- **按优先级排序**：核心功能优先，增强功能后续

## 3. 前端任务拆分流程

### 3.1 任务拆分步骤

1. **提炼范围**：在 **\`frontend-design.md\`** 中识别页面/模块与对后端能力的调用；若与设计文档之间存在明显不一致，列入「开放问题」。
2. **识别功能点**：根据 **前端设计文档** 识别所有功能点（可对照需求 REQ 编号做追溯标注）。
3. **提取功能点标题**：从前端设计中的功能概述或模块标题提取功能点标题
4. **评估功能点复杂度**：根据数据复杂度、组件复杂度、逻辑复杂度、交互复杂度等维度评估功能点复杂度
5. **确定任务数量**：根据复杂度自动识别所需任务数量，不必强制按固定阶段拆分
6. **分析代码复用**：确定可复用的组件、类型、服务
7. **拆分具体任务**：根据前端设计中的实现方案拆分具体任务，不必强制覆盖所有阶段
8. **检查依赖关系**：确认任务间的依赖关系，标注并行任务和关键路径

### 3.3 任务拆分参考指南（非强制）

以下 7 个阶段可作为任务拆分的参考指南，根据功能点复杂度灵活选择需要的阶段：

1. **数据与接口准备**：创建类型定义、确认服务接口（如需要）
2. **组件结构搭建**：创建组件基础结构、子组件（如需要）
3. **状态管理**：定义状态结构、状态初始化（如需要）
4. **生命周期管理**：数据获取、资源清理（如需要）
5. **核心逻辑实现**：业务逻辑、数据处理、计算（如需要）
6. **交互流程实现**：用户交互、用户反馈（如需要）
7. **边界情况与错误处理**：边界处理、错误处理（如需要）

**使用原则**：根据功能点复杂度灵活选择需要的阶段，不必强制覆盖所有阶段。

## 4. 后端任务拆分标准（任务清单）

后端任务清单用于指导后续实现阶段的“分层、分模块、可交付”工作。任务清单应按照以下结构组织，并输出清晰的编号、状态与依赖关系。

### 4.1 任务清单结构（建议通用分类）

任务清单建议包含以下通用分类（可根据项目实际增减/复制同类模块分组）：

1. 数据库设计
2. 基础功能模块（按项目实际调整；可包含用户/权限/配置等）
3. 核心业务模块（按项目实际调整；包含业务流程/审核/状态流转等）
4. 运营功能模块（按项目实际调整；查询/统计/导出/看板等）
5. 定时任务
6. 外部系统集成
7. 缓存和性能优化
8. 测试
9. 文档

### 4.2 任务编号规范与状态标记

1. **层级编号**：使用 \`主分类.子任务编号\`，例如 \`1.1\`、\`1.2\`、\`2.1\`、\`2.2\`。
2. **主分类递增**：主分类从 \`1\` 开始递增；当某类模块需要复制多组（例如多个基础功能模块、多个核心业务模块）时，复制后的主分类也应继续递增。
3. **子任务递增**：同一主分类下的子任务从 \`1\` 开始递增。
4. **状态标记**：
   - \`- [ ]\`：未完成
   - \`- [x]\`：已完成
5. **完成后的要求**：任务完成后必须将对应状态标记更新为 \`- [x]\`。

### 4.3 任务描述规范

1. 以动词开头：描述要执行的操作（例如“实现/设计/编写/优化/完善”）。
2. 描述要明确目标和范围，避免模糊项（例如避免“用户管理”“用户”这种泛称）。
3. 在任务描述中尽量体现交付物类型与验证方式（如“实现新增功能 + 分页查询 + 详情查看 + 编辑 + 逻辑删除 + 启用/禁用 + 权限控制”等）。

### 4.4 任务分组与执行顺序

1. **分组原则**：
   - 按功能模块分组：同类能力放在同一组
   - 按技术层次分组：数据库设计、业务逻辑、接口、测试等分层组织
   - 按优先级分组：重要任务前置
   - 按依赖关系分组：有依赖的任务放在依赖任务之后
2. **推荐执行顺序**：
   - 数据库设计优先完成
   - 基础功能模块在核心业务模块之前
   - 测试在功能实现之后
   - 文档在功能实现和测试之后

### 4.6 任务依赖表达（补充要求）

与前端任务相同，任何带依赖的后端任务都应在任务拆分结果中显式说明前置任务（例如：服务层依赖数据模型/外部依赖；测试依赖功能实现；文档依赖测试完成）。

## 5. 任务依赖与协作顺序

至少输出一张**任务级**依赖与顺序表：

- **行**：开发任务（后端/前端任务编号或标题）
- **列**：前置任务、阻塞原因（如依赖表结构/外部账号）、外部依赖、建议完成顺序；可选列：对应设计文档章节（便于追溯）

## 6. 开放问题处理

所有不确定项必须：

- 指明属于前端还是后端
- 指明影响到哪些任务或设计文档条目
- 指明需要用户/产品确认的具体问题
