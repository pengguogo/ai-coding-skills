# 前端编码规范

本文档为 \`fullstack-code-implementation\` 技能在前端编码阶段的编码规范参考，实现代码时须遵循本规范。若项目根目录存在 \`frontend-project.md\` 或项目内已有 ESLint/Prettier 等配置，则**项目约定优先**，与本规范冲突时以项目约定为准。

## 一、核心原则

### 1.1 代码质量原则

- **可读性优先**：代码应清晰表达意图，优先考虑可读性而非过度优化
- **一致性**：同一项目内代码风格、命名规范、组织结构应保持一致
- **可维护性**：代码应易于理解、修改和扩展
- **可测试性**：代码结构应便于单元测试和集成测试
- **性能与可维护性平衡**：在保证可维护性的前提下优化性能

### 1.2 架构设计原则

- **单一职责**：每个模块、组件、函数应只负责一个明确的功能
- **关注点分离**：UI、业务逻辑、数据访问应分层清晰
- **依赖倒置**：依赖抽象而非具体实现，便于测试和扩展
- **最小知识原则**：模块间应减少不必要的依赖
- **DRY（Don't Repeat Yourself）**：避免重复代码，提取公共逻辑

### 1.3 框架特定规范识别

- **项目约定优先**：框架特定的编码约定应优先从 \`frontend-project.md\` 中的技术栈说明和项目现有代码中识别
- **识别来源**：
  - \`frontend-project.md\` 中的技术栈章节（识别项目使用的框架）
  - 项目现有代码（识别框架使用模式和约定）
  - 框架官方文档（当项目没有明确约定时，遵循框架最佳实践）
- **约定遵循**：生成的代码应遵循项目中已建立的框架使用约定，保持与现有代码的一致性

## 二、代码风格规范

### 2.1 命名规范

#### 2.1.1 通用命名原则

- **语义化**：命名应清晰表达意图，避免缩写和歧义
- **一致性**：同一概念在不同场景下使用相同的命名
- **长度适中**：避免过短（如 \`x\`, \`tmp\`）或过长（超过 30 个字符）的命名

#### 2.1.2 文件与目录命名

- **目录命名**：使用 \`kebab-case\`（小写字母 + 连字符）
  - 正确示例：\`user-profile/\`, \`order-list/\`, \`shopping-cart/\`
  - 错误示例：\`UserProfile/\`, \`order_list/\`, \`ShoppingCart/\`
- **组件文件命名**：
  - Vue：\`PascalCase.vue\` 或 \`kebab-case/index.vue\`
  - React：\`PascalCase.tsx\` 或 \`PascalCase.ts\`
  - Angular：\`kebab-case.component.ts\`
- **工具文件命名**：使用 \`camelCase.ts\` 或 \`PascalCase.ts\`
  - 正确示例：\`utils.ts\`, \`formatDate.ts\`, \`ApiClient.ts\`
  - 错误示例：\`utils-helper.ts\`, \`format_date.ts\`

#### 2.1.3 变量与函数命名

- **变量命名**：使用 \`camelCase\`
  - 正确示例：\`userName\`, \`orderList\`, \`isLoading\`
  - 错误示例：\`user_name\`, \`OrderList\`, \`is_loading\`
- **常量命名**：使用 \`UPPER_SNAKE_CASE\`
  - 正确示例：\`MAX_RETRY_COUNT\`, \`API_BASE_URL\`
  - 错误示例：\`maxRetryCount\`, \`apiBaseUrl\`
- **函数命名**：使用 \`camelCase\`，动词开头
  - 正确示例：\`getUserInfo()\`, \`handleSubmit()\`, \`formatDate()\`
  - 错误示例：\`UserInfo()\`, \`submit()\`, \`dateFormat()\`
- **布尔值命名**：使用 \`is/has/should/can\` 前缀
  - 正确示例：\`isLoading\`, \`hasPermission\`, \`shouldValidate\`, \`canEdit\`
  - 错误示例：\`loading\`, \`permission\`, \`validate\`, \`edit\`

#### 2.1.4 类型与接口命名

- **类型/接口命名**：使用 \`PascalCase\`
  - 正确示例：\`UserInfo\`, \`OrderItem\`, \`ApiResponse<T>\`
  - 错误示例：\`userInfo\`, \`order_item\`, \`apiResponse\`
- **枚举命名**：使用 \`PascalCase\`，枚举值使用 \`UPPER_SNAKE_CASE\`
  \`\`\`typescript
  enum OrderStatus {
    PENDING = 'PENDING',
    COMPLETED = 'COMPLETED',
    CANCELLED = 'CANCELLED',
  }
  \`\`\`
- **泛型参数命名**：使用单个大写字母，语义明确时使用描述性名称
  - 正确示例：\`T\`, \`K\`, \`V\`, \`TData\`, \`TResponse\`
  - 错误示例：\`type\`, \`key\`, \`value\`

#### 2.1.5 组件命名

- **组件命名**：使用 \`PascalCase\`
  - Vue 模板中：\`<UserProfile />\`, \`<OrderList />\`
  - React：\`<UserProfile />\`, \`<OrderList />\`
  - Angular：\`<app-user-profile>\`, \`<app-order-list>\`
- **组件文件命名**：与组件名保持一致
  - 正确示例：\`UserProfile.vue\`, \`OrderList.tsx\`
  - 错误示例：\`user-profile.vue\`, \`order-list.tsx\`（除非使用目录 + index 形式）

### 2.2 代码格式规范

#### 2.2.1 缩进与空格

- **缩进**：使用 2 个空格（不使用 Tab）
- **行尾空格**：删除所有行尾空格
- **文件末尾**：文件末尾保留一个空行
- **最大行宽**：建议 100-120 个字符，超出时合理换行

#### 2.2.2 引号与分号

- **字符串引号**：统一使用单引号 \`'\`（除非字符串内包含单引号）
- **分号**：语句末尾统一使用分号 \`;\`

#### 2.2.3 对象与数组

- **尾逗号**：对象和数组的最后一个元素后添加尾逗号（便于 Git diff）
- **对象属性**：单行对象属性间使用空格，多行时每行一个属性

#### 2.2.4 函数与箭头函数

- **箭头函数**：单参数时可省略括号，多参数时保留括号
- **函数参数**：参数列表较长时换行，每行一个参数

#### 2.2.5 导入与导出

- **导入顺序**：按以下顺序组织导入
  1. 第三方库（如 \`react\`, \`vue\`, \`lodash\`）
  2. 项目内部模块（使用别名，如 \`@/components\`, \`@/utils\`）
  3. 相对路径导入（\`./\`, \`../\`）
  4. 类型导入（\`import type\`）
- **导入分组**：不同组之间使用空行分隔
- **导出**：优先使用命名导出，默认导出仅用于组件或主要入口

### 2.3 注释规范

#### 2.3.1 注释原则

- **必要性**：代码应自解释，只在必要时添加注释
- **及时更新**：代码变更时同步更新注释
- **清晰简洁**：注释应简洁明了，避免冗余
- **中文优先**：团队内部使用中文注释，对外 API 可使用英文

#### 2.3.2 函数注释

- **公共函数**：使用 JSDoc 风格注释，包含 \`@param\`、\`@returns\`、\`@example\` 等标签
- **复杂逻辑**：在关键步骤添加行内注释，说明"为什么"而非"是什么"

#### 2.3.3 类型注释

- **复杂类型**：为复杂类型添加注释说明，枚举值和接口字段应添加注释

#### 2.3.4 TODO 与 FIXME

- **TODO**：使用 \`// TODO: 描述待办事项\` 标记待实现功能
- **FIXME**：使用 \`// FIXME: 描述问题\` 标记需要修复的问题
- **NOTE**：使用 \`// NOTE: 说明\` 标记重要说明

#### 2.3.5 AI 生成代码注释标记（AI-Generate）

- 【强制】凡由 AI 辅助生成或主要由 AI 产出的前端代码（含组件、函数、Hooks、服务模块、工具函数、样式文件、配置文件等），须在相应位置增加可检索的注释标记 **\`AI-Generate\`**，便于评审、审计与后续人工维护时区分人机贡献。
- **标记文本**：固定使用英文 **\`AI-Generate\`**（大小写一致），可与其他说明文字同处一行，但标记本身须完整出现，勿改写为「AI生成」「auto」等变体。
- **放置位置（按粒度选用，至少满足其一）**：
  - **新建文件（组件/服务/工具/Store 等）**：在文件顶部第一行使用 \`// AI-Generate\` 注释（在 import 语句之前）。
  - **Vue 单文件组件**：在 \`<script>\` 或 \`<script setup>\` 标签内第一行使用 \`// AI-Generate\`。
  - **新增或整段替换的函数/方法**：在函数定义上方一行使用 \`// AI-Generate\`；若仅函数内局部为多行 AI 生成，可在该逻辑块上方单独一行注释 \`// AI-Generate\`。
  - **样式文件**：在 CSS/SCSS/Less 文件顶部或 \`<style>\` 标签内第一行使用 \`/* AI-Generate */\`。
  - **配置文件（JSON/YAML/JS 配置等）**：在文件顶部或生成片段上方使用该文件语法允许的注释形式写入 \`AI-Generate\`（如 JS 配置使用 \`// AI-Generate\`，JSON 不支持注释时在相邻的说明文档中标注）。
  - **HTML 模板片段**：在生成片段上方使用 \`<!-- AI-Generate -->\`。
- **人工修改后**：若已对 AI 生成部分做实质性重写或审核确认，可保留 \`AI-Generate\` 并追加说明（例如 \`// AI-Generate, reviewed by xxx @ 2026-03-23\`），或删除标记（团队约定以「可追溯」为准时建议保留追加说明而非静默删除）。

**Vue 组件示例**：
\`\`\`vue
<script setup lang="ts">
// AI-Generate
import { ref } from 'vue';

const count = ref(0);
</script>
\`\`\`

**React 组件示例**：
\`\`\`tsx
// AI-Generate
import React, { useState } from 'react';

const UserProfile: React.FC = () => {
  const [loading, setLoading] = useState(false);
  // ...
};
\`\`\`

**函数示例**：
\`\`\`typescript
// AI-Generate
export function formatCurrency(amount: number, currency = 'CNY'): string {
  return new Intl.NumberFormat('zh-CN', { style: 'currency', currency }).format(amount);
}
\`\`\`

**局部块示例**：
\`\`\`typescript
export function processOrder(order: Order): void {
  // AI-Generate: 以下为折扣计算逻辑
  const discount = calculateDiscount(order);
  // ...
}
\`\`\`

**样式示例**：
\`\`\`css
/* AI-Generate */
.user-profile {
  display: flex;
  align-items: center;
}
\`\`\`

## 三、架构设计规范

### 3.1 目录结构规范

#### 3.1.1 通用目录结构

所有前端项目应遵循以下基础目录结构：

\`\`\`
src/
├── components/          # 可复用的通用组件
├── views/              # 路由级页面组件（Vue/React Router）
├── layouts/            # 布局组件
├── router/             # 路由配置
├── stores/             # 状态管理（Pinia/Redux/Zustand）
├── services/           # API 服务层
│   ├── http/          # HTTP 客户端封装
│   ├── modules/       # 业务服务模块
│   └── types/         # 服务相关类型定义
├── hooks/              # 自定义 Hooks（React/Vue Composition API）
├── utils/              # 工具函数
├── types/              # 全局类型定义
├── styles/             # 全局样式
├── assets/             # 静态资源
└── main.ts / index.tsx # 应用入口
\`\`\`

#### 3.1.2 目录组织原则

- **按功能模块组织**：相关文件放在同一目录下
- **职责单一**：每个目录有明确的职责
- **层次清晰**：避免过深的目录嵌套（建议不超过 4 层）
- **命名一致**：目录命名使用 \`kebab-case\`

#### 3.1.3 文件组织规范

- **组件文件**：每个组件一个文件，组件名与文件名保持一致
- **类型定义**：与组件相关的类型定义放在同一目录或 \`types.ts\` 文件中
- **工具函数**：按功能模块组织，避免单个文件过大（建议不超过 300 行）

### 3.2 组件设计规范

#### 3.2.1 组件职责

- **单一职责**：每个组件只负责一个明确的功能
- **可复用性**：通用组件应设计为可复用，避免硬编码业务逻辑
- **可组合性**：组件应支持组合使用，通过 props 和 slots 扩展功能

#### 3.2.2 组件拆分原则

- **按功能拆分**：复杂组件按功能拆分为子组件
- **按复用性拆分**：可复用的部分提取为独立组件
- **按数据流拆分**：数据获取、数据处理、数据展示分离

#### 3.2.3 Props 设计

- **类型定义**：所有 props 必须定义类型
- **默认值**：为可选 props 提供合理的默认值
- **验证**：关键 props 添加运行时验证（如需要）
- **文档化**：公共组件的 props 应添加注释说明

### 3.3 状态管理规范

#### 3.3.1 状态管理原则

- **最小化全局状态**：只将需要在多个组件间共享的状态放入全局 store
- **局部状态优先**：组件内部状态优先使用组件自身状态管理
- **状态归一化**：复杂数据结构应归一化存储，避免嵌套过深

#### 3.3.2 Store 组织

- **按业务模块拆分**：每个业务模块对应一个 store
- **命名规范**：store 文件使用 \`useXxxStore.ts\` 或 \`xxxStore.ts\` 命名
- **类型定义**：store 的 state、getters、actions 都应定义类型

### 3.4 服务层设计规范

#### 3.4.1 服务层职责

- **API 封装**：统一封装所有 API 调用
- **错误处理**：统一处理 API 错误
- **类型定义**：为所有 API 定义请求和响应类型
- **请求拦截**：统一处理认证、日志等横切关注点

#### 3.4.2 服务模块组织

- **按业务模块拆分**：每个业务模块对应一个服务文件
- **统一入口**：禁止在组件中直接调用 HTTP 客户端
- **类型分离**：类型定义放在独立的 \`types/\` 目录
- **函数注释**：所有服务函数应添加 JSDoc 注释

### 3.5 工具函数规范

#### 3.5.1 工具函数原则

- **纯函数优先**：工具函数应尽量设计为纯函数，便于测试
- **单一职责**：每个工具函数只做一件事
- **类型安全**：所有工具函数应定义完整的类型
- **文档化**：公共工具函数应添加 JSDoc 注释

#### 3.5.2 工具函数组织

- **按功能分类**：相关工具函数放在同一文件中
- **命名清晰**：函数名应清晰表达功能
- **避免副作用**：工具函数应避免修改外部状态
- **函数注释**：公共工具函数应添加 JSDoc 注释

## 四、TypeScript 规范

### 4.1 类型定义规范

#### 4.1.1 类型使用原则

- **避免 any**：禁止使用 \`any\`，使用 \`unknown\` 或具体类型
- **类型推断**：充分利用 TypeScript 类型推断，避免冗余类型注解
- **类型安全**：所有函数参数和返回值都应定义类型

#### 4.1.2 接口与类型别名

- **接口优先**：对象类型优先使用 \`interface\`，类型别名用于联合类型、交叉类型等
- **命名规范**：接口和类型别名使用 \`PascalCase\`
- **可选属性**：使用 \`?\` 标记可选属性

#### 4.1.3 泛型使用

- **泛型命名**：使用有意义的泛型参数名（如 \`TEntity\`、\`TData\`、\`TResponse\`）
- **约束**：使用 \`extends\` 约束泛型参数

### 4.2 类型导入规范

- **类型导入**：类型导入使用 \`import type\`，避免运行时导入
- **类型导出**：类型导出使用 \`export type\`

### 4.3 类型断言规范

- **避免类型断言**：优先使用类型守卫而非类型断言
- **必要断言**：必须使用断言时，使用 \`as\` 而非 \`<>\` 语法
- **类型守卫**：定义类型守卫函数 \`isXxx(data: unknown): data is Xxx\` 进行类型检查

## 五、错误处理规范

### 5.1 错误处理原则

- **统一处理**：API 错误统一在服务层处理
- **用户友好**：错误信息应对用户友好，避免技术细节
- **错误恢复**：提供错误恢复机制（如重试、降级方案）
- **错误日志**：关键错误应记录日志，便于排查

### 5.2 错误类型定义

- **错误基类**：定义 \`AppError\` 基类，包含 \`message\`、\`code\`、\`statusCode\` 等属性
- **错误子类**：定义 \`ApiError\`（API 错误）、\`BusinessError\`（业务错误）等子类
- **错误命名**：错误类名使用 \`XxxError\` 格式

### 5.3 错误处理实践

- **统一处理**：在 HTTP 客户端拦截器中统一处理错误
- **错误分类**：区分 API 错误（\`error.response\`）、网络错误（\`error.request\`）、其他错误
- **错误转换**：将 HTTP 错误转换为应用错误类型

## 六、性能优化规范

### 6.1 性能优化原则

- **测量优先**：优化前先测量性能，识别瓶颈
- **避免过度优化**：在可维护性和性能间平衡
- **渐进增强**：优先保证核心功能，再优化体验

### 6.2 代码分割

- **路由级分割**：路由组件使用懒加载（如 \`lazy(() => import('@/views/xxx'))\`）
- **组件级分割**：大型组件按需加载
- **第三方库分割**：大型第三方库按需引入

### 6.3 渲染优化

- **避免不必要的渲染**：使用 \`React.memo\`、\`useMemo\`、\`useCallback\`（React）或 \`computed\`、\`watch\`（Vue）
- **虚拟列表**：长列表使用虚拟滚动
- **图片优化**：使用适当的图片格式和尺寸

### 6.4 请求优化

- **请求合并**：合并多个相关请求
- **请求缓存**：合理使用缓存，减少重复请求
- **防抖节流**：用户输入使用防抖（建议延迟 300ms），滚动等事件使用节流（建议延迟 100ms）

## 七、工具配置识别与规则遵循

### 7.1 工具配置文件识别

AI 在编码时应识别**项目根目录**下的工具配置文件，并确保生成的代码遵循这些工具的规则：

- **ESLint**：识别 \`eslint.config.js\`、\`.eslintrc.js\`、\`.eslintrc.json\` 等配置文件
- **Prettier**：识别 \`.prettierrc\`、\`.prettierrc.json\`、\`prettier.config.js\`、\`.prettierrc.js\` 等配置文件
- **Stylelint**：识别 \`.stylelintrc.js\`、\`.stylelintrc.json\`、\`stylelint.config.js\` 等配置文件
- **TypeScript**：识别 \`tsconfig.json\`、\`jsconfig.json\` 等配置文件
- **EditorConfig**：识别 \`.editorconfig\` 配置文件

### 7.2 代码规则遵循

#### 7.2.1 ESLint 规则遵循

- **识别配置**：读取项目中的 ESLint 配置文件，了解项目启用的规则
- **遵循规则**：生成的代码必须通过 ESLint 检查，常见规则包括：
  - 禁止使用 \`any\` 类型
  - 强制使用单引号
  - 强制尾逗号
  - 强制 import 排序
  - 其他项目特定的 ESLint 规则

#### 7.2.2 Prettier 规则遵循

- **识别配置**：读取项目中的 Prettier 配置文件，了解代码格式规范
- **遵循格式**：生成的代码必须符合 Prettier 格式规范，包括：
  - 缩进、引号、分号等格式规则
  - 行宽、换行等格式规则
  - 其他项目特定的 Prettier 规则

#### 7.2.3 Stylelint 规则遵循

- **识别配置**：读取项目中的 Stylelint 配置文件，了解样式代码规范
- **遵循规则**：生成的样式代码必须通过 Stylelint 检查，包括：
  - CSS 属性顺序规范
  - 类选择器命名规范
  - 其他项目特定的 Stylelint 规则

#### 7.2.4 TypeScript 规则遵循

- **识别配置**：读取项目中的 TypeScript 配置文件，了解类型检查规则
- **遵循规则**：生成的代码必须通过 TypeScript 类型检查，包括：
  - 严格模式规则
  - 未使用变量检查
  - 路径别名配置
  - 其他项目特定的 TypeScript 规则
