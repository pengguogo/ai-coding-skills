# 后端代码实现

## 职责边界（本 Skill 专有）

- **任务来源**：默认基于后端设计文档**自动拆分实现任务**。  
- **任务顺序**：按拆分出的依赖顺序执行；**Task N 为 \`Done\` 后才能开始 Task N+1**；默认**串行**推进。  
- **状态流转**：\`Pending\` → \`InProgress\` → \`Done\` / \`Failed\`（失败须记录原因，便于重试或回滚计划）。  
- **文档约定**：任务拆分清单、设计说明、执行日志按当前需求上下文与团队流程维护，不要求固定文件名。  

## 规范来源

- **编码、命名、分层、包与资源路径、配置、Spring MVC、异常与日志、逻辑删除、数据库脚本、测试、安全、审查清单、AI 生成注释标记等**：以 \`references/backend/coding-standard.md\` 为准（重点：**§3.3**、**§8.8**、**§6.5**、**§12.1**）。  
- **具体框架版本、注解习惯、包名与目录结构**：以**当前仓库既有代码**为准；本 Skill **不提供**代码模板。  

---

## 工作流程

### 步骤 1：读取设计输入与任务拆分

**目标**：基于设计文档确定「要做哪些任务、先做哪条任务」，且前置产物已齐。

**动作**：

1. **读取后端设计文档**，提取实现对象：数据模型、接口、服务、任务、测试点。  
2. **自动拆分任务清单**：生成任务 ID、描述、依赖、初始状态（\`Pending\`）。  
3. 若用户额外给出任务约束，则与自动拆分清单合并去重，以用户显式约束优先。  
4. 选出状态为 **\`Pending\`** 且**所有依赖任务已为 \`Done\`** 的条目；若多条可并行，默认一次只推进一条以降低冲突。  
5. 结合仓库现状与需求上下文确认技术栈、模块划分与实现约束。  
6. 将本条任务状态更新为 **\`InProgress\`**，并记下开始时间（用于执行日志）。  

---

### 步骤 2：实现前准备（每条任务执行前）

**目标**：减少风格漂移与路径错误。

**动作**：

1. 在仓库中 **定位同类现有实现**（如已有 Entity、Mapper、Controller），作为命名、分层、异常与返回体的**参照**，而非凭模板臆造。  
2. **路径与包名**：Java 包、Mapper XML、SQL 脚本目录等遵循 **§3.3**、**§8.8**；存量项目**禁止**引入与现网目录不一致的新根路径。  
3. **AI 产出**：凡主要由 AI 编写的类/方法/SQL 片段，按 **§6.5** 标注 **\`AI-Generate\`**。  
4. 若任务涉及**敏感配置**，仅从现有配置文件或环境变量约定延伸，**禁止**硬编码密钥（见规范中安全相关章节）。  

---

### 步骤 3：按任务类型执行（详细）

以下各节**不重复** \`references/backend/coding-standard.md\` 条文；具体注解、日志格式、事务边界、URL 写法等均以规范为准。

#### 3.1 数据库变更任务

1. 从设计或任务文档获取 **DDL/变更脚本**意图。  
2. **存放目录与文件命名**：**§8.8**（新项目与存量区分）；**授权语句**等按同节要求。  
3. 自检 **SQL 语法**与**环境**（方言、是否可重复执行等）。  
4. 更新任务状态为 **\`Done\`** 或失败时 **\`Failed\`** 并写明原因。  
5. 在执行日志中记录产物文件名与备注。  

#### 3.2 Entity 创建任务

1. 对照表结构或 DDL，与现有 Entity **字段类型、注解习惯**（如主键、逻辑删除、审计字段）对齐。  
2. 放置包路径遵循 **§3.3.1 / §3.3.2**（存量对齐现有 Entity 包）。  
3. 逻辑删除与表字段映射遵循规范中**数据删除**相关条款。  
4. 更新任务状态并记录产物类名。  

#### 3.3 Mapper 开发任务

1. 生成 **Mapper 接口**，与现有 Mapper **命名与注解**一致。  
2. 编写 **XML**（若项目使用 XML）：路径 **§3.3.3**；\`namespace\` 与接口全限定名一致。  
3. SQL **参数化**，禁止字符串拼接 SQL（见规范中安全与持久层相关条款）。  
4. 更新任务状态并记录接口/XML 路径。  

#### 3.4 Domain Service 任务

1. 实现领域逻辑，**调用 Mapper/仓储**；与现有 Domain 层**异常与日志**风格一致。  
2. 事务若在本层：按项目惯例与规范中**事务**条款；多数项目以 Service 层为事务边界，以仓库为准。  
3. 更新任务状态。  

#### 3.5 Service 任务（业务编排层）

1. 编排 Domain、外部调用；**\`@Transactional\`** 使用方式与现有 Service 一致。  
2. 日志：**入口/关键分支/外部调用**须有记录，脱敏见规范。  
3. 更新任务状态。  

#### 3.6 Controller 任务

1. **所有映射注解必须显式写出 path**（**§7**）。  
2. 参数校验、统一返回体、**接口日志**（入参/出参/耗时）与现有 Controller 对齐。  
3. 更新任务状态。  

#### 3.7 RPC / Consumer / Schedule / Facade 任务

1. 分别对照仓库中 **Feign/Dubbo、消息监听、定时任务、Facade** 的现有写法。  
2. 包路径仍遵循 **§3.3**；消息 Topic/Group 与现网命名规则一致（若有设计文档则服从设计）。  
3. 更新任务状态。  

#### 3.8 单元测试任务

1. 对**本次新增或修改**的类补测或改测；测试类命名与目录 **§3.3.4**、**§10.3**。  
2. 覆盖主流程与关键异常；Mock 外部依赖，避免依赖本机环境随机性。  
3. 更新任务状态。  

**每条子任务结束时**：状态 **\`Done\`/\`Failed\`**；失败时说明阻塞点（如缺少设计、环境不齐），便于在日志与任务拆分清单中追踪。  

---

### 步骤 4：记录执行日志

**目标**：留下可追溯的实现轨迹。

**动作**：

1. 在当期指定的**执行日志文档**中追加或更新本节任务：**状态**、**起止时间**、**涉及文件/脚本**、**备注**（如联调依赖、已知技术债）。  
2. 维护 **问题记录** 与 **文件清单（新增/修改）**，便于评审与归档。  

**结构示例**：

\`\`\`markdown
# 执行日志
## 执行概览
- **开始/结束时间**、**总任务数**、**成功/失败数**
## 任务执行记录
### Task Txxx
- **状态**、**时间**、**产物**、**备注**
## 问题记录
## 文件清单（新增/修改）
\`\`\`

---

### 步骤 5：自检与交付

**目标**：合并前达到团队最低质量线。

**动作**：

1. 对照 \`references/backend/coding-standard.md\` **§12.1 代码审查检查清单**做自检（命名、异常、日志、**AI-Generate**、路径与脚本等）。  
2. 本地执行**编译**与相关**单元测试**（若项目有约定命令则遵循）。  
3. 若仍有 \`Failed\` 任务，不在此隐瞒；在任务拆分清单与执行日志中保留原因，由流程决定是修复后继续还是上升评审。

# 前端代码实现

## Overview

根据需求分析及设计阶段输出的PRD、UI设计规范和技术方案文档，实现高质量、可维护的前端代码。

**实现范围与依据**：**若有 \`frontend-design.md\`（通常由 \`fullstack-design\` 产出）**，则严格按该文档的**实现路径**进行编码：只实现实现路径所要求的代码，不额外扩展本 SKILL 文档中提及的所有场景（如列表页、表单页、详情页、弹窗、权限、性能优化、测试等）；仅当实现路径明确需要某项能力或用户/任务另有指定时，才实现该项。若无该设计文档，则按 PRD、UI 设计规范和技术方案自行规划实现范围。

**项目上下文**：项目约束与基础架构优先基于 \`ocspec-<xxx>/knowledge/code/<项目名>/frontend-project.md\`。该文档通常包含业务总览、业务功能模块、接口调用清单、目录结构说明、技术栈、项目开发约束等。若存在该文档，本技能在识别项目约束和基础架构时**直接引用该文档**，无需重复按路径扫描；仅当文档缺失或需补充验证时再按路径分析。

**重要说明**：本技能是通用的前端代码实现技能，不基于任何特定项目。无论是新项目还是现有项目，无论是Vue2、Vue3还是React框架，都可以使用本技能进行代码实现工作。本技能会自动检测项目类型，并根据项目实际情况进行调整。

**技术栈说明**：本技能支持多种主流前端框架：
- Vue 2.x
- Vue 3.x
- React

**语言选型**：支持 **TypeScript** 与 **JavaScript**。根据以下规则与项目保持一致：
- **新项目**：以技术方案文档中的技术栈为准；若未明确指定，推荐 TypeScript。
- **现有项目**：必须与现有代码一致——若项目使用 \`.js\`、无 \`tsconfig.json\` 或组件多为无类型写法，则使用 **JavaScript** 实现；若项目使用 \`.ts\`、存在 \`tsconfig.json\`，则使用 **TypeScript** 实现。
- 实现时统一使用一种语言：TS 项目用 \`.ts\`/\`lang="ts"\` 与类型定义；JS 项目用 \`.js\` 或无类型写法，不引入 TS 语法。

## 前置条件

在使用此技能前，需要确保以下文档已准备好：

1. **产品需求文档（PRD）** - 包含功能需求和用户流程
2. **UI设计规范** - 包含设计系统、组件规范和页面设计
3. **技术方案文档**（\`frontend-design.md\`，通常由 \`fullstack-design\` 产出）- 包含技术栈选型、架构设计、实现路径、API 接口定义、组件接口定义等；**若有该文档，则严格按该文档的实现路径执行**。

**项目约束与基础架构来源**（二选一，优先使用1）：
- **1 frontend-project.md**（推荐）：若 \`ocspec-<xxx>/knowledge/code/<项目名>/frontend-project.md\` 存在，则**项目语言、目录结构、技术栈、接口规范、开发约束**等均从该文档中读取，无需在本技能内重复做路径级识别。
- **2 无 frontend-project.md**：在本技能工作流程中通过「确定项目语言 + 扫描现有资源」自行识别（见第零步）。

## 工作流程

以下步骤为**参考性流程**。**若有 \`frontend-design.md\`（通常由 \`fullstack-design\` 产出）**，则以该文档中的**实现路径**为准：实现路径要求的模块、组件、接口、路由等按顺序实现，未涉及的步骤可跳过。若无该文档，则按 PRD 和技术方案自行规划。本流程用于在实现某一步时查阅具体做法。

### 第零步：现有项目分析（如果是现有项目）

在开始代码实现之前，如果检测到是现有项目，**必须先分析现有项目**。项目约束与基础架构的获取方式如下。

#### 优先基于 frontend-project.md（若存在）

若 \`ocspec-<xxx>/knowledge/code/<项目名>/frontend-project.md\` 存在，则：

1. **读取 frontend-project.md**，从以下章节直接获取信息，**无需再按路径重复扫描**：
   - **技术栈** → 项目语言（TypeScript/JavaScript）、主框架、状态管理、路由、UI 库、HTTP 客户端、目录位置等
   - **项目开发约束** → Node 版本、语言配置、环境变量、npm scripts 等
   - **目录结构说明** → 组件目录、视图目录、服务目录、工具目录、样式目录、类型定义目录等及其用途与示例
   - **接口调用清单** → 服务模块路径、HTTP 封装位置、接口调用规范、认证与错误处理方式
   - **业务功能模块** → 功能模块与路由，便于页面开发时对齐

2. **仅在以下情况**下再按路径补充扫描或验证：
   - frontend-project.md 中某类信息缺失或标记为 \`[需人工确认]\`
   - 需要获取具体组件的 props/events、工具函数签名等实现级细节
   - 文档较旧，怀疑与当前代码不一致需核对

3. **识别工具配置**：在根目录识别 ESLint、Prettier、Stylelint、TypeScript、EditorConfig 等配置文件。生成的代码须符合这些配置的规则（详见 \`references/frontend/coding_standard.md\` 第七章）；若项目无某类配置，则按编码规范中的默认约定（如单引号、分号、缩进等）生成代码。

#### 无 frontend-project.md 时的回退流程

若不存在 \`frontend-project.md\`，则按以下步骤自行识别（与原有流程一致）：

**识别工具配置（与有无 frontend-project.md 无关）**
- 在根目录识别 ESLint（\`eslint.config.js\`、\`.eslintrc.*\`）、Prettier（\`.prettierrc*\`、\`prettier.config.js\`）、Stylelint、\`tsconfig.json\`/\`jsconfig.json\`、\`.editorconfig\` 等
- 生成代码须符合上述配置；无配置时遵循 \`references/frontend/coding_standard.md\` 中的格式与规则

**确定项目语言（与后续实现一致）**
- 查看是否存在 \`tsconfig.json\`、\`jsconfig.json\`
- 查看 \`src\` 下主流扩展名：\`.ts\`/\`.tsx\` 为主 → TypeScript；\`.js\`/\`.jsx\` 为主或无 TS 配置 → JavaScript
- 确定后，**整个实现过程与该语言一致**：TS 项目写 TS（含类型）；JS 项目写 JS（不含类型注解）

**扫描现有资源**
1. **扫描公共组件**：使用 \`list_files\` 等工具扫描组件目录（如 \`src/components/\`），识别已有通用组件及其 props、events、使用方式
2. **扫描公共方法**：扫描工具目录（如 \`src/utils/\`），识别工具函数及参数、返回值
3. **扫描公共样式**：扫描样式目录（如 \`src/assets/styles/\`、\`src/styles/\`），识别全局变量与可复用样式
4. **分析 API 请求方式**：查找服务目录（如 \`src/services/\`、\`src/api/\`），分析 HTTP 客户端、拦截器、错误处理与调用格式
5. **分析状态管理**：查找状态管理文件（Pinia/Vuex/Redux 等），了解 store 结构与使用方式

> 说明：若后续会频繁在该项目上做增量开发，建议在 \`ocspec-<xxx>/knowledge/code/<项目名>/frontend-project.md\` 维护该文件，再使用本技能，可避免重复识别路径并保持约束一致。

#### 复用原则

**在开发新功能时，必须优先使用现有资源**：

1. **组件复用**
   - 优先使用已有的公共组件
   - 只有当现有组件无法满足需求时，才开发新组件
   - 保持组件风格一致

2. **方法复用**
   - 优先使用已有的工具函数
   - 避免重复造轮子
   - 保持代码风格一致

3. **样式复用**
   - 优先使用全局样式变量
   - 遵循现有的样式规范
   - 保持设计系统一致

4. **API请求方式**
   - 严格遵循现有的API调用方式
   - 使用相同的HTTP客户端配置
   - 保持错误处理机制一致

### 第一步：项目初始化

#### 1.1 创建项目结构

根据技术方案中的目录结构，创建完整的项目目录。**若存在 frontend-project.md**，优先依据其「目录结构说明」章节中的目录结构树与各目录用途创建；无 frontend-project.md 时参考以下通用结构：

\`\`\`
项目名称/
├── public/
├── src/
│   ├── assets/
│   ├── components/
│   ├── composables/ 或 hooks/
│   ├── layouts/
│   ├── pages/
│   ├── router/
│   ├── stores/
│   ├── services/
│   ├── utils/
│   ├── types/
│   ├── constants/
│   ├── App.vue / App.tsx
│   └── main.ts / main.tsx
├── tests/
└── 配置文件
\`\`\`

#### 1.2 配置开发环境

**如果是新项目**：
- 安装依赖包（根据技术方案）
- 配置构建工具（Vite/Webpack）
- 配置代码规范工具（ESLint + Prettier）
- 配置环境变量（.env文件）

**如果是现有项目**：
- 跳过环境配置步骤
- 直接使用现有项目的配置

#### 1.3 初始化基础配置

**如果是新项目**：
- 配置路由系统
- 配置状态管理
- 配置HTTP客户端
- 配置全局样式
- 配置主题系统

**如果是现有项目**：
- **若存在 frontend-project.md**：从「技术栈」「项目开发约束」「接口调用清单」中读取路由、状态管理、HTTP 客户端、全局样式等配置位置与约定，直接遵循即可，无需重复分析路径。
- **若不存在 frontend-project.md**：按以下方式分析：
  - 分析现有路由配置
  - 分析现有状态管理
  - **重点分析现有HTTP客户端配置**：
    - 查找HTTP客户端文件（TS 项目：\`src/utils/request.ts\` 或 \`src/services/request.ts\`；JS 项目：\`request.js\`）
    - 分析请求拦截器和响应拦截器
    - 了解错误处理机制
    - 记录API调用的标准格式
    - 确保新开发的API服务严格遵循现有方式
  - 分析现有全局样式配置

### 第二步：开发基础组件

#### 2.0 公共方法搜索和复用

**在开发组件之前，必须先搜索现有项目中的公共方法**：

1. **搜索现有公共方法**
   - 扫描 \`src/utils/\` 目录下的工具函数

## 开发原则

### 1. 遵循设计规范
- 严格按照UI设计规范实现
- 保持样式一致性
- 实现所有交互状态

- 避免不必要的渲染

## 编码完成后的轻量门槛（仅编译阶段）

由于当前执行环境不支持服务并联运行/联动交互检查，本阶段仅以“编译/构建可用性”为门槛，防止出现编译失败或前端构建失败导致服务或页面直接起不来/挂掉。

### 步骤 1：后端编译闸门

**目标**：确保本次后端代码变更不会导致编译/构建失败。

**动作**：

1. 在执行后端编译前，先确认构建工具与必要依赖可用（优先使用仓库提供的构建包装器/脚本，避免环境差异导致的假失败/假通过）。
2. 执行后端仓库中“编译/打包/构建”类脚本（以仓库现有 CI 或项目约定命令为准）。
3. 若存在“可重复的干净构建/重建（如 clean/rebuild 语义）”，优先采用；否则至少确保本次执行不会依赖旧产物造成误判（如必要可删除旧产物目录后再构建）。
4. 若存在“仅编译/跳过耗时测试”的轻量命令，优先选择轻量版本以减少等待时间。
5. 记录命令、关键输出片段与退出状态，并在通过后检查关键编译产物是否生成/更新（以仓库约定的输出目录或产物文件为准）。

**检查点**：

- 若后端编译/构建失败：直接将当前后端相关任务标记为 \`Failed\`，并在执行日志中写明失败原因（以编译报错/日志为准），后续不进入归档/交付。
- 若在“依赖/构建工具就绪确认”阶段发现缺少依赖或工具不可用（例如依赖下载失败/找不到构建工具/关键环境变量缺失），判定为“当前环境安装问题”，并在执行日志中写明缺失点与错误摘要；后续不进入归档/交付。
- 若后端编译/构建“看似成功”但关键产物未生成/未更新：同样判定为失败（原因写为“产物生成异常/可能依赖旧产物”），后续不进入归档/交付。

---

### 步骤 2：前端构建闸门

**目标**：确保本次前端代码变更不会导致 lint/typecheck/build 失败（从而避免页面直接挂掉）。

**动作**：

1. 在执行前端 lint/typecheck/build 前，先确认前端依赖状态与项目配置一致（依赖安装/锁文件/环境差异导致的错误必须在日志中可追溯）。
2. 执行前端仓库约定的代码质量与类型检查（如有：lint / typecheck）。
3. 执行前端构建命令（build / bundling / package 等，以仓库现有脚本为准）。
4. 记录命令、关键输出片段与退出状态，并在通过后检查关键构建产物是否生成/非空（以仓库约定的输出目录为准，例如 build/dist 目录）。

**检查点**：

- 若前端 lint/typecheck/build 任一步失败：直接将当前前端相关任务标记为 \`Failed\`，并在执行日志中写明失败原因（以报错为准），后续不进入归档/交付。
- 若在“依赖/项目配置就绪确认”阶段发现缺少前端依赖或配置不完整（例如依赖未安装/锁文件与实际不一致/构建配置缺失），判定为“当前环境安装问题”，并在执行日志中写明缺失点与错误摘要；后续不进入归档/交付。
- 若构建通过但关键产物目录为空/缺失：判定为失败（原因写为“构建产物缺失/可能未实际构建”），后续不进入归档/交付。

---

### 步骤 3：产出轻量自检记录

**目标**：给出可追溯证据，便于后续修复与复盘。

**动作**：

1. 在执行日志/过程记录中追加一个小节，包含：
   - 后端：编译命令 + 结果（通过/失败）+ 失败摘要（如有）
   - 前端：lint/typecheck/build 命令 + 结果（通过/失败）+ 失败摘要（如有）
   - 失败分类（建议）：\`依赖/环境安装问题\`、\`编译/构建代码问题\`、\`产物生成异常/可能依赖旧产物\`（三选一或按实际细化）
2. 若通过：给出“轻量门槛通过”的确认文案，并标注本次检查覆盖了哪些变更任务（通常对应 \`task/task-split.md\` 内本次任务集合）。
