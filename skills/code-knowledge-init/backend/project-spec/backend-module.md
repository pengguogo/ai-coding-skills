本文档是项目初始化标准中涉及的项目设计相关的内容。

## 1 项目目的

说明项目的业务目标和价值，明确项目要解决的核心问题和预期达成的业务目标。

## 2 项目目录结构

项目目录结构按**分层约束**进行描述。产出时**根据实际代码扫描结果**，将扫描到的包/目录归入下列各层并输出目录树（或分层列表），不要求项目使用固定包名，以扫描结果为准。

### 2.1 分层约束

| 层级 | 说明 | 典型归属（供扫描归类参考） |
|------|------|----------------------------|
| **入口层** | HTTP 接口、RPC 接口、消息消费入口、定时任务入口等（完整入口类型见 [unified-scan-task-template.md §1 接口扫描](../../unified-scan-task-template.md#接口扫描)） | Controller、RPC 实现、Consumer、Schedule、Facade 等 |
| **业务逻辑编排层** | 业务流程编排、服务组合、执行链 | Service、Process、Executor 等 |
| **核心领域服务层** | 领域模型、领域服务、业务规则 | 按业务模块划分的领域类、聚合、模型等 |
| **外部依赖层** | 三方服务调用、MQ 组件、配置中心等 | Client、消息发送/消费封装、外部 SDK 封装等 |
| **数据层** | 持久化、缓存等 | SQL（Mapper、Entity、XML）、Redis、其他存储访问等 |

### 2.2 产出要求

- 根据代码扫描识别出的包路径与类职责，将**实际目录/包**归入上述五层（入口层、业务逻辑编排层、核心领域服务层、外部依赖层、数据层）。
- 输出形式可为：按层列出的目录树，或按层列出包路径与典型类/模块。若某层在项目中无对应代码，可注明「无」或省略该层。
- **代码目录结构树为必含项**，规范与示例见 **2.3**；与按层归类互补：树侧重「真实路径一览」，分层表侧重「职责归类」。
- 根目录的如 \`pom.xml\`、\`README.md\`、\`src/main/resources\`、\`backend-project.md\`、\`backend-interface.md\` 等可按实际扫描结果简要列在树顶端或独立一小节「工程根文件」。

### 2.3 代码目录结构树

在 \`backend-project.md\` 的「项目目录结构」中须单独给出**代码目录结构树**（标题可用「代码目录结构树」或与上下文合并为同一章节下的子块），满足：

| 项 | 要求 |
|----|------|
| **真实性** | 路径、包名、资源目录须来自**实际扫描**，与仓库一致；不存在的不写，不可用占位符臆造。 |
| **范围** | **主源码**：如\`src/main/java\`（或 Gradle 等价源码集）下的包目录；**资源**：如\`src/main/resources\`（含 \`mapper/\`、\`db/\`、\`application*.yml\` 等）；**多模块**：按 Maven/Gradle 模块分别建树，或在总览树中标注模块根（如 \`billing-api/\`、\`billing-service/\`）。 |
| **深度** | 至少展开到能区分**主要业务分包或子模块**（通常 **3～5 级**）；过深分支可合并为「…」并注实际根路径，避免无意义铺展。 |
| **注释** | 树节点旁可用 \`<!-- 或行尾注释 -->\` / 括注说明**用途**，或标注与 **2.1** 某层的对应（如「入口层」「数据层」）。 |
| **格式** | 推荐使用缩进或 \`├──\` / \`└──\` 的**纯文本树**置于 Markdown 代码块中；亦可使用嵌套列表，但须层次清晰、与真实目录一致。 |

**示例**（仅演示 \`├──\`/\`└──\` 树形格式，**禁止照抄路径**；产出须替换为当前仓库真实扫描结果）：

\`\`\`text
项目根/
├── pom.xml
├── README.md
├── module-billing/
│   └── src/main/
│       ├── java/com/example/billing/
│       │   ├── api/             # 入口层：HTTP
│       │   ├── service/       # 业务逻辑编排层
│       │   ├── domain/        # 核心领域服务层
│       │   ├── client/        # 外部依赖层
│       │   └── repository/    # 数据层：Mapper 接口等
│       └── resources/
│           ├── mapper/billing/
│           ├── db/init/
│           └── application.yml
└── backend-interface.md
\`\`\`

- 若仓库为**单模块**，可将 \`module-xxx/\` 内层直接接到仓库根下对应的 \`src/main/...\`。
- 与 **2.2** 中「按层列出的目录树」可同时保留：二者一为**物理树**，一为**逻辑分层**，避免重复粘贴时优先保证物理树与仓库完全一致。

### 2.4 入口层完整性自检

完成 2.1 分层归类与 2.3 代码目录结构树后，须对**入口层**执行以下三项自检，确保不遗漏非典型目录下的入口类。自检发现的新入口类须补充到 2.1 入口层中。

| 自检项 | 检查方法 | 说明 |
|--------|---------|------|
| **根包扫描** | 检查每个模块 \`src/main/java\`（或 Gradle 等价源码集）下**直接位于根包或一级包**（非 \`controller/\`、\`service/\`、\`task/\` 等已归类子包）的 \`.java\` 文件，逐一判断是否承担入口职责（启动类、调度器、初始化器、WebSocket 端点等） | 根包下的类容易被目录扫描遗漏，因为它们不在典型入口子包中。常见场景：启动类、定时调度器、集群初始化器等直接放在模块根包下 |
| **启动类追踪** | 读取 \`@SpringBootApplication\` 标注的启动类（或项目等价的启动入口），检查其 \`implements\`/\`extends\` 的接口或基类、\`@Import\`/\`@ImportResource\` 引入的配置、\`@Bean\` 方法返回的对象中，是否存在未归入入口层的入口类 | 能发现项目自定义启动框架的入口（如项目封装的应用生命周期接口及其实现类），以及通过 \`@Bean\` 注册的 \`CommandLineRunner\`、调度器等 |
| **配置文件追踪** | 检查 Spring XML 配置文件（\`applicationContext*.xml\`、\`*-context.xml\`）和 \`application*.yml\`/\`application*.properties\` 中声明的 bean 定义、组件扫描路径、定时任务配置、消息监听器配置等，是否存在未归入入口层的入口类 | 能发现通过 XML 声明的 Dubbo 服务、定时任务、消息监听器等非注解驱动的入口 |

**执行要求**：
- 三项自检均须执行，不可跳过。
- 若自检未发现新入口，无需额外产出；若发现新入口，须将其补充到 2.1 入口层对应位置，并在 2.3 目录结构树中标注。
- 自检结果不单独输出为文档章节，仅作为 2.1 入口层的补充校验手段。

## 3 模块划分

列出项目的功能模块，明确各模块的职责和边界。

### 3.0 模块依赖图

> 使用 Mermaid graph TB 展示模块间的依赖关系。仅 Maven/Gradle 多模块项目必须生成（数据来源为 pom.xml/build.gradle 的 \`<dependencies>\` 和 \`<modules>\`）；单模块项目（含 Ant 构建项目）为可选，若生成须标注"由包间 import 推断，需人工确认"。

**生成规则**：
- 节点为 Maven/Gradle 子模块名（如 \`business-car\`、\`common-util\`）
- 箭头方向为依赖方向（A → B 表示 A 依赖 B）
- 按层级分组（使用 subgraph），如公共层、业务层、启动层
- 单图节点不超过 30 个；超过时按层级拆分为多张图

**输出格式**：
\`\`\`markdown
#### 模块依赖图

\`\`\`mermaid
graph TB
    subgraph 公共层
        common-util
        common-db
    end

    subgraph 业务层
        business-car
        business-finance
    end

    subgraph 启动层
        app
    end

    business-car --> common-util
    business-car --> common-db
    business-finance --> common-util
    app --> business-car
    app --> business-finance
\`\`\`
\`\`\`

### 3.1 核心业务流程

描述项目的核心业务流程，包括流程步骤、输入输出、异常处理等。每条核心业务流程**必须附带一张 Mermaid 图**（根据流程特点选择 \`sequenceDiagram\` 时序图或 \`flowchart\` 流程图），缺少图表视为不合格产出。

- **时序图**：适用于模块/服务间有明确调用顺序的流程（如请求链路、审批流转）
- **流程图**：适用于包含条件分支、并行或循环的流程（如状态机、规则判断）
- 图中的 participant/节点须使用 3.2 业务模块中的模块名称或实际服务/类名，交互箭头/边标注具体业务动作，不使用泛化描述

**全量扫描要求**：核心业务流程必须基于全量代码扫描产出，覆盖所有入口层类，每条流程附带 Mermaid 图。完整校验规则见 SKILL.md 步骤 6 自检清单。

**输出格式**：
\`\`\`markdown
#### 业务流程1: [流程名称]

**流程说明**:
- **输入**: [输入数据描述]
- **处理**: [处理逻辑描述]
- **输出**: [输出结果描述]
- **异常处理**: [异常情况处理]

**流程图/时序图**：

\`\`\`mermaid
sequenceDiagram
    participant 用户
    participant Controller
    participant Service
    participant Repository
    用户->>Controller: 发起请求（如提交订单）
    Controller->>Service: 调用业务方法
    Service->>Repository: 持久化数据
    Repository-->>Service: 返回结果
    Service-->>Controller: 返回业务结果
    Controller-->>用户: 响应结果
\`\`\`

#### 业务流程2: [流程名称]

**流程说明**:
- **输入**: [输入数据描述]
- **处理**: [处理逻辑描述]
- **输出**: [输出结果描述]

**流程图/时序图**：

\`\`\`mermaid
flowchart LR
    A[接收请求] --> B{参数校验}
    B -->|通过| C[执行业务逻辑]
    B -->|失败| D[返回错误]
    C --> E{业务规则判断}
    E -->|满足| F[处理成功]
    E -->|不满足| G[处理异常]
    F --> H[返回结果]
    G --> H
\`\`\`
\`\`\`

### 3.2 业务模块

列出项目的业务模块，说明每个模块的功能、核心实体和主要接口。

**交叉引用数据源**：
- **主要接口**：优先从已生成的 \`backend-interface.md\`（或接口扫描中间产出 \`*-scan-result.md\`）中提取，按模块分组归入对应业务模块。不得脱离接口扫描结果凭印象列举。
- **核心实体**：优先从已生成的 \`backend-database.md\`（或数据模型扫描中间产出 \`*-scan-result.md\`）中提取实体类名，归入对应业务模块。不得臆造不存在的实体。
- 若 \`backend-interface.md\` 或 \`backend-database.md\` 尚未生成（生成顺序不同），则基于代码扫描直接提取，但须确保与后续生成的对应文档一致。

**输出格式**：
\`\`\`markdown
#### 用户管理模块
- **功能**: 用户注册、登录、权限管理、个人信息管理
- **核心实体**: User, Role, Permission
- **主要接口**: 
  - POST /api/users - 用户注册
  - POST /api/users/login - 用户登录
  - GET /api/users/{id} - 获取用户信息
  - PUT /api/users/{id} - 更新用户信息

#### 订单管理模块
- **功能**: 订单创建、支付、退款、订单查询
- **核心实体**: Order, OrderItem, Payment
- **主要接口**:
  - POST /api/orders - 创建订单
  - GET /api/orders/{id} - 查询订单
  - PUT /api/orders/{id}/pay - 支付订单
  - POST /api/orders/{id}/refund - 退款
\`\`\`
