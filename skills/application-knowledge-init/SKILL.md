# 应用架构知识生成器

## 标准母版结构（复用）

- 本文件遵循：文档职责边界 -> 角色定位 -> 何时使用 -> 前置输入 -> 执行流程 -> 输出与交付物 -> 规范引用 -> 执行红线。
- 本文件聚焦"流程与边界"，架构图表格式、组件划分规则、Mermaid 语法约束等实现细节统一收敛到 \`references/\`。
- 当规则变更时，优先修改 \`references/\`，避免在 \`SKILL.md\` 重复维护细节。

## 文档职责边界

- 本文件负责：执行路径选择、输入输出边界、交付物范围、更新策略与红线约束。
- 该系列文档用于描述系统的边界、拓扑、模块依赖与调用顺序。
- 细节规范（架构图表格式、组件划分规则、Mermaid 语法约束）统一放 \`references/\`，本文件不重复展开。
- 本技能**不负责**定义业务域（交由业务架构 \`business-knowledge-init\` 负责）。
- 本技能**不负责**直接扫描 Java/TS 源代码，而是高度依赖 \`code-knowledge-init\` (project-spec) 的输出基线。
- 如与项目既有规范冲突，以项目规范为准并显式说明差异。

### 流水线顺序与编号定义权

- 标准流水线顺序：\`code-knowledge-init\` → \`application-knowledge-init\` → \`business-knowledge-init\`。
- **S-* 编号定义权**：application 基于代码基线推导 S-*（业务场景）编号，产出即为正式编号。当 business 基线已存在时，必须直接引用其 S-* 编号，不得另起编号。**S-* 粒度要求**：S-* 应与代码基线中的包/模块粒度对齐，每个独立的业务动作都应有自己的 S-* 编号，不要过度合并。
- **DO-* 编号定义权**：DO-*（领域对象）的业务语义定义权归 \`business-knowledge-init\`。本技能在 \`application-components.md\` 的 DO-* 表中记录的是应用侧视角的数据对象，必须与 business 侧的 DO-* 编号保持一致；当 business 基线已存在时，必须增加"对应业务侧 DO-*"列进行显式追溯。
- **APP-*、AG-*、AC-* 编号定义权**：归本技能所有，business 侧只引用不定义。

## 角色定位

- 本技能是应用架构知识的沉淀与初始化入口，负责在 \`knowledge/application\` 下生成标准化的应用架构文档。
- 核心价值在于归纳存量系统拓扑、提取跨系统调用关系（尤其是大项目）、统一团队应用层面的架构认知。
- 本技能不负责定义业务域与业务场景（由 \`business-knowledge-init\` 负责）；不直接读取源代码（依赖代码扫描基线）；不生成接口文档或数据库设计（由 \`code-knowledge-init\` 负责）。

## 何时使用

- "帮我梳理一下整个系统的应用架构"
- "生成应用架构全景图"
- "更新系统的应用架构知识文档"
- "分析并输出这几个模块的调用关系和架构文档"
- "这是一个包含十几个子系统的庞大项目，帮我汇总出一份顶层应用架构"

## 前置输入

- 必选代码基线：批量或逐个读取 \`ocspec-<xxx>/knowledge/code/<子系统名>/\` 下的前后端项目说明文档（如 \`frontend-project.md\`, \`backend-project.md\`, \`backend-interface.md\`, \`backend-external-dependency.md\` 等）。若基线目录不存在，必须向用户说明并标记 \`[基线待补充]\`，不得凭印象推断子系统清单。
- 可选业务基线（优先对齐）：若 \`ocspec-<xxx>/knowledge/business/\` 已存在，必须读取其中的业务全景文档以对齐业务场景（S-*）编号，直接引用 business 定义的 S-*，不得另起编号。若 business 基线不存在，基于代码基线推导 S-* 即为正式编号。
- 外部服务处理原则：工作区内无代码基线的外部服务（如 service-iam、payment-service 等），在图表和表格中以服务名标注，并在真相源章节注明"外部服务，无本地基线"，不得臆造其内部结构。
- 规范文档：\`references/*.md\`

## 执行流程

### 步骤 1：确定分析范围与输入真相源
- 目标：明确本次架构生成的子系统清单与输入边界，确保所有推断有据可查。
- 动作：
  - 扫描 \`ocspec-<xxx>/knowledge/code/\` 下的实际目录，列出所有可用的代码基线子系统清单。
  - 若用户未明确指定范围，列出候选子系统清单并询问用户确认，不得凭印象列举。
  - 多子系统支持：用户可选择全部或部分子系统；若选择多个，按顺序逐个处理，不并行。
  - 检查 \`knowledge/business/\` 是否已存在，若存在则读取业务全景文档获取 S-* 编号体系。
  - 根据子系统数量，决定是生成单一扁平架构，还是生成"全局顶层架构 + 各子系统局部架构"的分层文档结构。
- 检查点：
  - 子系统清单必须来自实际目录扫描，不得凭印象列举。
  - 如必选代码基线缺失，必须在生成文档时标记 \`[基线待补充]\`。
  - 如业务基线已存在但 S-* 编号与其不一致，必须以业务基线为准修正，不得另起编号。

### 步骤 2：架构拓扑与调用链分析
- 目标：推导系统的层级结构、应用分组、应用间依赖及调用时序。
- 动作：
  - 应用与应用组划分：基于扫描基线的模块名和工程结构，推导出应用组（AG-*）和可部署应用（APP-*）。
  - 跨系统集成点识别：重点提取子系统之间的集成点（API、MQ、共享数据库等），明确谁是提供方，谁是消费方。
  - 应用组件识别：从应用内部包结构或功能特性中识别出应用组件（AC-*）。
  - 提取调用与依赖关系：推导应用之间的静态依赖与运行时调用关系。
  - 串联业务流程：结合业务场景（若有），推导主链路上的请求顺序如何在各个 APP 间接力。
  - 前后端串联分析：从前端代码基线（\`frontend-project.md\`）中提取 API 路径族（共享同一前缀的接口组），将路径族映射到后端应用与能力域，形成前后端集成表和前端应用总览。路径族与后端能力的映射必须有代码基线依据，不得虚构 endpoint。
- 检查点：
  - 确保图文一致，例如 Mermaid 图表中的节点 ID（如 APP-01）必须与表格中的应用 ID 完全一致。

### 步骤 3：按规范生成文档并落盘
- 目标：将推导出的架构知识严格按照标准模板输出到指定目录。
- 动作：
  - 若已存在产出，根据用户需求判断更新策略（见"输出与交付物"中的更新策略说明）。
  - 当涉及大量应用或模块（如 APP >= 8，或多子系统聚合）时，必须首先按照 \`application-architecture-task-template.md\` 生成 \`task.md\` 进行分批处理，生成后直接按任务顺序执行。
  - 按照标准格式生成三份核心文档。
  - 在整个应用架构知识完全生成并经用户最终确认后，必须删除临时的 \`task.md\` 文件。
- 检查点：
  - 检查产出路径是否正确。
  - 检查格式是否严格遵循 \`references/\` 下对应的专项规范（\`application-system-architecture-spec.md\`、\`applications-and-domains-spec.md\`、\`application-components-spec.md\`）。

### 步骤 4：生成后自检
- 目标：生成后对照标准自查，确保产出质量，发现问题就地修正。
- 动作：
  - 检查产出路径与文件名是否符合约定（\`ocspec-<xxx>/knowledge/application/\`）。
  - 检查产出语言是否为简体中文。：APP-*、AG-*、AC-* 在图、表、文本中是否完全一致。
  - 检查防信息过载：单张 Mermaid 图节点是否控制在合理规模（建议不超过 20-30 个节点）。
  - 检查集成点明确：跨子系统的 API、MQ、共享库依赖是否在表格或图中清晰体现。
  - 检查基线追溯完整性：所有应用和子系统是否附带了真实的基线路径，无本地基线的外部服务是否已注明。
  - 检查表格列完整性：所有表格是否严格遵循规范中定义的表头，无漏列。
  - 检查不确定项是否明确标注 \`[需人工确认]\`。
  - 检查前后端集成表（§4.3）：路径族是否来自前端代码基线，后端能力语义是否有据可查，无虚构路径。
  - 检查前端应用总览（§5）：是否覆盖所有前端 APP，路径族摘要与 §4.3 明细是否一致。
  - 若 \`knowledge/business/\` 已存在，检查 S-* 编号是否与业务基线一致。
- 检查点：
  - 文档结构与 \`references/\` 下对应的专项规范一致。
  - 没有遗漏必须产出的文档类型。
  - 自检发现问题必须就地修正，不得遗留已知错误后交付。

## 输出与交付物

- 产出目录：\`ocspec-<xxx>/knowledge/application/\`
- 产出文件：
  - \`application-system-architecture.md\`：侧重系统拓扑、分层图（Mermaid）、端到端调用关系与调用链说明。
  - \`applications-and-domains.md\`：侧重应用（APP）与应用组（AG）的主数据台账。
  - \`application-components.md\`：侧重应用组件（AC）、应用服务（AS）、扩展点（EP）、数据对象（DO）、组件间依赖及全局构建块映射。
  - \`task.md\`：（可选，仅在大篇幅或多子系统分批生成时必需）
- 产出格式要求：
  - 使用 Markdown
  - 仅使用简体中文
  - 结构与字段严格遵循 \`references/\` 下对应的专项规范（\`application-system-architecture-spec.md\`、\`applications-and-domains-spec.md\`、\`application-components-spec.md\`）
- 更新策略：
  - 首次生成：补齐三份核心文档。
  - 新增子系统：仅更新 \`applications-and-domains.md\`（新增 APP/AG 行）和 \`application-system-architecture.md\`（补充调用关系与 Mermaid 图）。
  - 调用关系变化：仅更新 \`application-system-architecture.md\` 的调用表与 Mermaid 图。
  - 组件内部变化：仅更新 \`application-components.md\` 对应 AC 行。
  - 全量重建：用户明确要求，或子系统数量/结构发生重大变化时执行。

## 执行红线

1. 不臆造输入中不存在的 AG、APP、AC 及调用关系；无法确定的关系和数据必须明确标记为 \`[需人工确认]\`；但可从代码基线推断的内容不得以 \`[需人工确认]\` 占位，必须基于基线实际内容生成。
2. 不绕过项目既有约束；严格遵循 \`references/\` 下对应专项规范的 Markdown 结构，不随意合并或拆分既定章节。
3. 不凭印象列举子系统——子系统清单必须来自 \`knowledge/code/\` 的实际目录扫描。
4. 外部服务不越界：工作区内无代码基线的外部服务只标注名称与调用方式，不推断其内部结构或组件。
5. 图文一致：各类组件编号（APP-*、AG-*、AC-*）在图、表和文本中必须绝对一致。
6. 防过载：Mermaid 图表节点或边过多时必须合理分拆，避免渲染失败。
7. Task.md 生命周期管理：所有任务执行完毕且经用户最终确认后，必须删除 \`task.md\`。
8. S-* 编号与业务侧对齐：若业务架构基线已存在，S-* 编号必须与其对齐，不得另起编号体系。
9. DO-* 编号与业务侧一致：\`application-components.md\` 中的 DO-* 编号必须与 \`knowledge/business/\` 下领域建模文档（若存在）中的 DO-* 保持一致。
10. APP 编号连续递增：APP-* 编号必须从 APP-01 开始连续递增，不得跳号。编号顺序为先后端再前端，按 AG 分组顺序排列。
11. AG 前端细分：前端应用必须按终端形态拆分为独立的 AG（如 PC 端前端、移动端前端、公共服务），不得将所有前端合并为一个 AG。
12. 时序图全覆盖：端到端调用链时序图必须覆盖所有核心业务链路和请求入口类型，不得遗漏。时序图必须从前端入口开始绘制，完整展示用户请求从前端发起到后端处理的全链路。当存在新旧架构并行时，关键链路需分别绘制。
13. 前后端集成可追溯：§4.3 前后端集成表中的 API 路径族必须来自前端代码基线（\`frontend-project.md\`），后端能力语义必须有后端基线或架构上下文支撑，不得虚构路径或能力映射。
