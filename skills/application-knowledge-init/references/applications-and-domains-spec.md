## 3 内容标准与填表指南

- **应用组/子系统 (AG)**：在大型项目中，应用组通常映射为一个完整的子系统或大业务域。它是高阶的逻辑分组。**前端应用必须按终端形态拆分为独立的 AG**（如 PC 端前端、移动端前端、公共服务），不得将所有前端合并为一个 AG。
- **应用 (APP)**：必须是**具体的可独立部署单元**（Deployment Unit），包括前后端项目、独立网关、数据脚本、定时任务进程等。如果一个 Maven multi-module 项目最终打成一个 Jar 包运行，它就是一个 APP；如果打成多个服务，就是多个 APP。
- **质量属性考量**：填写该应用在非功能性需求上的侧重，例如：高可用、强一致、大吞吐、低延迟等。
- **前端应用与后端能力总览（§5）**：从前端项目维度汇总，每个前端应用一行。"前端形态"填 SPA/App/H5/小程序等；"典型 API 路径族"从前端代码基线（\`frontend-project.md\`）中归纳主要 API 前缀，仅列摘要（3-5 个典型前缀），全量明细见系统架构册 §4.3；"主要后端能力"概括该前端消费的后端能力域（如"门面/BFF + 交易核心域 + 支付依赖"）。当系统只有单个前端时，此表仍需生成以保持结构完整。

## 4 生成约束

- \`应用 ID\` (如 APP-01) 必须全局唯一，并与系统架构册中的节点保持一致。对于多子系统，可采用前缀策略（如 \`ORD-APP-01\`）。
- **APP 编号必须从 APP-01 开始连续递增，不得跳号**。编号顺序为：先后端应用（按 AG 分组顺序），再前端应用（按 AG 分组顺序）。例如后端 APP-01~11，前端 APP-12~19，不得出现 APP-14 直接跳到 APP-17 的情况。
- \`代码模块(路径)\` 必须真实存在于扫描基线中。
- \`归属领域/业务能力\` 必须填写，无法推断则填 \`[需人工确认]\`。
