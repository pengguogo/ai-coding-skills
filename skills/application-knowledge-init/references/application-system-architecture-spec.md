## 3 内容标准与填表指南

- **宏观与微观分离**：对于包含 8+ 子系统的项目，架构图必须体现宏观（子系统级别）交互，将详细的内部交互下放到组件册或单独的局部视图中。
- **调用关系与串联**：重点梳理**跨子系统**的集成点。**注意区分"调用(RPC/HTTP)"和"依赖(如共用数据库/缓存)"**。如果是 MQ 异步通知，必须写明 Topic 或 Event 语义。
- **前后端集成（§4.3）**：路径族从前端代码基线（\`frontend-project.md\`）中提取 API 前缀归纳而来，后端能力语义从后端代码基线或应用架构上下文推导。路径族粒度以共享同一业务含义的前缀为准（如 \`/api/order/**\`），不要逐个接口罗列。无法确认后端能力语义时标记 \`[需人工确认]\`。

## 4 生成约束

- Mermaid 图表必须符合标准语义（分层、调用、时序），避免生成包含超过 30 个节点的单张超大图表导致渲染失败。
- **端到端调用链时序图必须覆盖所有核心业务链路**，不得遗漏。判断标准：每个独立的请求入口类型和每个核心业务场景都应有对应的时序图。当系统存在新旧两套架构时，关键链路需分别绘制新架构和传统架构的时序图。**时序图必须从前端入口开始**，完整展示用户请求从前端发起到后端处理的全链路，不得省略前端入口跳。
- **顶层架构图中的 subgraph 必须标注 AG 编号**（如 \`subgraph AG-01 [应用组名称]\`），确保图中的分组与主数据册的 AG 台账一致。
- 所有表格列必须与规范完全一致，不得随意删减列。如果某列无数据，填「-」或「不适用」。
- \`真相源与参考路径\` 必须真实引用所有参与聚合的子系统基线。严禁编造不存在的 markdown 文件。
