# 前后端技术方案设计（fullstack-design）

## 何时使用

- 用户需要**一次完成**本需求的**后端 + 前端**技术方案设计，或明确按「先后端、后前端」在同一技能内产出两份设计文档时。
- 用户请求或涉及：**后端设计文档**、**技术方案**、**接口设计**、**时序图**、**领域模型**、**流程图**、**模块/架构设计**；以及**前端架构**、**模块划分**、**状态管理**、**组件接口**、**前端技术方案**、**PRD/用户故事驱动的前端设计**等——均使用本技能。
- **产出边界**：**结构化 Markdown** + 标准要求的 **Mermaid 等图表**。**不产出可运行代码**；必要时仅用**带说明的伪代码或片段**表达意图。

## 强制顺序

1. **阶段 A**：完成后端技术方案设计并落盘 **\`design/backend-design.md\`**。  
2. **阶段 B**：在阶段 A 已落盘的前提下，完成前端技术方案设计并落盘 **\`design/frontend-design.md\`**。  
3. **禁止**在缺少已落盘的 **\`backend-design.md\`** 时开始或定稿 **\`frontend-design.md\`**（前端凡涉及后端 HTTP/API 的契约须以 \`backend-design.md\` 为准）。

## 规范来源

| 文档 | 用途 |
|------|------|
| \`references/design-backend-standard.md\` | **后端正文唯一标准**：§1～§6 章节结构、**§1.5 路径类约定**、新项目/存量写法、文档编写规范 |
| \`references/sequence-diagrams.md\` | 时序图（含改动点颜色标注等） |
| \`references/flowcharts.md\` | 流程图 |
| \`references/erd-diagrams.md\` | ER 图 |
| \`references/design_frontend_standard.md\` | **前端正文标准**：章节结构、格式与内容要求 |
| \`references/design_template.md\` | 前端设计文档排版模板（可选用） |

**技术栈无关**：后端设计避免绑定单一框架实现细节；前端设计需对齐项目实际技术栈（优先从 \`ocspec-<xxx>/knowledge/code/<项目名>/frontend-project.md\` 获取）。

## 执行原则

- **需求成稿对照（强制）**：本技能产出的前后端设计，须**严格以同需求目录下已落地的需求成稿为范围与验收基准**；默认路径为 **\`ocspec-<xxx>/requirements/<需求英文名>_<yyyymmdd>/requirement/requirement.md\`**（若团队另有约定文件名或拆分多文件，以任务约定为准，但须**唯一指定**哪一份为「主需求」）。**禁止**在需求中无依据地扩展功能或擅自改口径；若需新增/变更范围，须在正文或开放问题中注明 **\`[超出当前需求成稿]\`** 并说明待产品确认，**不得**默写进实现路径当作已确认需求。  
- 设计须**可追溯到需求**（功能/非功能/REQ 编号或章节与需求成稿对应）；材料不足处标注 **\`[需与产品确认]\`** 或写入开放问题章节。  
- **存量项目**：与**现状**对齐，突出**增量与变更**（见后端标准 §2、§1.5）。  
- **新项目**：可完整描述目标架构与选型理由。  
- 阶段 B 中凡涉及**后端接口**的表述，须与同需求 **\`backend-design.md\`** 一致，**禁止**臆造冲突的接口定义。

## 阶段 A：后端技术方案设计

### 步骤 A1：输入理解与上下文对齐

**目标**：明确「做什么、不做什么、依赖谁、约束是什么」。

**动作**：

1. **读取并对照需求成稿**：打开并通读同需求 **\`requirement/\`** 下主需求文档（通常为 **\`requirement.md\`**），建立**功能清单 / REQ 编号 / 验收要点**与设计的**逐项映射**；后续阶段 A 各节须能回溯到该文档，未覆盖需求项或超出范围须在开放问题或标注中说明。  
2. **收集输入**：需求规格、用户故事、会议纪要、接口草案、现网问题单等；理清**功能范围**与**非功能期望**（性能、安全、可用性等）。  
3. **读取项目上下文**：技术栈、模块划分、接口/网关习惯、配置与部署约束（文档路径见任务或 Spec 引用）。  
4. **判定场景**：**新项目** vs **存量增量**——决定 §2、§1.5、接口路径等章节的写法侧重（见标准 §2 章首通则）。  
5. **外部依赖清单**：列出需对接的系统、已有文档链接或 \`[需与产品确认]\`。  
6. **输出本步备注**：待确认问题列表，供 §6 或评审使用。  

### 步骤 A2：撰写 §1 背景与目标

**目标**：把「为什么做、做到什么程度、受什么限制、引用哪些依据」写清。

**动作**（小节定义与示例见 **design-backend-standard.md**）：

1. **1.1 背景**：业务场景、痛点、价值。  
2. **1.2 目标**：功能 / 性能 / 质量 / 业务目标，尽量**可度量**。  
3. **1.3 约束**：技术约束、业务与合规约束。  
4. **1.4 参考文档**：需求编号/路径、既有架构或接口说明；**存量**须引用**真实可追溯**的文档或仓库位置。  
5. **1.5 路径与配置类约定**：凡涉及 URL、配置文件路径、配置中心、存储路径、Topic/缓存 key 等，按标准中的**表格**区分**新项目/存量**，禁止把臆造示例当作现网路径。  

### 步骤 A3：撰写 §2 技术方案

**目标**：让读者理解**怎么拆系统、用什么技术、模块如何分工**。

**动作**：

1. **2.1 架构设计**：模式与思想、选型理由；**存量**写清**现状 + 本期变更边界**；**新项目**写**目标架构**与权衡。  
2. **2.2 技术选型**：数据存储、缓存、MQ、定时、HTTP 客户端、注册/配置中心等；**存量**以**实际使用**为准；**新项目**给出选型与理由。  
3. **2.3 模块设计**：模块职责与依赖；**存量**突出**本期涉及模块**及与既有模块关系；**新项目**可给全量或首期模块划分，可用 Mermaid 表示依赖（参见标准与 **flowcharts.md**）。  

### 步骤 A4：撰写 §3.1 模型设计

**目标**：统一**领域语言**与**落库形态**，避免实现阶段各说各话。

**动作**（模板见标准）：

1. **3.1.1 领域模型**：实体、值对象、聚合根、领域服务；属性、行为、边界写全。  
2. **3.1.2 数据模型**：表、字段、主键与索引、关系；附 **Mermaid ER**（见 **erd-diagrams.md**）。  
3. **3.1.3 状态机**（若适用）：状态、转换规则、校验与日志；附 **stateDiagram**（见标准示例）。  

### 步骤 A5：撰写 §3.2 功能设计（按模块/功能迭代）

**目标**：每个关键功能具备**可实现的调用链**与**对外契约要点**。

**动作**（每个「具体功能」一节按标准 **3.2** 子结构展开）：

1. **功能时序图**：自入口到持久化/外部系统的**成功与失败**分支；改动点用标准约定方式标注（见 **sequence-diagrams.md** 与标准内示例）。  
2. **对外接口**：方法 + URL + 入参/出参/说明；路径遵守 **§1.5**；**存量**与现网路由规则一致。  
3. **依赖接口**：外部系统、URL、参数、场景、异常处理。  
4. **幂等**：系统侧与业务侧，无则写「无」。  
5. **异常处理**：重试 / 阻断 / 丢弃等分类说明。  
6. **配置**：代码内配置文件路径（**存量**写真实路径类型）与动态配置项。  
7. **数据库 / 缓存 / 文件 / 定时 / 消息**（按需）：与本功能相关的表、key、路径、任务、Topic 等，不涉及写「无」。  

对多个功能模块**重复本节结构**，直至覆盖需求范围内的核心链路。

### 步骤 A6：撰写 §4 稳定性与安全评估

**目标**：说明**如何扛流量、如何失败可控、如何观测与核对**。

**动作**（见标准第 4 章）：

1. **系统稳定性**：限流维度与阈值；降级与熔断触发条件与恢复策略。  
2. **业务稳定性**：日志与监控指标、告警规则；事务与读写分离（若适用）；**核对告警**（若适用）。  
3. 与 §3.2 中的异常、幂等、外部依赖**相互印证**，避免矛盾。  

### 步骤 A7：撰写 §5 风险与 §6 开放问题

**目标**：暴露**技术与业务风险**及**未决项**，便于评审拍板。

**动作**：

1. **§5 风险评估**：技术风险（一致性、性能、依赖、安全、扩展等）与业务风险；每条有**应对措施**。  
2. **§6 开放问题**（如有）：待定方案、影响范围、待决策人；避免大量隐含假设留在正文。  

### 步骤 A8：自检与定稿（后端）

**目标**：满足标准中的**文档编写规范**与**内容要求**；**确保接口定义的字段明细足以支撑阶段 B 前端逐字段对齐**。

**动作**：

1. 对照 **design-backend-standard.md** 末尾 **「文档编写规范」**：章节完整性、接口与数据模型覆盖范围、图表类型（Mermaid）是否正确。  
2. 对照 **「内容要求」**：关键功能是否具备时序图与接口说明、核心服务是否考虑降级熔断（若标准有要求）。  
3. 核对 **§1.5**：凡路径类描述是否已区分新项目/存量并与引用一致。  
4. **对照需求成稿**：核心功能/接口/数据与边界是否与 **\`requirement/requirement.md\`**（或团队指定的主需求）一致；无遗漏或未经标注的「加需求」。  
5. **接口字段完整性检查（为阶段 B 服务）**：每个对外接口的**入参**和**出参**须以**表格**形式列出所有字段（字段名、类型、必填/可选、说明），不得仅给 JSON 示例而省略字段表；**错误码与典型文案**须集中列出。此为阶段 B 前端逐字段对齐的前置条件。  
6. 全文 **UTF-8**，语言与项目约定一致。  
7. 保存为 **\`design/backend-design.md\`**：\`ocspec-<xxx>/requirements/<需求英文名>_<yyyymmdd>/design/backend-design.md\`。

**阶段 A 产出**：UTF-8 Markdown；**不删减**标准中的必需章节类型；图表遵循 **design-backend-standard.md** 与 **references/*-diagrams.md**。

## 阶段 B：前端技术方案设计

本阶段在 **阶段 A 已落盘 \`backend-design.md\` 之后**执行。设计文档是连接需求与实现的关键桥梁：指导实现、降低返工、统一团队认知，并与 \`frontend-project.md\` 等规范衔接。**核心原则**：基于需求生成设计决策，而非直接生成代码；遵循项目实际技术栈。

### 步骤 B1：需求与上下文分析

**目标**：解析需求文档，分析项目上下文，确定技术选型；**并与已产出的 \`backend-design.md\` 对齐**。

**动作**：

1. **需求文档解析**（**须与**同需求 **\`requirement/requirement.md\`**（或团队约定的主需求成稿）**一致**）  
   - 功能点提取：识别所有功能模块和功能点，提取输入、输出和业务逻辑，识别功能点之间的依赖关系；**不得**引入需求成稿中未定义的功能，除非已标注 **\`[超出当前需求成稿]\`** / **\`[需与产品确认]\`**  
   - 非功能约束提取：性能、兼容性、可访问性、安全、可维护性  
   - 交互流程识别：用户操作流程、页面跳转关系、数据流转路径  
   - 数据模型识别：实体和属性、实体间关系、数据操作（增删改查）

2. **项目上下文分析**  
   - 检查现有项目规范：如存在 \`ocspec-<xxx>/knowledge/code/<项目名>/frontend-project.md\`，读取技术栈、目录结构、接口调用规范、开发约束；如不存在，询问用户或基于需求推断  
   - 技术栈兼容性分析、架构一致性检查

3. **UI 风格与组件一致性分析**（无详细设计稿或仅有简单视觉图片时尤为关键）  
   - **优先从 \`frontend-project.md\` 的「UI 风格与组件参考」章节获取**：UI 组件库、主题配置、常用 UI 组件约定、常用页面模式、参照页面索引  
   - 若 \`frontend-project.md\` 无此章节或信息不足，则扫描现有项目：  
     a. 识别 UI 组件库（从 \`package.json\` 依赖中提取）  
     b. 扫描主题/样式变量文件，提取主色、圆角、间距等设计 Token  
     c. 扫描现有 views 目录中与本次需求同类型的页面（如列表页、表单页），分析其组件组合方式  
   - **确定本次设计的 UI 参照基准**：选定 2-3 个现有页面作为 UI 风格参照，后续功能点设计中的组件选型、布局方式、交互模式须与参照页面保持一致  
   - 若无设计稿且无法从现有项目推断 UI 风格，标注 \`[需提供设计稿或 UI 参照]\` 并列入开放问题

3. **技术选型确定**  
   - 优先严格遵循项目现有技术栈（从 \`frontend-project.md\` 获取）  
   - 无现有技术栈时根据项目实际情况选择（主框架、状态管理、路由、UI 库、样式、构建工具等），并说明理由  
   - 引入新技术须说明必要性与影响

4. **后端设计对齐（涉及调用后端接口或后端能力时强制）**  
   - **必须**读取同需求下已产出的 **\`backend-design.md\`**（由阶段 A 落盘）。  
   - 凡涉及**调用后端 HTTP/API** 或依赖后端领域能力的，**URL、HTTP 方法、路径参数、请求/响应字段、错误码、幂等等**须**从 \`backend-design.md\` 查询、摘录并与之一致**后，再写入前端设计；**禁止**在未对照 \`backend-design.md\` 的情况下单独臆造接口定义。  
   - 若 \`backend-design.md\` 尚未覆盖某接口，在前端设计中标注 **\`[需后端设计补充]\`**，并列入开放问题或待协调项。
   - **逐接口构建「前后端接口对齐表」**（本步骤为强制动作）：  
     a. 遍历 \`backend-design.md\` §3.2 中所有**对外接口**（含新增与修改），逐个提取：**HTTP 方法、完整 URL、入参字段表（字段名 / 类型 / 必填 / 说明）、出参字段表（字段名 / 类型 / 说明）、错误码与典型文案**。  
     b. 对每个接口，在前端设计「数据与接口」章节中**完整展开**上述信息，并在每个接口条目旁标注 **\`来源：backend-design.md §x.x.x.x 接口N\`**，确保可追溯。  
     c. 前端 TypeScript \`interface\` 定义的**每个字段**须与后端出参/入参表**逐一对应**；字段名、类型、是否可选须一致；若前端需做字段映射或类型转换（如后端 \`string\` 前端需 \`number\`），须在字段注释中注明**映射规则与原因**。  
     d. 若后端接口存在**条件必填**字段（如「多员工时必传」），前端类型定义须体现（如 \`targetUserId?: number\` + 注释说明条件）。  
     e. 后端设计中的**错误码与典型文案**须在前端设计的「错误处理」小节中**逐一列出**对应的前端处理策略（提示文案、跳转、重试等）。  
     f. 若后端接口**仅修改现有接口**（如在出参中新增字段），前端设计须明确标注**新增/变更字段**及其对前端渲染逻辑的影响。

**检查点**：提取的功能点是否完整；技术栈冲突须说明方案；**每个后端接口在前端设计中均有完整的字段级对齐表，无遗漏、无臆造**。**若 \`backend-design.md\` 不存在或未完成阶段 A，不得开始阶段 B。**

### 步骤 B2：方案设计

**目标**：设计架构方案、组件接口和技术策略。

**动作**：

1. **架构设计**：模块划分与职责边界、模块依赖（可用 Mermaid）、架构层次（UI/状态/服务/类型）、目录结构（对齐 \`frontend-project.md\` 或框架约定）  
2. **组件设计**：新建/复用/扩展组件识别；Props/Events/Slots 定义；职责与边界  
3. **UI 组件选型与参照**（无详细设计稿时为强制动作）：  
   - 基于步骤 B1 确定的 UI 参照基准，为每个功能点选定使用的 UI 库组件（如表格用 \`ElTable\`、表单用 \`ElForm\` 等），须与现有项目同类型页面使用的组件保持一致  
   - 布局方式（栅格/弹性/固定宽度等）须与参照页面一致  
   - 交互模式（加载态、空态、错误态的展示方式）须与参照页面一致  
   - 在设计文档中每个功能点的组件结构中标注使用的 UI 库组件及参照页面路径  
4. **技术策略定义**：数据获取（**接口须与 \`backend-design.md\` 一致**）、状态管理、表单、错误处理、性能、交互体验（加载/空态/边界）  
4. **接口契约复核**：在方案设计完成后、生成文档前，**逐一复核**前端设计中引用的每个后端接口，确认：  
   - 入参字段名、类型、必填性与 \`backend-design.md\` 完全一致  
   - 出参字段名、类型与 \`backend-design.md\` 完全一致  
   - 错误码处理覆盖 \`backend-design.md\` 中列出的所有业务错误码  
   - 若发现不一致或缺失，**立即修正**或标注 \`[需后端设计补充]\`

**检查点**：架构与目录是否合理；关键组件接口是否完备；策略可落地且符合项目约束；**所有接口字段级对齐无遗漏**。

### 步骤 B3：生成设计文档

**目标**：按 \`references/design_frontend_standard.md\` 生成完整设计文档。

**动作**：包含**概述**、**架构说明**、**规范文档对齐**、**功能逻辑实现**（功能概述、数据与接口、代码复用分析、实现方案）；自我审查完整性、一致性、可执行性、合理性。

### 阶段 B：生成约束

1. **只输出设计，不输出代码**（可伪代码片段并标注）  
2. **基于需求成稿**（同需求 **\`requirement/requirement.md\`** 等），不臆造功能；不确定处 \`[需与产品确认]\`；与后端设计相同，**须与主需求文档对齐**  
3. **遵循项目规范**（\`frontend-project.md\` 等）  
4. **结构化组织**（标题、表格、列表、图表）  
5. **设计决策说明**（选型理由、权衡、组件边界）  
6. **与后端设计一致（涉及接口时）**：以 **\`backend-design.md\`** 为权威来源，前端接口表须可追溯到该文档  
7. **接口字段级对齐（强制）**：前端设计中每个涉及后端的接口，须以**表格形式**完整列出入参和出参的**每个字段**（字段名、类型、必填/可选、说明），并标注 \`来源：backend-design.md §x.x\`；**禁止**仅写「简要说明参数和返回结构」而省略字段明细  
8. **新增/变更字段显式标注**：凡后端接口为**修改现有接口**（如在出参中新增字段），前端设计须在字段表中以 **\`[新增]\`** 或 **\`[变更]\`** 标记，并说明对前端渲染/逻辑的影响  
9. **错误码全覆盖**：\`backend-design.md\` 中列出的所有错误码与典型文案，须在前端设计的错误处理章节中**逐一对应**，写明前端处理策略（提示/跳转/重试/忽略）

### 阶段 B：输出格式

- 保存到 **\`design/frontend-design.md\`**：\`ocspec-<xxx>/requirements/<需求英文名>_<yyyymmdd>/design/frontend-design.md\`  
- UTF-8、Markdown；遵循 **design_frontend_standard.md**；可用 **design_template.md** 排版；Mermaid 展示架构与交互

### 阶段 B：使用模式与补充说明

- **新功能 / 增量 / 技术重构 / 大型项目 / 快速原型**等模式与原前端设计技能相同，按需求规模裁剪深度；增量场景须严格读取 **\`frontend-project.md\`**。  
- **需求格式**：支持多种输入格式；信息不足时标注确认项。  
- **项目上下文**：优先 **\`frontend-project.md\`**；使用框架通用概念，不绑定特定 API。  
- **设计粒度**：足够指导开发，避免过度设计；大功能可分步细化。  
- **代码边界**：本技能仅产出设计文档；实现请用编码类技能。  
- **最佳实践**：明确组件类型与说明、Mermaid 清晰含异常路径、选型写理由、风险与缓解措施；成稿后做完整性/一致性/可执行性/合理性自检，并**再次对照** **\`requirement.md\`** 确认页面/流程/交互无偏离需求范围。

### 阶段 B：接口对齐自检清单（定稿前强制执行）

前端设计文档定稿前，须逐项通过以下检查，**任一项不通过须修正后再定稿**：

| 序号 | 检查项 | 通过标准 |
|------|--------|----------|
| 1 | **接口覆盖完整性** | \`backend-design.md\` §3.2 中所有对外接口（新增 + 修改），在前端设计中均有对应的「接口依赖」条目 |
| 2 | **入参字段逐一对齐** | 每个接口的入参字段表（字段名、类型、必填/可选、说明）与 \`backend-design.md\` 完全一致；条件必填字段有注释说明 |
| 3 | **出参字段逐一对齐** | 每个接口的出参字段表与 \`backend-design.md\` 完全一致；嵌套对象须展开到叶子字段 |
| 4 | **来源标注** | 每个接口条目标注了 \`来源：backend-design.md §x.x.x.x\` |
| 5 | **TS interface 与后端一致** | 前端 TypeScript \`interface\` 的字段名、类型、可选性与后端出参/入参表逐一对应；有映射的须注释说明 |
| 6 | **错误码全覆盖** | \`backend-design.md\` 中列出的所有错误码在前端设计的错误处理中均有对应处理策略 |
| 7 | **新增/变更字段标注** | 修改现有接口时，新增或变更的字段以 \`[新增]\` / \`[变更]\` 标记 |
| 8 | **无臆造接口** | 前端设计中不存在 \`backend-design.md\` 未定义的接口路径或字段；未覆盖的标注 \`[需后端设计补充]\` |
