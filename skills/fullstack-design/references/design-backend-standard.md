# 后端设计文档标准

定位: 通用后端设计规范指引，适用于任意新项目或新需求的设计与实现阶段。
衔接关系: 上承「通用需求规范」中的功能/非功能需求，下接实现时遵循「通用编码规范」；设计文档产出用例图、时序图、领域模型等，作为开发与验收的桥梁。

### 1.4 参考文档
- 对应的需求规格文档（或需求文档编号/路径）
- 既有架构说明、技术选型、接口规范等（若有）

**新项目与存量项目**  
- **存量项目**：路径、编号、网关文档等**以任务书、Wiki、接口平台或仓库内既有说明的引用为准**，与现网一致；勿写死与仓库不符的示例路径。  
- **新项目**：可约定统一编号规则与文档存放位置，并在本节列出**权威引用**（如 Spec 路径、API 文档入口）。  

### 1.5 路径与配置类约定（新项目与存量项目）

凡设计中出现**路径**（URL、文件路径、配置项挂载路径、存储路径、Topic/缓存 key 前缀等），须区分场景：

| 类别 | 存量项目 | 新项目 |
|------|----------|--------|
| **对外/对内 HTTP 接口路径** | 与现有网关前缀、服务 context-path、版本规范（如 \`/api/v1\`）及**已有 Controller 映射**一致；新增接口写在既有规则下 | 按团队 API 规范约定完整路径与版本策略，并在文档中写明 |
| **依赖外部系统接口 URL** | 与对接文档、联调环境**实际 base path** 一致；勿臆造域名与路径 | 以外部官方文档或合同附件为准；若未定，列入 §6 开放问题 |
| **代码侧配置文件路径**（如 \`src/main/resources/...\`） | 与仓库**实际**目录及文件类型（\`.yml\` / \`.properties\` / \`bootstrap.*\` 等）一致；新增项写入**既有**配置文件或团队指定文件，勿引入与存量习惯冲突的新路径 | 可采用团队统一模板路径，并在设计中写明文件名与环境拆分方式 |
| **配置中心 / 动态配置路径**（DataId、namespace、group 等） | 与现网 Nacos/Apollo 等**命名空间与 dataId 规则**一致 | 按平台规范新建，并说明各环境对应关系 |
| **文件与对象存储路径**（NAS 挂载、OSS bucket/key 前缀） | 与现网目录、权限及**既有业务目录约定**一致 | 说明 bucket/前缀、环境划分及生命周期策略 |
| **消息 Topic / 消费者组、缓存 key 前缀** | 与现有命名规范及**线上已有** Topic/key 风格一致，避免冲突 | 按团队命名规范新定义，并说明与环境、模块的对应关系 |

设计文档中的路径**示例**（如 \`POST /api/...\`）在存量场景下应替换为**真实或可引用**的片段，或显式标注「示例，实际以 \`xxx\` 文档为准」。

## 2. 技术方案

**新项目与存量项目（本章通则）**  
- **存量项目**：以仓库**既有**架构、模块边界、技术栈与部署形态为准；本章侧重**增量与变更**——写清与现状的**衔接**、**改动范围**、**兼容/迁移**及影响面，避免描述与代码、运维实际不一致的「理想架构」。技术栈以扫描/对照项目上下文文档与代码为准（与 §2.2 一致）。  
- **新项目**：可完整给出**目标**架构模式、分层或领域思想、技术栈与模块划分，并说明**选型理由**及与需求规模、非功能目标的匹配。

## 3. 详细设计

### 3.1 模型设计

#### 3.1.1 领域模型
必须包含核心业务领域的模型设计，包括：

**实体（Entity）**
- 实体名称、职责说明
- 实体属性：属性名、类型、说明、是否必填
- 实体行为：实体包含的业务方法
- 唯一标识：实体的唯一标识设计

**值对象（Value Object）**
- 值对象名称、职责说明
- 值对象属性：属性名、类型、说明
- 值对象行为：值对象包含的方法

**聚合根（Aggregate Root）**
- 聚合根名称、职责说明
- 聚合边界：聚合包含哪些实体和值对象
- 聚合根方法：对外暴露的业务方法

**领域服务（Domain Service）**
- 领域服务名称、职责说明
- 领域服务方法：方法签名、参数、返回值、业务逻辑说明

#### 3.1.2 数据模型
必须包含所有新增或修改的数据库表结构设计，包括：

- **表名**：使用下划线命名（snake_case），如 \`platform_user\`、\`business_order\`
- **字段定义**：包含字段名、数据类型、是否必填、默认值、字段说明、索引信息
- **主键设计**：明确主键类型（自增ID、UUID、业务主键等）
- **索引设计**：明确唯一索引、普通索引、复合索引的设计
- **外键关系**：说明表之间的关联关系（如需要）

**SQL 脚本产物（必须输出）**：
- **建表脚本**：为新建表输出 \`CREATE TABLE\` 及其索引/约束/授权语句
- **修改脚本**：为新增或修改表输出变更脚本（即便当前无变更，也需要给出占位脚本，确保脚本存在且后续可迭代）
- **脚本目录与命名约定**：
  - **新项目**：数据库脚本统一放在 \`src/main/resources/db/init/\`
  - **文件名建议**：\`V{版本号}__create_{表名}.sql\` 与 \`V{版本号}__alter_{表名}.sql\`
  - **授权语句**：每个建表脚本中包含 \`GRANT\`（格式参考编码标准）

**表关系图**：
- 使用 Mermaid ER 图格式
- 明确标注一对一（1:1）、一对多（1:N）、多对多（M:N）关系
- 说明关系的外键字段、关联方式（主键关联、外键关联等）

#### 3.1.3 状态机
对于有明确状态流转的业务对象，必须设计状态机，包括：

- **状态定义**：明确定义所有可能的状态，使用枚举类型管理
- **状态转换规则**：定义清晰的状态转换规则，明确哪些状态可以转换到哪些状态
- **状态转换校验**：状态转换前必须校验当前状态是否允许转换到目标状态
- **状态转换不可逆性**：某些状态转换应该是不可逆的
- **状态转换日志**：所有状态转换必须记录操作日志

**示例格式**：
\`\`\`markdown

- 使用 Markdown 格式编写

- 接口变更、数据模型变更、领域模型变更时，必须同步更新设计文档
- 设计文档的更新必须经过评审
