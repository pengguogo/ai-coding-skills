# 修复方案模板（fix-plan）

Step 3 按本模板产出 `{BASE_DIR}/bug/<id>-<slug>-fix-plan.md`（持久留底，改前确认门禁的方案依据）。本文件是**改前给用户拍板**的方案，回答「改哪里、为什么这么改、有什么风险、怎么验证、会不会越界」。

## 该写 / 不该写

**该写**：修复思路、每条决策的基线依据、允许改动文件清单（影响面冻结）、关联风险与影响、验证计划、越界检查。
**不该写**（避免与其他 step 重复）：
- 根因定位的调用链追溯全文 → 属 Step 2 `02-locate-and-impact.md`，本文件只**引用根因结论（文件:行号）**
- bug 现象/复现/分级 → 属 Step 1，不复述
- 完整代码片段/diff → 属 Step 4，本文件只列「要改哪些文件」不贴代码

```markdown

- 基线出处取值（四选一）：`design:<文件>#<章节>` / `req:REQ-<编号>` / `knowledge:<文件>#<规则>` / `[无设计基线-代码现状推断]`（仅无设计基线档允许）

|---|---|---|

## 验证计划
- 静态因果自证：必做（Step 7 核对）
- 单测复现（仅纯逻辑根因且有测试框架）：<测试类#用例 + 执行命令；改前断言失败→改后转绿>
- 无测试框架：`[无测试基建]`（降级为仅静态自证）
```

---

## 字段要点

| 章节 | 要点 |
|---|---|
| 头部元信息 | 关联需求/级别/类型/根因结论 + 无基线时的置顶风险横幅 |
| 修复方案表 | 每条决策双向可追溯：向下到根因(文件:行号)、向上到基线出处；防 AI 主观发挥 |
| 允许改动文件清单 | 影响面冻结基线，Step 4 逐仓 `git diff` 比对的依据；含纯逻辑 bug 单测文件 |
| 关联风险与影响 | 改前门禁让用户看清波及面（间接影响/数据/兼容/回归/同源缺陷） |
| 受影响模块与编译命令 | 结构化供 build-verifier 注入，避免全量构建 |
| 验证计划 | 与 §3.8 单一验证策略对齐，按根因纯逻辑性互斥触发 |
| 越界检查 | 命中即 BLOCKED 升级，是 bug-fix 的能力边界闸门 |
