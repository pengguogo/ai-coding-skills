## 发现记录结构

每条审查发现按以下字段记录：

| 字段 | 说明 | 必填 |
|------|------|------|
| 检查项编号 | 如 BE-NAME-01、FE-TS-01、CC-SEC-01 | ✅ |
| 文件路径 | 含行号，如 \`src/main/java/.../UserService.java:42\` | ✅ |
| 严重性 | blocking / important / suggestion / nit / learning / praise | ✅ |
| 描述 | 用协作式提问风格描述问题 | ✅ |
| 建议 | 具体修复方案或可选方案 | blocking/important 必填 |
| 规范来源 | 如 \`coding-standard.md §6.5\` | blocking/important 必填 |

## 反馈风格示例

本技能采用协作式反馈，以下为正反示例：

**提问而非命令**：
- ❌ "这个方法太长了，必须拆分。"
- ✅ "这个方法有 120 行，是否考虑按职责拆分为几个私有方法？这样单测也更容易覆盖。"

**解释原因**：
- ❌ "不要用 any。"
- ✅ "这里使用了 \`any\` 类型，是否可以用 \`unknown\` 或具体类型替代？这样 TypeScript 编译器能帮助捕获潜在的类型错误。"

**肯定优点**：
- ✅ "👍 这里的错误处理很完善，覆盖了网络异常和业务异常两种场景，降级方案也很合理。"

**区分主观与客观**：
- ✅ "[规范要求] SQL 必须使用参数化查询（coding-standard.md §11）。"
- ✅ "[个人偏好] 这里用 Stream API 可能比 for 循环更简洁，但不影响功能。"
