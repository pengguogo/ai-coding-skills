# 事实源与合理性校验规范

**文档版本**: 1.0
**适用范围**: `requirement-analysis`、`product-requirement-analysis` 两个需求分析技能。
**定位**: 本文件是「需求正文每一句话从哪来」的唯一权威规则来源。需求项模板结构见 `requirement-analysis-standard.md`；本文件只管**溯源与可信度**。

---

## 一、为什么需要事实源门禁

需求文档的最大风险不是写得不够细，而是**写得很细但没有依据**——AI 把「合理的推测」写成「确定的需求」，下游 `fullstack-design` 与 `task-split` 会把它当硬约束实现，返工成本极高。

因此本规范要求：**凡进入需求正文的关键事实，必须可回溯到一个明确的来源锚点；无法回溯的一律降级为待确认，不得伪装成事实。**

---

## 二、事实源分级（F1~F5）

| 级别 | 来源 | 可直接作为需求正文依据 | 说明 |
|------|------|----------------------|------|
| **F1** | 用户提供的原始材料原文（含图片识别出的内容锚点） | ✅ 可 | 最高可信。docx/pdf/pptx/txt 正文、表格、图片锚点 |
| **F2** | 用户在对话中明确确认的内容 | ✅ 可 | 含产品版 brainstorm 中被用户**回答或认领**的结论 |
| **F3** | 知识库既有事实（`business/`、`application/`、`code/`、`custom/`） | ✅ 可，但锚点须可定位 | 引用须精确到文件 + 章节/表格行/接口签名 |
| **F4** | 历史需求文档（`{OCSPEC_ROOT}/requirements/<历史>/`） | ⚠️ 仅作参照 | 须显式声明与本次的关系，禁止大段复制 |
| **F5** | AI 推断（材料未写、用户未确认、知识库无据） | ❌ **不可** | 必须降级为待澄清项，或由用户显式认领后升为 F2 |

**F5 降级规则（强制）**：任何 F5 内容进入正文前，必须二选一——
1. 转为待澄清问题，正文对应处标 `[推断待确认]`；
2. 经用户在对话中明确认领 → 升级为 F2，并在事实源表登记「用户确认」。

**禁止**：把 F5 内容直接以陈述句写入正文而不加任何标记。

## 三、事实源登记表

### 3.1 表结构

事实源表落在 `{WORKSPACE}/requirement/01-fact-source.md`，交付时归档到 `{BASE_DIR}/sources/fact-source.md`。

| 字段 | 说明 | 必填 |
|------|------|------|
| `事实源 ID` | `FS-001` 起顺序编号，全文唯一 | 是 |
| `事实内容` | 一句话摘要（不超过 40 字） | 是 |
| `级别` | F1 / F2 / F3 / F4 / F5 | 是 |
| `来源文件` | 文件名或知识库相对路径 | 是 |
| `定位锚点` | 见 §3.2 锚点精度要求 | 是 |
| `原文摘录` | 来源中的原始表述（F1/F3 必填，≤ 60 字） | 条件 |
| `关联需求项` | REQ-00X（可多个，逗号分隔）；归不到写 `—` | 是 |
| `校验状态` | 待校验 / 可信 / 存疑 / 缺失 | 是 |

### 3.2 锚点精度要求（按来源类型）

| 来源类型 | 锚点写法 | 示例 |
|----------|---------|------|
| Word / PDF / 文本材料 | 章节号或小标题 + 段落/表格定位 | `《XX需求.docx》§3.2 表格第 4 行` |
| PPT 材料 | 页码 + 元素 | `《XX方案.pptx》P12 右侧流程图` |
| 图片 | 归档文件名（与 `sources/media/` 一致） | `REQ-001_01_登录页.png` |
| 知识库 business / application | 相对路径 + 章节锚点 | `business/order-domain.md#订单状态机` |
| 知识库 code | 相对路径 + 接口签名或类名 | `code/xx-svc/backend-project.md#POST /api/order/pay` |
| 历史需求 | 目录 + 章节 | `requirements/order-pay_20260401/requirement/requirement.md#三、支付` |
| 对话确认 | 轮次或问题标识 | `对话确认（第 3 轮：审批层级）` |

**锚点不合格的典型写法（禁止）**：只写 `business/`、只写文件名不给章节、写「知识库中提到」「材料里有」这类无法定位的表述。

## 四、强制挂溯源的条目

以下类型的内容，在建模产出与终稿中**必须**能对应到事实源表中的条目：

| 类型 | 强制级别 | 说明 |
|------|---------|------|
| **数字型事实** | **仅 F1 / F2** | 金额、时限、阈值、条数、并发量、超时、重试次数、保留天数、层级数等。**禁止推断**，无据则标 `[推断待确认]` |
| 关键业务规则 | F1 / F2 / F3 | 校验规则、准入条件、计算口径、权限规则、状态流转条件 |
| 字段清单 | F1 / F2 / F3 | 三维度中「数据展示维度」的字段与标签 |
| 接口 / 消息名 | F1 / F2 / F3 | 复用既有接口时须锚点到 code 知识库；臆造接口名视为违规 |
| 状态流转 | F1 / F2 / F3 | 状态取值与迁移条件 |
| 外部系统名 | F1 / F2 / F3 | 系统名称须与知识库或材料一致 |
| 角色 / 参与者 | F1 / F2 / F3 | 用例图参与者与节点描述责任对象 |

**正文标记粒度（避免污染可读性）**：

- **数字型事实**与**关键业务规则**：正文就地挂轻量标记 `[FS-00X]`
- 其余类型：不在正文挂标记，仅在 `sources/fact-source.md` 索引表中登记关联需求项

## 五、双信号合理性校验（通用规则）

对每条事实源记录两类信号并比对。图片是本规则的一个特例（见 `requirement-analysis-standard.md` §2.4）。

| 事实源类型 | 信号 A（位置信号） | 信号 B（内容信号） |
|-----------|-------------------|-------------------|
| **图片** | 来源文件 + 文档位置 + 初判需求项 | 内容锚点（标题/字段/按钮/节点/状态词） |
| **文本规则** | 材料中的出现位置 | 语义自洽性：与其他规则、术语定义、状态机是否矛盾 |
| **知识库对照项** | 引用路径 + 锚点是否真实存在 | 该锚点内容是否真的描述此能力 |
| **历史需求** | 目录/需求名匹配度 | 正文中可指认的相似点 |
| **数字型事实** | 材料中数字出现位置 | 单位、量纲、上下文口径是否一致 |

### 5.1 判定矩阵

| 比对结果 | 判定 | 处理 |
|----------|------|------|
| 信号 A 与信号 B **一致** | 可信 | 正常引用，无额外标记 |
| 信号 A 与信号 B **矛盾** | 存疑 | 标 `[事实源存疑]`，纳入待确认项 |
| 锚点**查不到**（路径/章节/接口不存在） | 缺失 | 标 `[事实源缺失]`，纳入待确认项 |
| 仅有 F5 推断、无任何来源 | 推断 | 标 `[推断待确认]`，纳入待确认项 |

### 5.2 标记语义（不得混用）

| 标记 | 含义 |
|------|------|
| `[事实源存疑]` | 有来源，但信号 A/B 矛盾，可信度不足 |
| `[事实源缺失]` | 声明了来源，但按锚点查不到对应内容（含臆造的知识库引用） |
| `[推断待确认]` | 纯 AI 推断，材料与知识库均无据 |
| `[图片待人工确认]` | 图片内容无法识别或无法提取（见 standard §2.4） |
| `[图片归属待人工确认]` | 图片可识别但归属存疑（见 standard §2.4） |
| `[知识库待补充]` | 知识库应有但确实缺失该主题（产品版；非臆造，区别于 `[事实源缺失]`） |

以上标记全部纳入终稿**待确认项清零检查**；残留则本次状态须为 `DONE_WITH_CONCERNS`。

## 六、无源断言检测（反向校验）

正向校验查「事实源表里的条目是否真实」，反向校验查「正文里是否有表外的内容」。两个方向都必须做。

反向扫描建模产出与终稿，逐项比对是否存在事实源表中**没有登记**的：

1. 功能点 / 需求项
2. 接口路径、方法名、消息主题
3. 字段名与字段标签
4. 角色 / 参与者
5. 外部系统名
6. 数字（金额、时限、阈值、条数等）

发现表外内容 → 判为**无源断言**，按 §5.1 归入「推断」处理：要么补登记来源，要么标 `[推断待确认]`。

---

## 七、校验强度

| 条目类型 | 核验比例 |
|----------|---------|
| 数字型事实 | **100%** 逐条打开来源核对 |
| 关键业务规则 | **100%** |
| 接口 / 消息名 | **100%**（须 grep 验证知识库中确实存在） |
| 其余条目（字段、角色、外部系统等） | **≥ 30%** 抽样，且每个需求项至少 1 条 |

**核验方式硬要求**：必须重新打开来源文件按锚点定位核对，**不得凭记忆或凭上下文印象判断**。知识库引用须用检索工具验证存在性。

---

## 八、门禁结论

校验产出末尾给出结论，三档取值：

| 结论 | 判定条件 | 后续动作 |
|------|---------|---------|
| `PASS` | 无 `[事实源缺失]`；无无源的数字型事实；存疑项 ≤ 2 且均已标记 | 进入成稿组装 |
| `CONDITIONAL` | 存在存疑或推断项，但均已正确标记且不涉及数字型事实 | 进入成稿组装，存疑项带入交付报告待确认项 |
| `FAIL` | 出现下列任一：数字型事实无 F1/F2 来源；知识库引用臆造（`[事实源缺失]`）；无源断言未标记 | **回退建模步骤修正后重跑校验**，不得进入成稿 |

## 九、产品版专属规则（product-requirement-analysis）

本章仅适用于 `product-requirement-analysis`。`requirement-analysis` 不涉及知识库与 brainstorm，可忽略本章。

### 9.1 Brainstorm 推断认领门（Step 0 Phase F 强制）

Step 0 Phase D 明确要求「推断背景/用户/价值，不停轮确认」，产出 `inferred_context`。这些内容属 **F5**，如果直接被 Step 1 当作「首要依据」消费，推断会在步骤交接中无痕升格为需求事实——这是产品版最主要的幻觉入口。

因此 `PRESENT_DRAFT` 中每一条结论**必须**标注来源属性：

| 标注 | 含义 | 对应级别 |
|------|------|---------|
| `[用户确认]` | 用户在对话中明确回答或提供 | F2 |
| `[材料原文]` | 来自 `RAW_MATERIALS` | F1 |
| `[知识库]` | 来自 `business/`/`application/`/`code/`，须带锚点 | F3 |
| `[AI推断]` | Phase D 推断得出，用户尚未确认 | F5 |

**`FINAL_APPROVAL` 门禁条件**：草案中所有 `[AI推断]` 条目必须二选一处理完毕，才允许写入 `BRAINSTORM_STATUS: approved`——

1. **用户显式认领** → 改标 `[用户确认]`，级别升为 F2；
2. **用户未认领** → 移入 brainstorm 的「待澄清」小节，**不得**进入功能清单（§4）与验收口径（§5）。

**禁止**：`00-brainstorm.md` 中同时存在 `BRAINSTORM_STATUS: approved` 与未处理的 `[AI推断]` 条目。校验时发现此情形，门禁结论直接判 `FAIL`。

### 9.2 知识库引用真伪验证（F3 强制）

`01-intake.md` §8「与现有能力对照」的「来源文档（路径）」列，精度必须满足 §3.2 的锚点要求（文件 + 章节/接口签名），**只写目录名或只写文件名不合格**。

每条 F3 引用须逐条验证两件事：

| 验证项 | 方式 | 失败处理 |
|--------|------|---------|
| **锚点存在性** | 打开该路径，确认章节/接口/类名确实存在 | 标 `[事实源缺失]`，门禁判 `FAIL` |
| **内容相符性** | 确认该锚点内容确实描述了对照表所说的能力 | 标 `[事实源存疑]` |

**接口名专项（最高风险）**：需求项 §3.2.3 数据交互维度中凡声明「复用已有接口」，接口路径与方法必须能在 `{CODE_KNOWLEDGE}` 中检索到。**检索不到即为臆造**，判 `FAIL`，不接受「接口应该叫这个名字」的推定。

### 9.3 `[知识库待补充]` 与 `[事实源缺失]` 的区分

两者都涉及知识库，但语义相反，**不得混用**：

| 标记 | 语义 | 责任方 |
|------|------|--------|
| `[知识库待补充]` | 知识库**确实没有**这个主题，需求本身合理 | 知识库维护方后续补齐 |
| `[事实源缺失]` | 引用**声称**知识库有，但按锚点查不到——即引用是臆造的 | 本次需求分析必须修正 |

判断口径：先按锚点查证。查不到但整个主题在知识库中本就不存在 → `[知识库待补充]`；查不到却在正文中已按「已有能力」表述 → `[事实源缺失]`。

### 9.4 历史需求对照（F4）

`01-intake.md` §9 中标注「迭代/扩展」关系的项，须满足：

- 锚点精确到历史需求的具体章节（见 §3.2）
- 终稿 §3.1 需求概述中以**摘要级文字**说明与历史需求的关系
- **禁止**大段复制历史正文（复制超过连续 3 句判违规）
- **禁止**写入或修改历史需求目录下任何文件

校验须实际打开历史文档核对相似点，不接受仅凭目录名推定的「相似度」判断。
