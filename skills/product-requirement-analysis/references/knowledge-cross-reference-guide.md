# 知识库对照指引（Step 1 Phase A）

产品需求分析须在接收材料后，**主动读取**已拉取知识库的三层主知识，并与本次功能列表对照。

## 读取顺序

1. `{KNOWLEDGE}/_workspace/product-req/00-kb-readiness.md` — 了解各层是否可读
2. `{KNOWLEDGE}/business/` — 业务全景、流程用例、领域模型（**术语与流程优先以本层为准**）
3. `{KNOWLEDGE}/application/` — 系统拓扑、应用域、组件清单（**系统边界与归属**）
4. `{KNOWLEDGE}/code/` — 代码级模块、接口、库表（**实现落点与复用**）
5. `{CUSTOM_KNOWLEDGE}/` — 若 `CUSTOM_KNOWLEDGE_STATUS=present`，读制度/术语/对接规范

`KNOWLEDGE_READINESS=minimal` 时：仅读 readiness 与 custom（若有），§8 知识库对照写「知识库内容不足，本次以原始材料为准」，**不 Halt**。

## `{CODE_KNOWLEDGE}` 解析

- 扫描 `{KNOWLEDGE}/code/` 子目录
- **仅 1 个项目子目录** → 作为 `{CODE_KNOWLEDGE}` 深入读取
- **多个子目录** → 按功能列表中的「所属模块/系统名」匹配最相关 1～2 个；无法匹配则各读 `backend-project.md` / `frontend-project.md` 摘要（若存在）

## 对照产出（写入 01-intake.md §8）

须包含：

### 8.1 与现有能力对照（表格）

| 本次功能/需求项 | 知识库已有能力 | 来源文档（路径 + 锚点） | 关系 | 说明 |
|----------------|---------------|------------------------|------|------|
| ... | ... | `business/order-domain.md#订单状态机` | 复用/扩展/新增/疑似重复 | ... |

**关系**取值：
- **复用**：已有能力可直接满足
- **扩展**：在已有模块/流程上增量
- **新增**：知识库无对应条目
- **疑似重复**：与已有需求/能力高度重叠，须产品确认

#### 锚点精度要求（强制，Step 2 维度 3 会逐条验证）

「来源文档」列须精确到**可定位**，取值格式见 `fact-source-standard.md` §3.2：

| 层 | 合格写法 | 不合格写法 |
|----|---------|-----------|
| business / application | `business/order-domain.md#订单状态机` | `business/`、`order-domain.md`、「业务知识库中提到」 |
| code | `code/xx-svc/backend-project.md#POST /api/order/pay` | `code/`、「代码库里有这个接口」 |

**引用即验证（强制）**：写入本表前须**实际打开该锚点**确认内容存在且与所述能力相符。

| 情形 | 处理 |
|------|------|
| 锚点存在且内容相符 | 正常写入，标 F3 |
| 主题在知识库中确实不存在 | 关系写「新增」；如本应有则标 `[知识库待补充]` |
| 声称已有但锚点查不到 | **不得写入本表**；Step 2 会判 `[事实源缺失]` 并使门禁 `FAIL` |

**接口专项（最高风险）**：需求项 §3.2.3 数据交互维度凡声明「复用已有接口」，接口路径与方法必须能在 `{CODE_KNOWLEDGE}` 中**检索到**。检索不到即为臆造——写为占位并标 `[推断待确认]`，**不得**编造看起来合理的路径，也不得以「接口应该叫这个名字」推定。

### 8.2 术语与边界对齐

- 与 `business/` / `custom/` 不一致的术语列出对照表
- 超出 `application/` 系统边界的项标注 `[超出当前系统边界]`

### 8.3 范围与冲突预警

- **范围膨胀**：材料要求超出 application 文档中的系统范围
- **接口重复**：与 `code/` 接口清单中已有 API 重叠
- **流程冲突**：与 business 流程用例矛盾

无法确认时标注 `[需与产品确认]`，不臆造知识库内容。

## 历史需求对照（§9）

扫描 `{OCSPEC_ROOT}/requirements/` 下各需求目录：

1. 读取各目录名与（若存在）`requirement/requirement.md` 的文档信息/需求内容清单标题
2. 按功能列表关键词、`RELATED_REQUIREMENT`（若 Pin 中有）、以及 Pin 中的 `REQUIREMENT_SLUG`（若非「未提供」）匹配相似项
3. 产出表格：

| 历史需求目录 | 相似度 | 关联说明 | 本次关系 | 章节锚点 |
|-------------|--------|---------|---------|---------|
| `<slug>_<date>/` | 高/中/低 | ... | 迭代/并行/无关联 | `requirement/requirement.md#三、支付` |

**本次关系**取值：迭代（v2 相对 v1 的替换或演进）、并行（独立共存）、无关联。

**相似度判定依据（强制）**：须**实际打开**历史 `requirement.md` 核对后填写，「章节锚点」列指向可指认的相似章节。**不接受**仅凭目录名或 slug 相近推定的相似度——Step 2 维度 5 会打开历史文档核验。

若用户指定 `RELATED_REQUIREMENT`，须优先**只读**展开该目录并在 §9 首行标注「用户指定关联」。

### 历史需求只读边界（强制）

| 允许 | 禁止 |
|------|------|
| 只读引用历史 `requirement.md` 的章节、术语、需求项名称 | 复制粘贴历史正文到 `01-intake.md` / `01-modeling.md` / 终稿 |
| 摘要性对比：本次相对历史的增/删/改/不变 | 写入、覆盖、删除历史目录下任何文件 |
| 在 §9 与 3.1 概述中说明迭代或并行关系 | 将 `{BASE_DIR}` 设为历史需求目录 |
| 将历史未覆盖而本次材料新增的内容正常建模 | 默认「在历史需求基础上直接续写」；**除非**用户 prompt **明确指定** |

**成稿范围**：本次 `requirement.md` 须基于**用户本次提供的 RAW_MATERIALS** 独立撰写；历史需求仅作参照，不是成稿模板。
