# Checkpoint: Step 3 成稿最终校验

> **审查级别**：L2（完整审查）— 检查全部维度，含跨步骤一致性和跨需求项引用一致性。
> **审查原则**：你是审查者，不是作者。必须重新打开产出文件逐项核对，不能凭记忆判断。
> **强制停止点**：这是交付点。汇总全部待确认项，停下来等待用户确认。

## 审查时需打开的文件
- 产出文件：`{REQ}/requirement.md`
- 上游比对：`{WORKSPACE}/requirement/01-intake.md`、`{WORKSPACE}/requirement/00-brainstorm.md`（追溯范围，非终稿章节）
- 门禁报告：`{WORKSPACE}/requirement/02-verify-report.md`
- 事实源归档：`{BASE_DIR}/sources/fact-source.md`

## 下游等价性（product-requirement-analysis 强制）
- [ ] 终稿章节结构与 `requirement-analysis` 产出一致（§1 → §2 → 各需求项 §3.1/§3.2.1～§3.2.7）
- [ ] 终稿**不含**独立「头脑风暴」「知识库对照」「历史需求对照」「事实源登记表」「校验报告」等产品中间产物章节
- [ ] 终稿**不含** `00-brainstorm.md` 大段粘贴
- [ ] 终稿**保留** `[FS-00X]` 溯源引用与 §1.1「事实源索引」行（这两项不属于中间产物）
- [ ] 涉及前端交互的需求项含三维度逻辑（页面操作/数据展示/数据交互）
- [ ] `fullstack-design` 可直接以本文件为 `{REQ}/requirement.md` 输入，无需额外转换

## 路径合规（Init / 落盘）
- [ ] 产出位于 `{OCSPEC_ROOT}/requirements/<需求>_<日期>/requirement/requirement.md`
- [ ] 工作区根不存在误建的 `_workspace/` 或并行 `ocspec-*`（与 Init 摘要一致）
- [ ] 中间产出仅在 `{BASE_DIR}/_workspace/` 下
- [ ] `sources/` 位于 `{BASE_DIR}` 下（非工作区根；无 GBK 乱码目录）

## 事实源门禁与归档检查
- [ ] `02-verify-report.md` 存在，`GATE_RESULT` 为 `PASS` 或 `CONDITIONAL`（为 `FAIL` 则本步骤本不应执行）
- [ ] 门禁报告全部 6 个维度均已实际执行（无「未启用」）
- [ ] 门禁报告 §7「待标记项汇总」中**每一条**都已在终稿对应位置落标记（逐条核对，遗漏视为绕过门禁）
- [ ] 落标记时未擅自改写正文内容
- [ ] `{BASE_DIR}/sources/fact-source.md` 已归档，`关联需求项` 列已回填最终 REQ 编号
- [ ] `校验状态` 列已按 Step 2 结论更新（可信/存疑/缺失），无残留「待校验」
- [ ] 归档文件开头写明了下游用途（区分硬约束与待确认项）
- [ ] 终稿 §1.1 基础信息含「事实源索引」行指向 `../sources/fact-source.md`
- [ ] 终稿正文中每个 `[FS-00X]` 在 `sources/fact-source.md` 中确实存在该 ID
- [ ] 终稿正文无裸数字（每个数字均挂 `[FS-00X]` 或待确认标记）
- [ ] 声明「复用已有接口」的接口均经 Step 2 检索验证，无臆造
- [ ] `00-brainstorm.md` 中未认领的 `[AI推断]` 条目未进入终稿正文
- [ ] `[知识库待补充]` 主题已汇总到状态报告，供 Step 4 参考

## 章节完整性
- [ ] 包含 §1 文档信息（§1.1 基础信息 + §1.2 修订历史）
- [ ] 包含 §2 总体概述（§2.1 需求内容清单 + §2.2 基本术语定义 + §2.3 非功能性清单参考）
- [ ] 每个需求项有独立的一级大标题章节
- [ ] 每个需求项包含完整的 §3.1 + §3.2（§3.2.1 ~ §3.2.7）

## 术语一致性
- [ ] 需求项名称在 §2.1 清单和各大标题中完全一致
- [ ] 术语在 §2.2 定义和正文中使用一致
- [ ] 角色名称在用例图和节点描述中一致
- [ ] 外部系统名称在全文中一致

## 需求覆盖
- [ ] 01-intake.md 功能列表中的每个需求项在正文中有对应的大标题章节
- [ ] 5W1H 中识别的每个角色在相关用例图中有体现
- [ ] 5W1H 中的关键业务规则在对应需求项的触发逻辑中有体现

- [ ] 不同需求项中引用同一外部系统时，系统名称一致

## 待确认项清零检查（终稿强制）
- [ ] 终稿全文不包含 `[需与产品确认]` 标记
- [ ] 终稿全文不包含 `[需人工确认]` 标记
- [ ] 终稿全文不包含 `[知识库待补充]` 标记
- [ ] 终稿全文不包含 `[事实源存疑]` 标记（残留则状态须 DONE_WITH_CONCERNS）
- [ ] 终稿全文不包含 `[事实源缺失]` 标记（残留则状态须 DONE_WITH_CONCERNS）
- [ ] 终稿全文不包含 `[推断待确认]` 标记（残留则状态须 DONE_WITH_CONCERNS）
- [ ] 终稿全文不包含 `<!-- STATUS_REPORT -->` 块

> `[FS-00X]` 为正常溯源引用，**不纳入**本清零检查。

## 待确认项提取
- 待确认项清零检查中任何未通过的项
- 全文中所有 `[需与产品确认]`、`[需人工确认]`、`[知识库待补充]` 标记（含位置）
- 全文中所有 `[事实源存疑]`、`[事实源缺失]`、`[推断待确认]` 标记（含位置与对应 FS-ID）
- 门禁报告中判定为存疑/缺失的事实源条目
- 门禁报告中检索不到的接口名
- 需求覆盖检查中未覆盖的需求项
- 评审自检中未通过的项
- 状态报告中的 corrections-made、manual-review-needed 和 unresolved-items
