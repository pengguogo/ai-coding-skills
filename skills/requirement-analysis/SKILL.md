# 需求分析

## 何时使用

用户需要 **分析需求**、**整理/标准化需求文档**、**需求评审/澄清**，或提供原始材料（Word、PDF、文本、会议纪要、聊天摘录等）要求输出结构化需求时启用。

## 规范来源

| 参考文件 | 用途 |
|----------|------|
| \`references/requirement-analysis-standard.md\` | **成稿结构**：文档信息、总体概述、各需求项下的需求概述与业务流程（用例图、前置条件、触发事件及重要逻辑、节点描述、后续动作、非功能性清单）；含 Mermaid、表格与示例 |
| \`references/5w1h-analysis-guide.md\` | **5W1H**：Why/What/Who/When/Where/How 的问题、要点与示例，用于挖全场景 |
| \`references/review-checklist.md\` | **评审与自检**：准备、完整性、Given-When-Then、5W1H、隐藏场景、非功能等检查项 |

产出为 **UTF-8 Markdown**。**章节标题、表格列、四段流程关系**以 **requirement-analysis-standard.md** 为准；**每个 W/H 怎么问**以 **5w1h-analysis-guide.md** 为准；**交付前检查**以 **review-checklist.md** 为准。

## 执行原则

- 以用户提供的材料为据，**不臆造**材料中未出现的功能；缺失信息用 **\`[需与产品确认]\`**（或等价表述）并列出待澄清问题。  
- 术语、优先级、需求项 ID 在全文保持一致。  
- 节点描述中的**责任对象**（前端 / 服务端 / 网关·中间件 / 外部系统）须与 **requirement-analysis-standard.md** 约定一致，便于前后端分工。

## 工作流程

### 步骤 1：接收材料与范围确认

**目标**：读懂「要做什么」与「不做什么」，标出缺口。

**动作**：

1. 收集原始材料全文（可多文件合并为一份逻辑需求）。  
2. 提取：**业务目标**、**干系人/用户角色**、**大致功能列表**、**已知约束**（时间、合规、对接系统等）。  
3. 标注：**范围外**或**明确不做**的内容（若材料未写排除项，在文档中列出「待确认是否排除」。  
4. 列出 **待澄清清单**（问题 + 建议找谁确认），无法确认处统一用 **\`[需与产品确认]\`** 在成稿中留痕。  

---

### 步骤 2：5W1H 穿透分析

**目标**：系统性补全需求信息，减少评审返工。

**动作**（具体问题与示例见 **\`5w1h-analysis-guide.md\`**，此处为执行顺序）：

1. **Why**：背景、痛点、价值、不做的影响、优先级理由。  
2. **What**：功能边界、包含/排除、输入输出、验收口径（可测表述）。  
3. **Who**：角色、权限差异、外部系统与运营/管理方。  
4. **When**：触发时机、截止时间、定时/批处理、时效与 SLA 期望。  
5. **Where**：终端/渠道、部署或集成环境、数据上下游。  
6. **How**：主流程、关键规则、异常与回退、与非功能相关的实现约束（性能、安全等线索）。  

将结论整理为**可写入文档的要点**（不必在分析稿中重复最终 Markdown 结构）。

---

### 步骤 3：需求项拆解与总体概述骨架

**目标**：得到 **2.1 需求内容清单** 的行集，并锁定后文大标题顺序。

**动作**：

1. 从步骤 2 归纳独立**需求项**，每项分配稳定 **名称/ID** 与 **所属模块**、**优先级（P0/P1/P2）**。  
2. 按 **requirement-analysis-standard.md** 中 **2.1** 表格列填写「需求内容清单」。  
3. 编写 **2.2 基本术语定义**（缩写、领域名词）。  
4. **2.3 非功能性清单参考**：可直接引用标准中的类别表作为「参考」，具体指标在各需求项的 **3.2.6** 中落地（无则写「无」或省略该小节）。  

**检查**：清单中的每一行，在后文必须有对应的一个**一级大标题**需求项章节。

---

### 步骤 4：逐需求项 — 业务流程建模

**目标**：每个需求项具备完整的 **3.1 需求概述 + 3.2 业务流程** 全套小节。

**动作**（小节定义与示例见 **requirement-analysis-standard.md**）：

对 **2.1 清单中的每一项** 依次完成：

1. **3.1 需求概述**：一句话说清业务/系统结果（目的）。  
2. **3.2.1 用例图**：Mermaid \`flowchart\`（或标准允许的形式），标出参与者与系统边界内的用例，与本需求项名称对应。  
3. **3.2.2 前置条件**：进入流程前必须满足的状态；无则写「无」或等价说明。  
4. **3.2.3 触发事件及重要逻辑**：谁在什么时机触发；主流程步骤编号 1、2、3…；分支、业务规则、异常要点；**步骤序号与下文节点编号可追溯对应**。当流程步骤 ≥ 5 步或存在多分支时，须在文字步骤下方附 Mermaid flowchart TD 业务流程图（见标准 3.2.3.1）。  
5. **3.2.4 节点描述**：用表格列齐 **节点编号、节点名称、责任对象、动作简述**；责任对象取值限定为：前端、服务端、网关/中间件、外部系统（与标准一致）。  
6. **3.2.5 后续动作**：正常结束后的状态、写库、消息、跳转等；**后置条件**写清。  
7. **3.2.6 非功能性清单（可选）**：按 **2.3** 类别挑选本项相关行，填指标/实现要求/验收方式；无则写「无」或省略。  

**隐藏场景**：在步骤 4 编写过程中，将边界/异常/集成类发现记入「触发逻辑」或单独「补充说明」段落，避免只写 happy path。

---

### 步骤 5：隐藏场景与一致性加固

**目标**：对照常见遗漏类型做第二轮补强（与 **review-checklist.md** 中隐藏场景、场景覆盖呼应）。

**动作**：

1. **边界**：空值、极值、大批量、重复提交等。  
2. **异常**：超时、下游失败、部分成功、幂等与重试期望（若材料有提）。  
3. **特殊**：特定角色、特殊时间窗口、特殊业务状态。  
4. **集成**：跨系统数据一致、回调、对账、补偿（若涉及）。  

将补强结果**回填**到对应需求项的 **3.2.3 / 3.2.4** 或集中「待确认」列表，不引入材料未授权的新功能。

---

### 步骤 6：输出路径自检与成稿组装

**目标**：确认输出路径在正确的知识库仓库中，然后输出一份结构完整、可评审的 Markdown。

**输出路径自检（在写文件前必须执行）**：

1. **定位知识库仓库**：在工作区中查找 \`ocspec-<xxx>/\` 根目录（通常为 \`ocspec-\` 开头的文件夹，内含会 \`knowledge/\` 和 \`requirements/\` 子目录）。
2. **确认目标路径**：输出路径必须为 \`ocspec-<xxx>/requirements/<需求英文名>_<yyyymmdd>/requirement/requirement.md\`，其中 \`ocspec-<xxx>/\` 是步骤 1 定位到的知识库仓库根目录。**禁止**在工作区根目录或其他位置新建 \`requirements/\` 文件夹。
3. **首次创建检查**：若 \`ocspec-<xxx>/requirements/<需求英文名>_<yyyymmdd>/\` 目录不存在，属于正常情况（首次需求分析），在知识库仓库内创建即可。

**成稿组装动作**：

1. **1 文档信息**：文档名称、作者、创建日期；**1.2 修订历史**至少一行初稿。  
2. 按标准顺序组装：**1 → 2（概述全文）→ 按 2.1 顺序的各需求项大标题章节**。  
3. 通读：**术语**与 **清单/概述** 中的名称一致；**节点编号**与 **触发逻辑步骤** 可对照。  
4. 全文 **UTF-8**，语言与团队约定一致（若项目要求仅中文，与项目规范对齐）。  
5. 保存为 **\`requirement/requirement.md\`**：\`ocspec-<xxx>/requirements/<需求英文名>_<yyyymmdd>/requirement/requirement.md\`。

---

### 步骤 7：评审准备与自检

**目标**：可开会、可签字、可转测试与设计。

**动作**：

1. 打开 **\`review-checklist.md\`**，逐项勾选或记录例外说明。  
2. 重点过：**Given-When-Then 可读性**、**5W1H 是否在成稿中有落点**、**隐藏场景是否覆盖**、**非功能是否可验收**。  
3. 生成或附上：**评审参与人建议列表**、**待澄清项汇总**（可与步骤 1 合并更新）。  
4. 修订后定稿；重大变更回写 **修订历史**。  
5. 全文 **UTF-8**，语言仅使用简体中文（或与团队约定一致）。  
6. 保存路径与步骤 6 自检结果一致：\`ocspec-<xxx>/requirements/<需求英文名>_<yyyymmdd>/requirement/requirement.md\`。

---

## 与其它工作的衔接

- 成稿可作为 **后端设计 / 前端设计**、**测试用例设计** 的输入；接口级契约建议在 **节点描述** 与 **触发逻辑** 中写清调用关系，详细 API 定义由后续设计文档或接口规范承接。
- **下游路径对齐**：\`fullstack-design\` 技能会从 \`requirement/requirement.md\` 读取需求成稿作为设计输入，路径必须一致。
