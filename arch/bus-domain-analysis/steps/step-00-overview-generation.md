# Step 0: 整体业务架构总览生成（前置 · 强制门禁）

## 元信息

- execution-mode: subagent（扫描）+ inline（生成）
- agent: code-scanner（全仓扫描）
- input: 当前工作区**所有非知识库代码仓库**
- output: `{OCSPEC_ROOT}/knowledge/business/business_arch.html`（系统级业务架构总览）+ `domain-backlog.md`（领域梳理清单）
- **门禁：本步产出后必须强制停止，等待用户明确确认，方可进入单领域梳理（Step 1+）**

## 目的

在梳理任何单个业务领域之前，先对**整个工作区的全部应用代码仓库**做一次系统级扫描，产出**业务架构总览 `business_arch.html`**——它是所有单领域详情页的"母图"与导航入口（各领域方块从此页跳转）。没有这张总览，单领域梳理会缺乏全局定位、领域边界易错漏。

## 触发判断（是否执行本步）

执行本技能时，先判断 `{OCSPEC_ROOT}/knowledge/business/business_arch.html` 是否已存在：

- **不存在** → 必须先执行 Step 0 生成总览，然后**停止等待确认**。
- **已存在** → 由用户决定重做系统总览、执行 Step 0.5 生成纵向领域仅总览，或在已完成 Step 0.5 后明确指定领域与场景进入下钻。

## 执行指令

### 1. 识别工作区代码仓库范围（排除知识库）

- 扫描工作区根目录，列出所有**应用代码仓库**（含 `pom.xml`/`package.json`/`build.gradle` 等的工程）。
- **排除知识库仓库**：即 ocspec 知识库自身（含 `knowledge/`、`common/`、本技能所在目录的仓库）；如工作区有 `repos.txt`，其中标记 `type=kb`（或等价）的仓库不纳入业务扫描。
- 若存在 `repos.txt`，以其中 `type=app`（业务应用）的仓库为准。

### 2. 全仓扫描（subagent: code-scanner）

对每个应用仓库扫描，提取：

| 维度 | 说明 |
|------|------|
| 仓库定位 | 每个仓库的角色（接入层/核心/抽数/核算/渠道等）、技术栈 |
| 分层链路 | 渠道 → 接入 → 核心 → 下游 的数据流关系（据配置/调用确证） |
| 业务领域 | 各仓库承载的业务领域（按交易码/Controller/模块归纳） |
| 领域×仓库矩阵 | 领域在哪些仓库出现、主/次承载 |
| 外部系统/渠道 | 网关、编排、外部合作方（据代码痕迹，无痕迹标 `[待确认]`） |
| 核心链路 | 交易→核算的端到端数据流 |

**代码驱动强制**：所有结论须有代码依据（配置文件/枚举/类名/调用）；工作区外系统标 `[待确认]`。

### 3. 按模板生成 business_arch.html（涵盖必备内容）

参照 `references/overview-template.html` 生成，**必须涵盖以下章节**：

1. **系统概述与分层方法**：系统定位、仓库数、分层链路总述，并说明“横向通用域 × 纵向生命周期域”的组织视角。
2. **§1 系统分层架构与业务领域全景图（强制使用模板内置 `.a5-*` HTML 卡片，不得用 Mermaid 或自由布局替代）**：
   - 使用模板的五个通用层位 `{LAYER_1_*}` 至 `{LAYER_5_*}`。每层的名称、说明、标识符、卡片内容、分组和层间关系均必须基于扫描结果填充；模板不预设任何行业、系统、业务域或技术链路。
   - 第 3 层使用主区域的两个可配置分组 `{LAYER_3_GROUP_1_*}`、`{LAYER_3_GROUP_2_*}`；第 4 层使用侧栏卡片；第 5 层使用两个可配置分组。某层或分组缺乏代码证据时填 `[待确认]` 或空卡片说明，不得借用其他项目的业务内容补齐。
   - 需要下钻的领域卡片使用 `<a class="a5-cell a5-core" href="{DOMAIN_LINK}">{DOMAIN_CELL_CONTENT}</a>` 生成真实稳定链接；链接目标即使尚未生成也必须预填。每张卡片必须包含扫描到的名称、代表能力和主要仓库/模块代码依据。
   - **领域详情场景对齐（强制）**：若 `{domain}/{domain}_arch.html` 已存在，领域方块的场景标签必须逐项复制该详情页的正式场景标题，禁止缩写、合并或改写；禁止显示“含 N 个场景 / N 个用例 / 领域总览含……”等数量性描述。若详情页尚未生成，可暂列代码归纳的子能力，但生成或调整详情页后必须回写图 1，使其以正式场景标题对齐。
   - 使用模板占位符填充全部结构：`{LAYER_1_MARK}`～`{LAYER_5_MARK}`、对应的 `{LAYER_N_TITLE}` / `{LAYER_N_DESCRIPTION}` / `{LAYER_N_CELLS}`、所有层间标签、分组标题、分组卡片与证据占位符。卡片区填入 `.a5-cell`，证据区填入 `.a5-repo` 或空字符串。
3. **§2 端到端数据流**：用 Mermaid `flowchart LR` 表达从渠道受理到核心记账、日终抽数/ETL、总账/报表的链路；明确同步调用、文件/消息等异步边界及代码依据。
4. **§3 业务生命周期**：至少一个纵向主线与一个横向组件生命周期 Mermaid 图；纵向主线覆盖受理/开立/存续/处置/核算等实际阶段，横向图覆盖可复用业务组件。
5. **§4 领域 × 代码仓库映射矩阵**：必须按“横向通用域”和“纵向业务生命周期域”分组（使用 `grp` 行）；每格标明主要/次要承载、模块/证据，矩阵后的跨系统职责边界补充以 `{MATRIX_NOTES}` 填入一个或多个 `.note` 输出。
6. **§5 各仓库业务领域清单**：每个仓库或职责相同的仓库组必须独立输出 `5.1`、`5.2`… 小节。每节依次包含仓库定位/技术或架构职责说明、领域证据表（领域中文名、domain、模块/入口、代表类或交易码、依据路径），以及有必要时的差异/边界 `.note`；禁止将所有仓库压缩为单表。
7. **§6 待确认事项**：除代码缺口外，必须纳入跨系统职责边界、外部依赖、产品/账务生命周期转换、主次承载无法唯一判定等架构不确定性；每项写明代码事实、待确认问题与业务/追溯影响。

**格式要求**：
- 引用 `../../common/case.css`、`../../common/mermaid.min.js`（总览页在 `knowledge/business/` 下，经 `../../common/` 引用与 `knowledge/` 同级的公共资源）。
- §1 固定使用模板内置 `.a5-*` CSS 卡片结构；§2、§3 固定使用 Mermaid；不得复制 example 中的具体系统名称、领域、仓库、渠道或文字内容。
- Mermaid 图 `theme:'dark'`；防裸尖括号泛型破图。
- 领域跳转链接在 Step 0 根据 `domain-backlog.md` 的 domain 立即写入 `href="{domain}/{domain}_arch.html"`，不等待领域详情页生成，也无需后续回填。

### 4. 落盘公共资源（首次建库 · 全库唯一一份）

技能全部产出（总览 / 领域 / flow / code 页）统一引用 ocspec 根下、与 `knowledge/` **同级**的一份公共资源 `{OCSPEC_ROOT}/common/`。首次向知识库落文件时，将技能包自带的 `references/case.css`、`references/mermaid.min.js` 复制到该目录（不存在则创建）：

- `{OCSPEC_ROOT}/common/case.css`
- `{OCSPEC_ROOT}/common/mermaid.min.js`

各页面按自身相对深度引用：总览 `../../common/`、领域 `../../../common/`、flow 与 code 页 `../../../../common/`。已存在则跳过，无需按领域重复落盘。

### 5. 同步生成 domain-backlog.md（领域梳理清单）

在 `{OCSPEC_ROOT}/knowledge/business/domain-backlog.md` 输出**待梳理领域清单**，作为后续单领域梳理（Step 1+）的计划：

- 按业务能力域列出所有识别到的领域（中文名 / domain / DOMAIN_CODE / 覆盖用例概要 / 跨越应用 / 代码依据 / 前置待确认项）。
- 标注建议起步顺序与优先级。
- 标注各领域的前置待确认项（是否阻塞）。

**职责边界**：domain-backlog.md **只放待梳理清单与优先级/阻塞项**，禁止写入已在 business_arch.html 中结论化的业务口径、架构分析或系统间职责描述——这类内容只在总览页维护一份，不在 backlog 中重复。当所有领域梳理完成后，该文件可删除。

### 6. 强制停止 · 等待用户确认（门禁）

生成 `business_arch.html` + `domain-backlog.md` 后，**必须停止，不得自动进入 Step 0.5 或 Step 1**。向用户输出：

```
已生成系统级业务架构总览 business_arch.html 与领域梳理清单 domain-backlog.md。
请审阅总览图（分层/领域方块/矩阵/待确认项）是否准确完整。
确认无误后，我将先为全部纵向业务领域生成仅含领域边界、能力与场景目录的总览页；之后再次等待您指定领域和场景，再生成用例与时序下钻内容。
```

- **只有用户明确回复确认后**，才可执行 Step 0.5。
- 完成 Step 0.5 后仍必须等待用户明确指定领域 + 场景，才可进入 Step 1。
- 用户若对总览提出修改，先改总览、再次停下确认，直至用户认可。

## 校验

- business_arch.html 覆盖上述 7 个必备章节；§1 必须存在模板内置 `.a5-wrap`、五类层次卡片与核心领域真实 `href` 链接，禁止以 Mermaid/自由布局替代。
- 每个核心领域卡片、通用能力卡片、ETL/总账卡片均有代表能力与仓库/模块代码依据；领域卡片与 §4、§5、domain-backlog 的 domain 一致且不重复。
- 对每个已存在 `{domain}/{domain}_arch.html` 的领域链接，逐项比对图 1 卡片场景标签与详情页正式场景标题：名称、顺序均须一致；图 1 方块不得含“含 N 个场景 / N 个用例 / 领域总览含……”等数量性描述。
- §4 按横向通用域/纵向生命周期域分组；§5 按仓库输出独立编号小节与证据表，不得合并成单表。
- 所有仓库均被扫描（对照 repos.txt / 工作区仓库清单，无遗漏）；结论有代码依据，工作区外/未定位处标 `[待确认]`。
- §6 每个待确认项均包含代码事实、待确认问题、业务或追溯影响，并至少检查跨系统职责/外部依赖/主次承载边界。
- **确认门禁生效**：未获用户确认前不进入 Step 1。
