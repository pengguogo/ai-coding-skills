核心理念

🔧 规范化

每个阶段严格遵循标准化流程与规范引用，确保产出物结构一致、可审计。所有 Skill 遵循「文档职责边界 → 角色定位 → 执行流程 → 输出与交付物 → 执行红线」的统一母版结构。

🔗 可追溯

从需求到代码的全链路可追溯：REQ 编号 → 设计文档 → 任务拆分 → 代码实现 → 归档。每个产物都明确标注上游输入与下游消费者，形成完整的知识链。

✅ 质量内建

质量不是事后检查，而是内建于每个阶段：TDD 驱动开发、系统化调试、完成前验证、代码审查请求与接收，贯穿全流程的质量保障 Skills 确保每一步都达到交付标准。

阶段 0：技能分发与同步

概述

技能分发与同步是整个 E2E 流水线的起点，确保所有 AI 编码工具（Cursor / Kiro / Trae / Claude Code / OpenCode）使用统一版本的技能包。通过从 GitHub 中央仓库拉取最新技能包，并分发到各工具的配置目录，实现技能版本的统一管理。

核心 Skill

📦 spec-skills-refresh

工作流程

步骤动作检查点
1. 确认配置确认 git 仓库地址、目标工具（Cursor/Kiro/Claude Code/OpenCode/Trae）、更新范围（全局/项目）仓库 URL、分支策略、工具与范围明确
2. 执行更新脚本从 GitHub 拉取 main 分支，同步到所选路径脚本以 0 退出，日志中出现「技能更新完成」
3. 同步结果说明汇总已同步的源目录、各工具 skills 路径、备份快照路径路径与范围一致

快速开始

# 交互式执行
bash skills/spec-skills-refresh/script/spec-skills-refresh.sh

# 或在 AI 工具中输入
/spec-skills-refresh

阶段 1：环境初始化

概述

环境初始化阶段负责将开发所需的代码仓库批量克隆到本地工作区，并切换到指定分支。支持幂等操作——已存在的仓库会自动更新而非重复克隆。

核心 Skill

🏗️ workspace-init

工作流程

步骤动作说明
1. 解析 repos.txt读取工作区根目录的 repos.txt（TSV 格式：name/type/url/branch）跳过空行与 # 注释行
2. 批量 clone/更新对每行执行 git clone 或 fetch + checkout + pull --ff-only幂等操作，目录存在则更新
3. 结果校验逐条校验目录存在、git 仓库、远程 URL、当前分支、同步状态异常时尝试安全修复
4. 手动清单无法自动修复的条目输出可执行的手动处理清单包含可复制的 git 命令

清单文件格式（repos.txt）

# name    type    url                                    branch
my-api    app     https://github.com/org/my-api.git      main
my-web    app     https://github.com/org/my-web.git      develop

阶段 3：需求分析

概述

需求分析阶段从设计原型出发，经过推导和结构化分析，产出可评审、可追溯的需求文档。分为两步：原型推导（从 Axure/Figma 原型提取规则）和需求结构化（5W1H 穿透分析）。

两步流程

Step 1: 原型推导

prototype-derivation

  • 盘点原型来源（站点图、HTML 页面）
  • 映射模块（对齐产品主题）
  • 摘录规则（推导明细）
  • 处理冲突（冲突/决策日志）
  • 交接给正式规格

产出：推导索引表、推导明细、冲突日志

→

Step 2: 需求结构化

requirement-analysis

  • 接受材料与范围确认
  • 5W1H 穿透分析
  • 需求项拆解与总体概述
  • 逐需求项业务流程建模
  • 隐藏场景与一致性加固
  • 评审准备与自检

产出：requirement/requirement.md

4

阶段 4：技术方案设计

概述

技术方案设计阶段在同一执行会话内按顺序完成后端设计与前端设计。后端设计先行，前端设计基于后端设计的接口定义进行字段级对齐，确保前后端契约一致。

核心 Skill

🎯 fullstack-design

强制顺序

阶段 A：后端设计

产出 design/backend-design.md

  • §1 背景与目标
  • §2 技术方案（架构/选型/模块）
  • §3.1 模型设计（领域/数据/状态机）
  • §3.2 功能设计（时序图/接口/幂等/异常）
  • §4 稳定性与安全评估
  • §5 风险 & §6 开放问题
→

阶段 B：前端设计

产出 design/frontend-design.md

  • 需求与上下文分析
  • 后端设计对齐（字段级对齐表）
  • 架构设计（模块/组件/状态）
  • UI 组件选型与参照
  • 接口契约复核
  • 接口对齐自检清单（8 项强制检查）
⚠️ 关键约束：禁止在缺少已落盘的 backend-design.md 时开始或定稿 frontend-design.md。前端凡涉及后端 HTTP/API 的契约须以 backend-design.md 为准。
5

阶段 5：任务拆分

概述

基于已产出的后端和前端设计文档，将本次需求拆分为可落地的开发任务清单（先后端、后前端），输出任务依赖关系与时序建议，供后续代码实现阶段使用。

核心 Skill

📋 task-split

工作流程

步骤动作说明
1读取设计文档并提炼任务来源通读 backend-design.md 和 frontend-design.md，提取可拆分的工作包
2确定颗粒度与边界任务小到可在一次迭代内完成，明确交付物与验证方式
3生成后端任务清单数据库、模块、集成、测试、文档等编号任务
4生成前端任务清单路由、组件、状态、联调等编号任务
5任务依赖与执行顺序前后端任务的前置依赖、可并行项、联调窗口
6开放问题与风险设计中未闭合项、需确认的问题
7落盘与自检写入 task/task-split.md

产出路径：ocspec-<xxx>/requirements/<需求英文名>_<yyyymmdd>/task/task-split.md

6

阶段 6：代码实现

概述

代码实现阶段基于任务拆分进行前后端编码。按依赖顺序先执行后端任务，后端完成后执行前端任务，最终通过编译门槛验证。

核心 Skill

⚡ fullstack-code-implementation

后端编码流程

步骤动作
1. 读取设计输入与任务拆分基于后端设计文档自动拆分任务清单，按依赖顺序串行推进
2. 实现前准备定位同类现有实现作为参照，路径与包名遵循规范
3. 按任务类型执行数据库变更 → Entity → Mapper → Domain Service → Service → Controller → RPC/Consumer → 单元测试
4. 记录执行日志状态、起止时间、涉及文件、备注
5. 自检与交付对照代码审查检查清单自检，执行编译与单元测试

前端编码流程

步骤动作
0. 现有项目分析优先基于 frontend-project.md 获取项目约束
1-2. 项目初始化 + 基础组件创建项目结构、配置开发环境、开发通用/业务组件
3-4. 布局 + 页面组件开发布局组件、按优先级开发页面（P0→P1→P2）
5-7. API + 状态 + 路由API 集成、状态管理、路由配置
8-10. 权限 + 样式 + 交互权限控制、样式实现、交互状态
11-14. 错误 + 性能 + 测试 + CR错误处理、性能优化、测试、代码审查准备

编译门槛（编码完成后）

后端编译门槛

执行编译/打包/构建脚本，确认关键编译产物生成

前端构建门槛

执行 lint / typecheck / build，确认构建产物非空

7

阶段 7：项目归档

概述

项目归档是 E2E 流程的收尾阶段。在一次执行中完成业务层、应用层、代码/接口层的统一归档，并将增量知识回写到知识库，确保知识库持续更新。

核心 Skills

🔎 fullstack-code-review 📁 project-archive

代码审查 — fullstack-code-review

设计驱动的全栈实现质量审查。对照设计文档、任务拆分与编码规范，对代码进行结构化审查，输出分级审查报告。覆盖四大维度：

维度编号说明
编码规范合规BE-* / FE-* / CC-*后端/前端/通用编码规范检查
后端业务实现质量BQ-*幂等/事务/一致性/并发/重试/状态机/异常处理
前端业务实现质量FQ-*状态一致性/竞态/接口健壮性/操作防护/权限
改动影响分析IA-*影响范围、兼容性、回滚方案

项目归档 — project-archive

产出文件视角内容
code-archive.md代码/接口层接口契约表、数据模型变更、前后端实现路径、目录/路由/组件变更
application-archive.md应用层前端页面→后端接口→数据/外部依赖的调用链
business-archive.md业务层目标、范围、角色、业务流程、规则、需求对照表

知识库同步（强制）

归档正文落盘后，必须按 5 步流程（读取→分析→定位→融合→校验）更新知识库：

knowledge/application/
knowledge/business/
knowledge/code/.../frontend-project.md
knowledge/code/.../backend-project.md

Skills 详情

本仓库包含 12 个 Skills，每个 Skill 都有独立的 SKILL.md 定义文件和参考文档。

spec-skills-refresh 规范技能刷新

从 GitHub 拉取 ai-coding-skills 技能包（默认 main 分支），并按所选工具与范围同步到全局或项目内的 AI 技能目录。支持 Cursor / Kiro / Trae / Claude Code / OpenCode。

📁 3 个文件📍 阶段 0

workspace-init 工作空间初始化

读取工作区根目录 repos.txt（TSV：name/type/url/branch），在根目录按 name 自动 clone/更新并切换分支；初始化结束后必须校验各仓库是否就绪，异常时尝试安全修复，无法修复则输出可执行的手动清单。

📁 3 个文件📍 阶段 1

code-knowledge-init 代码知识还原

统一执行代码知识还原与初始化：识别目标代码库的前端/后端/一体化属性，并生成对应的 knowledge/code 文档产出。适用于初始化代码知识、还原项目知识、生成项目文档、分析代码库等场景。

📁 12 个文件📍 阶段 2

application-knowledge-init 应用架构知识生成

当用户要求生成、梳理或更新"应用架构设计"、"系统架构图"、"应用组件全景"等相关文档时使用。基于前后端代码扫描基线及可验证源码/配置，归纳生成应用架构知识。支持分批次、分层级聚合生成。

📁 6 个文件📍 阶段 2

business-knowledge-init 业务架构知识生成

当用户要求生成、梳理或更新"业务架构"、"业务领域知识"、"业务流程"、"用例图"、"领域对象(DO)与领域事件(DE)"等相关文档时使用。基于源码与基线，归纳生成标准化的业务领域知识文档。

📁 7 个文件📍 阶段 2

prototype-derivation 原型→需求推导

从设计原型（Axure 导出 HTML、Figma 导出或同类静态包）推导结构化需求追溯物：模块映射、规则摘录、冲突矩阵与交付正式规格前的交接说明。

📁 2 个文件📍 阶段 3

requirement-analysis 需求分析

将原始需求整理为符合团队标准的 Markdown 需求文档，并用 5W1H 与评审清单支撑澄清与评审。适用于任意技术栈。

📁 4 个文件📍 阶段 3

fullstack-design 前后端技术方案设计

在同一执行会话内按顺序完成后端设计（design/backend-design.md）与前端设计（design/frontend-design.md）。不产出可运行代码。本包内含全部 references。

📁 8 个文件📍 阶段 4

task-split 任务拆分

在已通过 fullstack-design 产出两份设计文档之后，基于设计文档将本次需求拆分为可落地的开发任务清单（先后端、后前端），输出任务依赖关系与时序建议。产出 task/task-split.md。

📁 3 个文件📍 阶段 5

fullstack-code-implementation 前后端代码实现

前后端编码合并技能。基于 task/task-split.md 的后端/前端任务拆分，按后端与前端原有编码流程分别实现。凡由 AI 生成的前后端代码均须标注 AI-Generate。

📁 9 个文件📍 阶段 6

fullstack-code-review 前后端代码审查

设计驱动的全栈实现质量审查技能。对照设计文档、任务拆分与编码规范，对代码进行结构化审查，输出分级审查报告。审查覆盖四大维度：编码规范合规、后端业务实现质量、前端业务实现质量、改动影响分析。

📁 8 个文件📍 阶段 7

project-archive 项目统一归档

端到端统一归档（独立技能）：一次性覆盖前端与后端，结合需求、设计、任务拆分与知识库，产出 code-archive.md、application-archive.md、business-archive.md。落盘后须更新知识库并增量更新项目文档。

📁 4 个文件📍 阶段 7

贯穿全流程的质量保障 Skills

以下 Skills 不绑定特定阶段，而是在任何阶段均可激活，提供横切质量保障能力。

🧪

test-driven-development

在实现任何功能或修复 Bug 前，先编写测试。确保代码质量与需求覆盖。

🔍

systematic-debugging

遇到任何 Bug、测试失败或意外行为时，在提出修复方案前进行系统化调试。

✅

verification-before-completion

在声称工作完成、修复或通过之前，运行验证命令并确认输出。证据先于断言。

📤

requesting-code-review

完成任务、实现重要功能或合并前，请求代码审查以验证工作满足要求。

📥

receiving-code-review

收到代码审查反馈后，在实施建议前进行技术严谨性验证，不盲目执行。

⚡

dispatching-parallel-agents

面对 2+ 个独立任务时，分派并行代理以提高效率，无共享状态或顺序依赖。
