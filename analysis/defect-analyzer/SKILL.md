# 缺陷分析与修复

## 何时使用

- 用户描述一个系统缺陷/异常现象（如数据不一致、状态错判、金额偏差、流程异常），需要定位根因
- 需要梳理跨模块/跨仓库的执行链路与时序，找出问题发生的确切位置
- 需要构造可复现的问题示例、评估影响面、给出代码修复或数据订正方案
- 需要输出可交付的 HTML 格式缺陷分析与修复报告

## 核心方法论（不针对单一问题，适用于一切缺陷分析）

缺陷分析的本质是：**在一条或多条执行链路上，找出「应该怎样」与「实际怎样」的分歧点，追溯到产生分歧的根因代码，并在不引入新副作用的前提下修复。** 六个核心动作：

1. **澄清问题（Clarify）**：先确认「现象、场景、范围」是否明确。问题不清晰时，分析无从谈起——必须先向用户提问补充，而非凭猜测开工。
2. **梳理链路时序（Sequence）**：把缺陷涉及的数据/状态在**哪几条链路**上被读写、**分别在什么时点**执行画清楚。缺陷往往源自「两条链路对同一事物各算一次且不同源」，或「消费方读到的值早于/晚于生产方写入」。
3. **定位根因（Root Cause）**：找到产生分歧的**确切代码位置**（文件:行号），区分「权威源」与「消费方」，说明为什么会算错/读错，而非停留在表象。
4. **构造示例（Example）**：用**具体的、可复现的**输入数据，展示「预期值 vs 实际值」的分歧，让非作者也能一眼看懂缺陷。
5. **评估影响（Impact）**：分歧会波及哪些下游功能、严重度多高、生产是否真实暴露（哪些依赖配置无法从代码断定，需人工核对）。
6. **设计修复（Fix）**：**先分析被改代码的作用域**（所有调用方、服务的所有场景、维护的不变量/契约），再设计**只改缺陷路径、不破坏其他场景**的最小化修复；配合（如有存量数据）数据订正方案，并对代码改动与数据订正各做**逐条影响分析**，评估是否引入新副作用、执行时机、可回滚性。

## 执行原则（强制）

- **明确性门禁优先**：Step 1 判定问题不明确时，**立即停止并向用户提问**，不得带着假设继续分析。这是硬性约束。
- **事实源优先**：所有结论必须有代码引用支撑，禁止凭经验臆断。引用格式统一为 `文件路径:行号`。未找到引用时，明确标注「未找到代码引用，建议人工确认」。
- **时序为纲**：先画清链路和时点，再谈根因。必须区分「谁先写、谁后读」「哪条链路是权威源、哪条是消费方」。
- **根因优先于表象**：定位到产生错误的代码机制，而非只描述现象。能回答「为什么会这样」才算定位成功。
- **示例可复现**：问题示例必须用具体数值，给出「预期 vs 实际 vs 是否一致」，避免空泛描述。
- **改代码前先定作用域（Scope-before-fix，强制）**：设计代码修复前，必须先摸清待改代码的作用范围——用搜索找全**所有调用方**、列出它服务的**所有业务场景**、识别它维护的**不变量/契约**（取值粒度、非空保证、排序假设、字段联动等）。修复只改缺陷路径、保持其他场景行为不变；共享代码用护栏/分支而非改动公共逻辑；保留原有边界兜底。禁止不做作用域分析就直接给 diff。
- **修复评估副作用**：任何修复（改代码或订数据）都要做后置影响分析——代码改动要对照作用域矩阵**逐个调用方/场景**判定「保持不变 / 有变化但可接受 / 会破坏」，数据订正要回答「会不会被覆盖、会不会误伤、什么时候执行安全、能否回滚」。出现「会破坏」必须重新设计。
- **区分代码事实与配置事实**：能从代码断定的写结论；依赖运行时配置/数据才能断定的（如某产品是否启用某开关），标注为「需人工核对」，不臆断。
- **多仓库全覆盖**：工作区内所有相关代码仓库都要搜索，不得遗漏跨仓库的链路。
- **搜索策略**：对每个目标类名/表名/字段名，分别用精确匹配和模糊匹配（驼峰、下划线）搜索。
