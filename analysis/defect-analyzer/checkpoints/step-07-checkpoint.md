# Checkpoint: Step 7 质量校验

> **审查级别**：L2（深度审查）— 需实际读取代码验证事实源。
> **审查原则**：你是审查者，不是作者。必须实际 readFile 验证，不能凭记忆判断。缺陷报告事实源错误的危害大于不分析。

## 校验清单

### 事实源真实性（最高优先级）
- [ ] 每个 `文件:行号` 引用真实存在（readFile 确认）
- [ ] 引用行号处代码内容与报告描述一致
- [ ] Mapper XML 中 SQL 条件与报告原文一致
- [ ] 无虚构、无错位引用

### 链路时序完整性
- [ ] 目标数据的写入点无遗漏（grepSearch set/insert）
- [ ] 目标数据的消费点无遗漏（grepSearch get/WHERE/ORDER BY）
- [ ] 权威源 vs 消费方界定准确
- [ ] 各链路执行时点（在线/EOD/初始化）描述与代码一致

### 根因定位准确性
- [ ] 定位的是代码机制，而非仅现象
- [ ] 根因代码顺逻辑复算确实会导致所述错误
- [ ] 不存在被忽略的更上游根因

### 问题示例可复现性
- [ ] 示例具体数值代入根因逻辑能复算出报告所说"实际值"
- [ ] "预期值"符合正确链路规则
- [ ] 覆盖了暴露问题的边界场景

### 代码修复作用域（改代码前是否做够分析）
- [ ] 是否列全了待改代码的**所有调用方**（grepSearch 方法名/字段名核实无遗漏）
- [ ] 是否识别了它服务的**所有场景**与维护的**不变量/契约**（粒度、非空、排序、联动等）
- [ ] 修复是否**只改缺陷路径**、保持其他调用方/场景行为不变（共享代码用护栏而非改公共逻辑）
- [ ] 是否**保留了原代码的边界兜底**（null/空集/异常），没有把旧缺陷换成新缺陷（如 NPE）
- [ ] 作用域矩阵每个场景都判定为 ✅/⚠️，无 ❌（有 ❌ 说明方案会破坏其他场景）
- [ ] 存量订正的目标值口径与修复后代码产出口径一致

### 数据订正安全性
- [ ] 订正 SQL 的 WHERE 不会误伤非目标记录
- [ ] 目标值若来自 JOIN，不会一对多取错值
- [ ] 订正值不会被某 Job / 存量初始化作业重算覆盖（已搜索确认）
- [ ] 执行时机与代码/作业上线先后约束正确

### 逻辑一致性
- [ ] 严重度分级与影响说明匹配
- [ ] 根因、示例、影响、修复四者指向同一问题，自洽
- [ ] 依赖配置无法断定的项已标注「需人工核对」

## 判定标准

- **全部 ✅**：校验通过，进入 Step 8
- **存在 ❌**：回到对应 Step 修正，最多重试 2 次
- **仅 ⚠️**：补充后进入 Step 8
- **2 次后仍有 ❌**：标注 `[需人工确认]` 后进入 Step 8
