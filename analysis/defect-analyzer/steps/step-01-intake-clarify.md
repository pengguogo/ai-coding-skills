# Step 1: 输入接收与明确性判断（门禁）

## 元信息

- execution-mode: inline
- checkpoint: checkpoints/step-01-checkpoint.md
- gate: true（未通过不得进入 Step 2）

## 参数

- input: 用户提供的缺陷描述（现象、日志、SQL、截图、复现步骤等，形式不限）
- output: 结构化问题陈述（明确）或 澄清问题清单（不明确，停止）

## 目的

缺陷分析最常见的失败不是分析错，而是**分析了一个没描述清楚的问题**。本步骤是硬性门禁：先判断「现象、场景、范围」是否足以支撑分析，不足则先向用户要信息，绝不带着假设开工。

## 执行指令

### 1. 归纳用户输入

把用户提供的一切信息（自然语言描述、错误日志、异常数据、SQL、复现步骤、截图说明）归纳为结构化要素：

| 要素 | 说明 | 是否关键 |
|------|------|---------|
| 现象（Symptom） | 出了什么问题？**预期行为 vs 实际行为**分别是什么 | ★关键 |
| 触发场景（Trigger） | 什么条件/操作/时点下发生？是否可复现 | ★关键 |
| 影响对象（Scope） | 涉及哪些业务模块/表/字段/接口/账户 | ★关键 |
| 代码基线（Baseline） | 哪个仓库/分支/版本；工作区是否包含相关代码 | 重要 |
| 佐证（Evidence） | 错误信息、日志、异常数据样本、监控告警 | 有则更好 |
| 期望产出（Goal） | 只要定位根因，还是要连修复方案一起 | 默认全量 |

### 2. 按明确性清单判定

对照 `checkpoints/step-01-checkpoint.md` 逐项打分。核心判据：

- **现象是否具体**：能区分「预期」与「实际」，而非仅「有问题/不对/异常」这类笼统词
- **能否落到代码**：影响对象能映射到可搜索的模块/表/字段/接口，而非纯业务黑话
- **范围是否可控**：代码基线在工作区内可检索，或用户明确指定了检索范围

判定规则：

| 情形 | 判定 | 动作 |
|------|------|------|
| 三个★关键要素齐备且现象具体 | **明确** | 产出结构化问题陈述，进入 Step 2 |
| 缺 1 个★关键要素，但可从工作区代码合理推断补齐 | **基本明确** | 记录假设（标注「待用户确认」），进入 Step 2，并在报告开头列出假设 |
| 缺 ≥2 个★关键要素，或现象本身笼统 | **不明确** | 生成澄清问题清单，**停止执行**，等待用户补充 |

### 3a. 若判定「不明确」——生成澄清问题并停止

**必须停止，不得继续 Step 2。** 输出格式：

```
你的缺陷分析请求还缺少一些关键信息，补充后我才能准确定位。请帮我确认：

【现象】
- 期望的正确行为是什么？实际观察到的错误行为是什么？（越具体越好，最好带一组数据）

【场景】
- 什么操作或什么时点触发？是必现还是偶现？

【范围】
- 大概涉及哪个业务模块/功能/表/接口？相关代码在哪个仓库？

（如有）错误日志、异常数据样本、报错截图也一并发我。
```

- 只问**真正缺失**的项，已提供的不要重复问。
- 问题要具体、可回答，避免开放式大问题。
- 补充信息后，重新执行 Step 1 再判定。

### 3b. 若判定「明确 / 基本明确」——产出结构化问题陈述

输出以下结构，作为后续所有步骤的分析基准：

```
## 问题陈述

- 现象：{预期行为} → {实际行为}
- 触发场景：{条件/操作/时点，是否可复现}
- 影响对象：{模块 / 表 / 字段 / 接口 / 账户}
- 代码基线：{仓库/分支}
- 佐证：{日志/数据/告警，若有}
- 分析目标：{定位根因 / 定位根因+修复方案}
- 待确认假设：{若为"基本明确"，列出推断项，标注需用户确认}
- 问题简称：{用于报告命名，如 "MAD快照宽限日不一致"}
```

## 产出

- **不明确** → 澄清问题清单（流程在此中止，等待用户）
- **明确/基本明确** → 结构化问题陈述 + 问题简称，进入 Step 2

## 反例（禁止行为）

- ❌ 用户只说「XX 数据不对」，就直接猜一个表开始查代码
- ❌ 缺关键信息却「先分析着，边分析边猜」
- ❌ 把「基本明确」的推断项当成既定事实，不在报告中标注为假设
