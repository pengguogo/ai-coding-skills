# Step 7: 质量校验（Subagent Check）

## 元信息

- execution-mode: subagent
- agent: general-task-execution
- checkpoint: checkpoints/step-07-checkpoint.md

## 参数

- input: Step 1-6 的全部产出
- output: 质量校验结果（✅/❌/⚠️ 清单 + 修正动作）

## 目的

缺陷分析报告一旦事实源引用错误、根因判断偏差或修复方案有副作用，危害比不分析更大（会误导订正、破坏正确数据）。本步骤由独立 subagent **重新验证所有事实源**，确保报告可交付。

## 执行指令

使用 `invokeSubAgent`（name: `general-task-execution`）执行交叉校验。

### Subagent Prompt 模板

```
请对以下缺陷分析与修复方案进行质量校验。你是独立审查者，必须实际读取代码文件重新验证，不信任主流程的任何结论。

## 校验输入

[将 Step 1-6 的完整产出粘贴到此处]

## 校验项

### 1. 事实源真实性（最高优先级）
- 报告中每个 `文件:行号` 引用是否真实存在？（用 readFile 打开验证）
- 引用行号处的代码内容是否与报告描述一致？
- Mapper XML 中的 SQL 条件是否与报告原文一致？
- 发现虚构/错位引用立即标 ❌

### 2. 链路时序完整性
- 是否遗漏了对目标数据的写入点或消费点？（用 grepSearch 搜字段的 set/get、XML 引用）
- 权威源 vs 消费方的界定是否准确？
- 执行时点描述是否符合代码（在线/EOD/初始化）？

### 3. 根因定位准确性
- 定位的是代码机制还是仅现象？
- 根因代码是否真的会导致所描述的错误？（顺着逻辑复算）
- 是否存在更上游的真正根因被忽略？

### 4. 问题示例可复现性
- 示例的具体数值代入根因代码逻辑，能否复算出报告所说的"实际值"？
- "预期值"是否符合正确链路的规则？

### 5. 修复方案安全性
- 代码修复是否会影响其他调用方？
- 订正 SQL 的 WHERE 是否可能误伤非目标记录？
- 订正值是否会被某个 Job 重算覆盖？（搜是否有 update 该字段的 SQL）
- 执行时机约束是否正确？

### 6. 逻辑一致性
- 严重度分级是否与影响说明匹配？
- 报告各段结论之间是否自洽（根因、示例、影响、修复指向同一问题）？

## 输出格式

对每个校验项输出：
- ✅ [校验项] - 通过原因
- ❌ [校验项] - 问题描述 + 具体修正建议（须指明哪个 Step 的哪个产出需要修正）
- ⚠️ [校验项] - 报告未覆盖但应补充的内容

## 校验原则
- 必须实际 readFile 验证关键引用，不可凭记忆
- 对关键 SQL/字段用 grepSearch 确认原文与遗漏
- 对问题示例必须动手复算验证
```

### 校验后处理

1. **全部 ✅**：进入 Step 8
2. **存在 ❌**：按修正建议回到对应 Step 修正，修正后重新执行 Step 7
3. **仅有 ⚠️**：将补充建议纳入对应 Step 产出后进入 Step 8
4. **最多重试 2 次**：2 次后仍有 ❌ 的项，标注 `[需人工确认]` 后进入 Step 8

## 产出

- 质量校验结果（✅/❌/⚠️ 清单）
- 修正动作记录（若有）
