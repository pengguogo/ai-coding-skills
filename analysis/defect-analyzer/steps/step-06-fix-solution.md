# Step 6: 修复方案设计

## 元信息

- execution-mode: inline

## 参数

- input: Step 3 根因 + Step 5 影响分析
- output: 修复方案（变更点作用域分析 + 代码修复 + 存量数据订正 + 逐条后置影响分析 + 执行时机 + 验证防回归）

## 目的

给出**根因级修复**，而非头痛医头。一个完整的缺陷修复通常有两条腿：
- **代码修复**：从源头堵住缺陷，让新数据不再产生偏差
- **存量数据订正**：已经产生的错误数据如何安全纠正

**核心纪律：改代码前先定作用域。** 待修改的方法/代码块往往同时服务多个调用方与业务场景、并维护着某些隐性契约（不变量）。不先摸清这些就动手，"修好一个场景、改坏三个场景"是缺陷修复最常见的翻车方式。因此代码修复<strong>必须</strong>先做变更点作用域分析，再设计最小化、不破坏其他场景的改法。

## 执行指令

### 1. 代码修复方案

> 顺序强制：先做 1.1 作用域分析 → 再做 1.2 修复设计 → 最后 1.3 逐调用方/场景影响确认。**不得跳过 1.1 直接给 diff。**

#### 1.1 变更点作用域分析（改代码前必做 · 硬性）

对每一处待修改的代码（Step 3 问题点清单里的每个方法/代码块），先用 `readFile` / `grepSearch` 把它的「作用范围」摸清楚，回答：

1. **职责与服务场景**：这段代码承担哪些职责？被哪些业务场景走到？（如：正常态 / 逾期态 / 核销态；单件产品 / 组合产品；在线 / EOD / 初始化；批量 / 单笔）逐一列出。
2. **调用方清单（必须搜全）**：用 `grepSearch` 搜方法名/字段名，找出**所有** caller。每个 caller 代表一个使用场景，都会受这次改动波及。遗漏 caller = 遗漏副作用。
3. **维护的不变量 / 契约**：这段代码对外隐性保证了什么？常见的有：
   - 取值粒度（如"每账户一个周期级单值" vs "逐条各异"）
   - 非空保证（原代码恒返回非空，下游未做 null 防护）
   - 排序 / 顺序假设（下游按某字段排序取第一条）
   - 幂等 / 唯一性 / 范围约束
   - 与其他字段的联动（改 A 必须同步 B）
4. **输出的下游消费方**：这段代码产出的值/状态流向哪里、被谁按什么规则消费（承接 Step 2 的消费链路）。
5. **共享状态**：是否读写缓存、批处理上下文、静态变量、线程本地量。

产出**作用域矩阵**（后面 1.3 要逐行判定影响）：

| 调用方 / 场景 | 事实源 文件:行号 | 该场景期望的行为 / 依赖的不变量 |
|---------------|-----------------|-------------------------------|
| {caller / 场景} | `{文件:行号}` | {它要求这段代码保证什么} |

> 若作用域里存在「无法从代码断定、取决于业务语义或运行数据」的点（如"一个集合内是否只含同一周期的数据"），标注为**需业务/数据确认**，并说明它如何影响修复选型——不臆断。

#### 1.2 修复设计（最小化、精准化）

在 1.1 的作用域约束下设计修复，遵循：

- **只改缺陷路径，其余保持不变**：定位到出问题的那一条分支/场景，只改它；不改变其它调用方/场景看到的行为。
- **共享代码用护栏而非改公共行为**：若待改方法被多场景共享，优先在缺陷路径上加分支/条件（guard），而不是改动所有场景都会走的公共逻辑。
- **保留原有边界兜底**：原代码若有 null/空集/异常/默认值兜底，修复后必须保留（否则可能把"错误值"换成"NPE/空值"这种新缺陷）。
- **保持不变量**：1.1 列出的粒度、非空、排序、联动等契约，修复后必须仍然成立；若必须改变某个不变量，需在 1.3 显式说明并评估所有依赖它的下游。
- 给出修复策略一句话 + 代码 diff（删除行 ✗ / 新增行 ✓）；多个问题点逐一给。
- 若同一根因有多种改法（如改配置 vs 改代码；改生产方 vs 改消费方），列出候选并说明取舍与推荐。

#### 1.3 变更影响逐项确认（对照 1.1 矩阵）

对 1.1 作用域矩阵的**每一个**调用方/场景，逐行判定本次修复的影响，用事实源支撑：

| 调用方 / 场景 | 修复后行为 | 判定 |
|---------------|-----------|------|
| {caller / 场景} | {保持不变 / 有何变化} | ✅ 不受影响 / ⚠️ 有变化但可接受(原因) / ❌ 会破坏(需重新设计) |

- 出现任何 ❌ → 回到 1.2 重新设计（不能带着"改坏其他场景"的方案继续）。
- 显式回答一句：**本次代码改动是否会给其他调用方/场景引入新副作用？** 有则列出并给出规避措施。

### 2. 存量数据订正方案（如有存量脏数据）

若缺陷已产生错误存量数据，设计订正 SQL。**先查后改**：

#### 2.1 存量问题数据查询（先查后改）

给出定位待订正记录的 SELECT，**必须收窄范围避免误伤**：
- 明确订正主键（UPDATE 的定位 Key）和目标值（回填成什么）
- 排除「合理差异」记录（如某些状态下差异是正常的，不是 bug）
- 限定真正受影响的范围（产品/场景/时间窗）
- 补齐唯一键，避免 JOIN 一对多导致行膨胀

对每个收窄条件，用注释说明「为什么必须加这个条件」。

> **目标值取值同样要过作用域分析**：回填成什么值，必须与 1.2 修复后代码产出的值口径一致（如：改代码用"周期级权威值"，订正也要回填同一口径，而不是另一种算法），否则代码与数据两条修复自相矛盾。

#### 2.2 订正 SQL

给出 UPDATE 语句 + 涉及字段含义表。

#### 2.3 逐条后置影响分析（复用数据变更影响分析方法）

订正是一次数据变更，必须分析它会触发/影响哪些下游功能。用整合表，每行含「后置功能 + 事实源 + 触发条件 + 影响结论」：

| 后置功能（+事实源 文件:行号） | 触发条件（SQL条件/代码判断原文） | 影响结论 |
|------|------|------|
| {功能名（EOD/在线/会计）} `文件:行号` | `{条件原文}` — {补充} | ✅安全 / ⚠️需关注 / ❌危险 |

影响结论标签规则：
- ✅ 安全：订正不影响该功能或影响符合预期
- ⚠️ 需关注：行为有变化，需人工确认
- ❌ 危险：会导致错误或异常（如被 EOD 重算覆盖、误改非目标记录）

**必查项：**
- **覆盖风险**：订正后的值会不会被某个 Job 重新计算覆盖？（查是否有 update 该字段的 Mapper SQL 及其触发路径；含存量初始化作业重跑）
- **WHERE 安全性**：订正 SQL 的 WHERE 是否可能误伤非目标记录？
- **目标值匹配**：目标值若来自 JOIN 其他表，是否可能一对多导致取错值？
- **审计字段**：last_change_date 等是否需同步更新

### 3. 执行时机与顺序

明确订正必须在什么时点执行才安全。常见约束：
- 必须在当日 EOD 某步骤**之前/之后**执行（否则当日按旧值处理或被覆盖）
- 多条 SQL 之间的先后依赖
- 代码修复与存量订正/初始化作业的上线先后（避免旧代码重跑覆盖订正值）
- 已过期/已被消费的错误数据能否直接订正，还是需走差错流程逐户处理

用流程式文字给出推荐执行顺序（评估范围 → 生成待订正清单+人工复核 → 备份 → 订正 → 验证）。

### 4. 验证与防回归

| 环节 | 动作 |
|------|------|
| 数据校验 | 订正后重跑 2.1 差异查询，确认一致 |
| 回归测试 | 用 Step 4 的示例场景验证代码修复，覆盖各边界 |
| 场景回归 | 覆盖 1.1 作用域矩阵里的**每个**调用方/场景，确认未被改坏（重点验证未直接改动但共享代码的场景） |
| 上线巡检 | 日终后定时跑差异比对，不一致即告警 |

### 5. 一句话结论

用一句话概括根因 + 修复要点（含"只改缺陷路径、保持其他场景不变"）+ 数据处理原则。

## 产出

- **变更点作用域分析**（作用域矩阵 + 不变量 + 调用方清单）
- 代码修复方案（策略 + diff + 逐调用方/场景影响确认）
- 存量数据订正方案（查询 + UPDATE + 字段含义 + 逐条后置影响分析）
- 执行时机与推荐顺序
- 验证与防回归清单（含场景回归）
- 一句话结论

## 校验自问

- [ ] **改代码前是否列全了被改代码的所有调用方/场景与不变量，并逐一判定影响？**（1.1 + 1.3）
- [ ] 修复是否**只改缺陷路径**、保持其他调用方/场景行为不变？共享代码是否用护栏而非改公共行为？
- [ ] 是否**保留了原代码的边界兜底**（null/空集/异常/默认值）？修复会不会把旧缺陷换成新缺陷（如 NPE）？
- [ ] 1.1 矩阵里每个场景是否都判定为 ✅ 或 ⚠️（可接受），没有 ❌？
- [ ] 存量订正的目标值口径是否与修复后代码产出的口径一致？
- [ ] 修复是否针对**根因**，而非表象/补丁？
- [ ] 订正 SQL 是否先查后改、范围是否收窄避免误伤？订正值会不会被 Job/初始化作业覆盖？
- [ ] 是否给了明确的执行时机与上线先后约束？
- [ ] 依赖配置/业务语义无法断定的地方是否标注「需人工核对」？
