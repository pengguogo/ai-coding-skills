# Step 5: 影响分析

## 元信息

- execution-mode: inline

## 参数

- input: Step 3 根因 + Step 4 分歧维度与示例
- output: 影响面清单（含严重度分级与生产暴露条件）

## 目的

回答「这个缺陷有多严重、波及多广、生产上是否真的踩到了」。缺陷的严重度不取决于代码有多丑，而取决于**错误值会流向哪些下游功能、造成什么业务后果**。同时要诚实区分：哪些能从代码断定，哪些依赖运行时配置无法断定、需人工核对。

## 执行指令

### 1. 追踪错误值的下游流向

从 Step 2 的消费链路出发，列出错误值/错误状态会波及的所有下游功能：
- 直接消费：谁直接读这个错误值做判断/计算
- 间接传导：错误值参与计算后，结果又流向哪里（如逾期天数 → 罚息 → 五级分类 → 监管报送）

### 2. 影响面清单与严重度分级

| 影响面 | 说明（错误值如何导致该后果） | 严重度 |
|--------|------------------------------|--------|
| {功能/指标名} | {传导路径与业务后果} | 高 / 中 / 低 |

**严重度判定标准：**

| 严重度 | 判定标准 | 典型场景 |
|--------|----------|---------|
| 高 | 资金错误 / 错误出单扣款 / 监管报送错误 / 数据被错误覆盖 / 影响面广且不可逆 | 多收罚息、错误置逾期、金额计算错误 |
| 中 | 影响后续计算/凭证/分类，可纠正但需处理 | 期次偏移、状态误判、粒度被抹平 |
| 低 | 影响审计字段/展示，业务后果轻微 | 时间戳不准、非关键展示偏差 |

### 3. 生产暴露条件（诚实标注不确定性）

代码存在缺陷 ≠ 生产一定踩到。必须列出「在什么条件下生产才真实暴露」，并标注哪些**无法从代码断定、需人工核对配置/数据**：

```
是否生产真实暴露，取决于（代码无法断定，需核对）：
① {配置项 A 是否启用，如某产品是否配了某开关}
② {数据条件 B 是否满足，如是否存在该类存量记录}
③ {链路是否对该场景启用}
上述任一成立，就大概率存在存量偏差 / 持续新增偏差。
```

- 能从代码断定的（如「只要走到这段代码必然错」）→ 直接下结论
- 依赖运行时配置/数据的 → 标注「需人工核对」，给出核对方法（查哪张配置表、跑什么查询）

## 产出

- 错误值下游流向说明
- 影响面清单表（含严重度）
- 生产暴露条件与需人工核对项

## 校验自问

- [ ] 每个影响面是否说清了「错误值如何传导到该后果」？
- [ ] 严重度分级是否与业务后果匹配（涉及资金/监管的是否标了高）？
- [ ] 是否诚实区分了「代码可断定」与「需人工核对配置」？
