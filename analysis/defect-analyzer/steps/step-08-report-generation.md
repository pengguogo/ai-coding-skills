# Step 8: HTML 报告生成

## 元信息

- execution-mode: inline

## 参数

- input: Step 1-6 的产出（经 Step 7 校验通过）
- output_file: `{问题简称}问题分析与修复.html`（工作区根目录）
- reference: `references/report-template.html`

## 执行指令

将 Step 1-6 的结果按 `references/report-template.html` 的结构组装为单一 HTML 报告。报告采用**七段式结构**，与四大核心产出（链路时序分析 + 问题定位 + 问题示例 + 修复方案）对应。

### 报告结构与 Step 映射

```
header（标题 + 副标题一句话点明矛盾 + badge 标签）
toc（目录）

一、链路时序分析      ← Step 2（链路 A/B/C 的 flow 时序图 + 矛盾点 note）
二、问题定位          ← Step 3（问题代码 pre 块 + 问题点清单表 + 权威源界定）
三、分歧维度          ← Step 4 第1部分（分歧维度对照表 + 边界一致条件 note）
四、问题示例          ← Step 4 第2部分（具体数值示例表 + 后果直观 flow）
五、影响分析          ← Step 5（影响面表 + 生产暴露条件 note）
六、修复方案与逐条影响分析 ← Step 6（6.1 变更点作用域分析表 + 6.2 代码修复 diff & 逐调用方/场景影响确认表 + 6.3~6.4 订正查询/SQL + 6.5 逐条影响表）
七、验证与防回归      ← Step 6 第4部分（验证表含"场景回归" + 推荐执行顺序 flow + 一句话结论）

footer（代码基线说明）
```

> 若分析目标仅为「定位根因」（Step 1 确认不需要修复方案），则六、七段可省略或简化为「修复方向建议」。

### 关键呈现元素（严格使用模板 CSS class）

| 元素 | CSS class | 用途 |
|------|-----------|------|
| 时序流程图 | `.flow` | 等宽字体展示链路调用序列（保留缩进/箭头/注释） |
| 代码块 | `pre` + `.kw/.str/.cmt/.add/.del` | 问题代码/修复 diff，关键字/字符串/注释/增删着色 |
| 行内代码 | `code.inline` | 字段名、方法名、条件原文 |
| 文件路径 | `.path` | 小字灰色展示 `文件:行号` |
| 提示块 | `.note` / `.note.warn` / `.note.danger` / `.note.ok` | 矛盾点、边界条件、暴露风险、结论 |
| 结论着色 | `td.ok` / `td.bad` | 示例表「是否一致」列 ✅/❌ |
| 标签 | `.tag.a/.g/.o/.r` | 严重度（高=r红/中=o橙/低=g绿）、状态标记 |

### flow 时序图写法（第一段核心）

链路时序图是本报告最有价值的部分。每条链路用一个 `.flow` 块，保留 `white-space:pre`，用箭头和缩进画出调用序列，用 `<span class="cmt">` 加注释。示例结构：

```html
<h3>链路 A：{角色，如"账单出单（权威值）"}</h3>
<p class="path">{入口文件路径}</p>
<div class="flow">{入口方法}()
   │
   ├─ {分支条件1} → {处理}
   └─ {分支条件2} → {处理}
   ▼
{写入点} ──► {目标表.字段}  ★权威值</div>
```

各链路画完后，用 `<div class="note danger">` 点明**矛盾点**（两条链路为何不一致 / 时序为何错位）。

### 代码 diff 写法（第二、六段）

问题代码用 `<span class="del">` 标错误行、`<span class="cmt">` 加「✗ 原因」注释；修复代码用 `<span class="add">` 标新增行。

### SQL 高亮

`.kw`（SELECT/UPDATE/WHERE/AND/JOIN/ON 等关键字）、`.str`（字符串值）、`.cmt`（注释）。

### header 与 badge

- 标题：`{问题简称} · 问题分析与修复方案`
- 副标题：一句话点明核心矛盾（如「表 X 的字段 A 与 Y 的字段 A 不自洽」）
- 代码基线：注明仓库/分支
- badge：一句话概括分歧本质

### 假设与待确认项

若 Step 1 判定为「基本明确」并带假设，或 Step 5 有「需人工核对」项，必须在报告中用 `.note.warn` 显式列出，不得隐藏。

### 文件命名与输出

- 命名：`{问题简称}问题分析与修复.html`（用 Step 1 确定的问题简称）
- 用 `fsWrite` 写入工作区根目录
- HTML 必须是完整、自包含（CSS 内联）、可直接浏览器打开的独立文件

## 产出

- `{问题简称}问题分析与修复.html`
