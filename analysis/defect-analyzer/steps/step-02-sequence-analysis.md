# Step 2: 链路时序分析

## 元信息

- execution-mode: subagent
- agent: context-gatherer

## 参数

- input: Step 1 的结构化问题陈述（现象、影响对象、代码基线）
- output: 链路时序清单（每条链路的执行路径、读写点、时点）

## 目的

缺陷几乎都发生在「链路」上：同一数据/状态被**多条链路**处理，或**生产方与消费方**在不同时点读写。本步骤要把这些链路和时点画清楚——这是后续定位根因的地图。**先有时序图，再谈根因。**

## 执行指令

使用 `invokeSubAgent`（name: `context-gatherer`）搜索代码库，梳理与缺陷相关的执行链路。

### Subagent Prompt 模板

```
针对以下缺陷，梳理代码库中涉及的执行链路与读写时点：

问题现象：{Step 1 的现象描述}
影响对象：{涉及的表/字段/状态/接口}
代码基线：{仓库范围}

请完成：

1. 识别所有相关链路。围绕问题涉及的核心数据/状态，找出对它进行「写入」和「读取/消费」的所有代码路径，通常包括：
   - 生产链路：谁计算并写入这个值（在线交易 / 出单 / 初始化 / 定时任务）
   - 消费链路：谁读取这个值做判断或计算（EOD 批处理 / 下游服务 / 报表）
   - 若存在"同一事物被多处各算一次"，逐条列出各自的计算来源

2. 对每条链路给出：
   - 入口方法（类名.方法名）+ 文件路径
   - 关键调用序列（A 调 B 调 C，标注分支条件）
   - 对目标数据的操作类型：读 / 写 / 判断
   - 执行时点：在线实时 / 日终 EOD / 初始化 / 结息日等

3. 定位读写点的确切位置：文件路径 + 行号 + 上下各 2 行上下文代码。

4. 特别标注：
   - 同一数据在不同链路用了不同的计算公式/取数来源（分歧根源）
   - 消费方读取时点是否可能早于/晚于生产方写入时点（时序根源）
   - Mapper XML 中相关 SQL 的 WHERE/ON 条件（决定命中范围）

搜索策略：
- 表名：精确匹配（下划线）+ 驼峰匹配（PO/Entity 类名）
- 字段名：下划线 + 驼峰两种形式
- 关注 *Eod*、*Batch*、*Job*、*Impl*、*Mapper.xml* 等文件
- 多仓库全覆盖

输出要求：
- 按链路分组（链路 A/B/C...），每条链路列出入口、调用序列、读写点（文件:行号）、执行时点
- 明确标注哪条链路是"权威源/生产方"、哪条是"消费方"
```

### 补充搜索（inline）

若 subagent 返回不足，用 `grepSearch` 补充：
- 按目标字段的驼峰名搜索所有 Java 文件（`setXxx` / `getXxx` / 计算表达式）
- 按表名搜索所有 XML 文件（关注 WHERE/ON/ORDER BY 中的目标字段）
- 按状态枚举值/常量名搜索触发判断逻辑

## 产出

**链路时序清单**，按链路分组，每条链路记录：

- 链路标识与角色：`链路 A（生产/权威源）`、`链路 B（另算一份）`、`链路 C（消费方）`
- 入口方法 + 文件路径
- 调用序列（含分支条件，可用缩进/箭头表示）
- 目标数据的操作：读/写/判断
- 执行时点
- 关键读写点：`文件路径:行号`

**矛盾点预判**：初步标出「哪两条链路对同一事物不同源」或「哪个消费点的时点相对写入点有先后风险」，作为 Step 3 定位根因的切入点。

> 本步骤只画链路与时点、标出可疑点，**不下最终根因结论**（留给 Step 3）。
